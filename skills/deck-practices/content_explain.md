# Content: explaining tools, mechanisms, research, and releases, and usage guides

Part of §1 "What changes by material type" of [content.md](content.md). Open it, in addition to the audience's file, when the material explains how a tool or mechanism works, reports research or an investigation (including summaries of industry trends), recommends a protection such as isolation or a sandbox, explains an article, talk, or release, or guides setup or usage. Read it together with content.md (the "Every type" rules in §1 and §0 apply too).

- [deck-content-043] For technical research reports that people without the background also read (analyses of formulas, thresholds, probabilities, and so on; internal ones too), add explanatory pages at the head of the chapter without changing the main flow or the existing pages. Their contents: a diagram of the mechanism (what comes before what), the input and output for one real data item mapped to the terms, how to read the metrics (logit and so on), how to read the figures (state clearly that they are schematic), and a before/after comparison on an example. Separate them with a section divider. Rewriting the main part in simpler terms breaks the line of reading for people who know the background.
- [deck-content-046] In materials that explain how tools, skills, or mechanisms work inside, make at least half of the main pages figures (boxes and arrows for things and actors, branches, time flow, before/after contrast). At the outline stage, decide the figure type for each page before writing. Keep tables and numbered cards only for pages used as lookup lists (tables of arguments and tools, how to read reports). Put first one overall figure of the actors (who holds what and checks what), and draw later figures with the same box names and colors. After a page that explains a procedure or a decision rule (steps, conditions), put one running example (if fictional, write 「模式」), and draw how the input changes at each step, using the same step numbers and box colors as the explanation page. Keep the source of the example as md in the material's folder.
- [deck-content-047] Pages that show how easy a tool or product is (it can be built with an agent, and so on) show real screens from actually having it build something, with measurements (number of instructions, time, cost, code written by people); do not use mock screens. For a demo, start the tool the audience uses, with the same setup as the audience (a folder with the skills installed, and so on) (if you have it read things afterwards, the screens do not reflect the setup). Write separately what the person asked for and what the tool decided.
- [deck-content-048] In materials that explain an article, talk, or release, put a 「取り上げる発表」 page right after the cover (before the question page), showing what the material is based on (medium, author, date, title, a one-line summary, link) and what the material adds (explanation and guesses not in the source). Write the main points of the original in `authorNotes`. When proper nouns in the source article (companies, products, teams, earlier products) are new to the audience and matter to the storyline (who built it, what it replaces), do not settle for a footnote: explain on one page or one step of a figure what it is, when, and how it relates. Do not only show the name and write 「同じチーム」 or 「置き換え先」.
- [deck-content-003] Materials that guide through setup or getting started first show on one page what the tool (the official CLI and so on) does automatically and what it does not, and then go into the steps you set up yourself. In an overall setup diagram or list, draw what is created automatically and what you set up yourself (step numbers) so they can be told apart by column names or step-number tags. Do not make a figure where you cannot tell which is which.
- [deck-content-044] Materials that guide people who only use AI tools (agents, material-making tools, and so on), such as sales, include one page on the recommended models and when to use which. State firmly which to choose (normally, when in a hurry, when keeping costs down), and write time, cost, and quality as numbers together with the measurement conditions (topic, page count, number of runs, list price or not). Write the weaknesses of the cheaper models (quality scores, errors) on the same page. Also write how to switch (the action in the conversation, which tools support it). Replace firm wording such as 「圧倒的に」 with numeric ratios. People who only use the tools do not have their own criteria for choosing a model.
- [deck-content-049] In a usage guide for a tool you can start just by pasting (it installs when you give a prompt to an agent, and so on), put on the first page right after the cover that prompt (one for first-timers and one for people who already have it installed) and 「これを貼れば始まる。読むのはそのあと」. Do not start from the explanation of the mechanism or steps (some people read the guide in order and never reached the part to paste).
- [deck-content-050] On guide pages for people who only use the tool, make the body of each page short tags and words (1–2 lines per box), show the explanation with figures (paths, before/after contrast, position diagrams, icons and short tags), and move the text to `authorNotes`. Do not end with a page of explanatory text in numbered steps or a page of three text-heavy cards. Things to paste, such as prompts, and tables used as lookup lists may stay, but keep the cells short.
- [deck-content-051] When updating a material that explains a tool or mechanism, first go through the changes from the version you checked before (the commit or release written in the outline) to the current version (`git log`, release notes, 「決めたこと」 in the README), and fix every page where a changed implementation appears (how to write it, file formats, commands, counts, what is asked at install time), including pages you were not told about. Update the checked version in the outline and in the dates of the source lines.
- [deck-content-010] When recommending a protection such as isolation or a sandbox, write the scope the protection contains and what stays outside it (components running in the same process, credentials, network). Read the builder's threat model (SECURITY.md and so on) first, and show the protections split the same way the builder splits them.
- [deck-content-013] For technical research on OSS or tools, do not stop at reading documents and code; run what can be run locally and check the material's claims. Before running, tell the user what you will run and where (do not wait for approval). Install it in a throwaway folder under /tmp, and run it with version upgrades and outbound sending blocked. When a risky operation is needed (passing credentials, sending outside, incurring charges, changing local settings or shared things), confirm first. For what you could not run, write the scope in the material as 「動かして確かめていない」.
- [deck-content-014] When researching to improve our own mechanisms (harness, skills, settings, and so on), do not just list the approaches you found; apply them to the actual current usage and check the fit. Apply them to local data and history (log formats and so on), the current settings, the tools in use, and so on. Decide how far to apply them by choosing what bears on the request's question.
- [deck-content-058] 依頼の見立て（「〜の不具合がある気がする」など）を確かめる調査で、見立てが外れて別の原因が分かったら、資料は見立ての検証の報告にせず、分かった事実（本当の不具合・仕組み）を主題にして書く。題・要旨・章立てに外れた見立てを据えず、見立てが外れたことは「経緯」に 1 段落で書く。社内に共有する不具合の資料は、症状・条件・再現・影響・回避策・報告先の順にし、読んだ人がすぐ当てはめられるようにする。
- [deck-content-008] When summarizing industry trends, do not stop at a table that lists specs or products; include a landscape map that shows on one page where each camp stands (example: the open spec and OSS side, and each vendor's managed-product side). With layers or kinds as rows and camps as columns, you can read where the camps connect and where they split.
