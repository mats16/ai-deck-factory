# 決まりの直し方（修正の指示の戻し方と、決まりの確かめ方）

ユーザーから修正の指示を受けたときと、決まりを足す・直すときに開く。書き留め方と、その場で戻すことは、どの会話でも要るので AGENTS.md の「修正の指示」に置いてある。ここは、どこへ戻すかと、どう確かめるか。取りこぼしは、定期の整理（`../dreaming/`）が毎日、会話の記録から拾い、決まりの変更を提案する（ユーザーが「適用」と返したら入る）。

## 決まりの層

決まりは 2 層に分かれ、ワークスペースが優先する（2026-10-11 にユーザーが決めた。ユーザー「AGENTS.md 優先です」）。ワークスペースは、やり取りの積み重ねで決まりと点検を育てていく 1 つのプロダクトとして扱い、大元（プラグイン）を直すべきものだけを PR にする（同じ日。ユーザー「セットアップ対象のフォルダ配下を1プロダクトのように育てていく方針で、やり取りの蓄積からルール・チェックすべき項目を改善、大元を改善すべき場合は PR 作成のようなコンセプト」）。

| 層 | 置き場所 | 中身 | 誰が変えるか |
|---|---|---|---|
| ワークスペース | `AGENTS.md`（どの会話でも要ること）、`rules/<スキル>/<ファイル>`（資料を作る場面だけで要ること。プラグインの同じパスのファイルに足す・上書きする）、`rules/deck-build/checks.py`（lint に足す点検） | その人・その組織の決まりと点検、修正の指示で育つもの | 作る会話がその場で戻す。dreaming は提案する。ワークスペースを git で管理していれば commit する |
| プラグイン | `skills/`（このフォルダなど。入った場所は読むだけ） | 誰が使っても同じ決まり、点検、スクリプト、テンプレート | スキル `factory-kaizen` で、過去の資料で確かめてから PR を出す（持ち主も同じ）。マージされたら `update` で届く |

- **プラグインの入った場所（`~/.claude/plugins/cache/…` など）は書き換えない。** 入れ直すと消える。
- **`rules/` は読み忘れない仕組みがある。** プラグインのファイルを開くと（Claude Code は Read・Bash・Skill、pi は read・bash）、プラグインの hook（`hooks/rules_overlay.py`）が、同じパスの `rules/` のファイルを続けて出す。出てこない環境（hook のない器）では、自分で `rules/` を開く。
- **点検もワークスペースで育てる。** 機械で見られる決まりは、まず `rules/deck-build/checks.py` に足す（lint が毎回読み込む。書き方は `rules/README.md`）。ほかの人にも効くと分かったら、`lint.py` に移す PR にする。
- **プラグインに上げる。** ワークスペースの決まりと点検のうち、ほかの人にも効くもの（その人の好みや顧客の事情でないもの）は、dreaming が「プラグインに上げる」提案にする。適用はスキル `factory-kaizen`（元のリポジトリの worktree で直し、過去の資料で前後を比べ、理由・背景・検証の結果・見た目なら画像を入れた PR を出す）。マージされたら、ワークスペースの `rules/` の写しは消す。
- `deck-research/` の調べ直しの結果（`sources.md` と、反映するスキルの直し）は、プラグインの知見なので、`factory-kaizen` で PR にする。ログと `state.md` はワークスペースの `Research/deck_research/` に残す。

## 修正の指示の戻し方

- **まとめて、決まりの形にする。** 同じ趣旨のものはまとめ、「〜のときは〜する」の形の決まりに直す。この資料の中身だけの直し（このページの言い回し、数字の差し替え）は `[戻し先: 戻さない]`。
- **戻す先:** ワークスペースに戻す（上の「決まりの層」）。どの会話でも要る決まり（社外秘の扱い、フォルダ、調べもの、いい資料の考え方の要点）は AGENTS.md。資料を作るときにだけ要ることは、AGENTS.md に足さない（Codex は AGENTS.md を 32 KiB で切り、Claude Code は毎回全部を読む。dreaming の 4h）。作り方は、下の表のプラグインのファイルと同じパスの `rules/<スキル>/<ファイル>` に書く（例: 見た目なら `rules/deck-practices/visual.md`。なければ作り、冒頭に「`deck-practices/visual.md` に足す・上書きする」と書く）。プラグインの文を変えたいときも、`rules/` に「〜は〜にする（プラグインの〇〇の節より優先）」と書く。
  - 作業の手順と残すもの: [SKILL.md](SKILL.md)
  - 構成・言葉・文体と出典の書き方: [content.md](content.md)
  - 見た目: [visual.md](visual.md)（スライド）、[visual_doc.md](visual_doc.md)（ドキュメント）
  - 流用: [reuse.md](reuse.md)
  - 材料と台帳: [materials.md](materials.md)
  - Slides API での組み方: `../deck-build/slides.md`
  - Docs API での組み方と、ドキュメントの確認と納品: `../doc-build/SKILL.md`
  - 確認と納品: `../deck-build/SKILL.md` と `../deck-review/SKILL.md`（レビューの観点は、依頼文の `prompt_slides.md`・`prompt_doc.md`）
  - この決まりの直し方: このファイル
  - 顧客ごとの好み: 顧客フォルダの直下の `CLAUDE.md`（作業の始め方の 2 で読む）

  確かめ方も決める（下の「決まりの確かめ方」）。
- **聞いてから戻すもの:** いまの決まりと食い違うものと、この資料だけのことか決まりにすることか分からないもの。`[戻し先: 未]` にして、報告で聞く。
- **残して伝える。** 戻したものは ワークスペースの `Research/deck_research/state.md` の「採用したもの」に 1 行足す（ログの欄は「修正（<フォルダ>）」）。報告の最後に、どの指示をどのファイルに戻したかを書く。

## 決まりの確かめ方

決まりは、作るときに守り、仕上げで同じ決まりを使って確かめる。考慮事項を足すより、どう確かめるかを決めるほうを先にする（2026-10-08、ユーザー「検証可能な条件に落とし込む（作成時も考慮するが、lint や review で同じ条件を使う）ことの方が重要」）。決まりを足すときは、次のどれで確かめるかも決める。

| 確かめ方 | 見るもの | 書き方 |
|---|---|---|
| lint | JSON で数えられるもの（文字の大きさ、書体、字数、位置、ページの並び）。JSON で見積もれない位置（行の折り返し、改ページ、箱の中の余白）は、Google が描いたページの画像で測る（`box_pad.py`・`doc_layout.py`） | 決まりの文に「lint が〜」と書き、ワークスペースの `rules/deck-build/checks.py` に足す（大元に上げるときは `lint.py` と `--selftest` に移す）。くり返すのを待たず、1 回目から足す |
| レビュー | 画像・テキスト・構成案と決まりの文から、AI が判断するもの（話の筋、言葉の印象、図の意味、余白や密度の見え方） | 札は付けない（「lint が」のない決まりは、レビューで見る）。deck-review の依頼文（スライドは `prompt_slides.md`、ドキュメントは `prompt_doc.md`）の観点 1〜5 のどこで見るかを確かめ、入らなければ観点に足す |
| 考え方 | AGENTS.md の「いい資料の考え方」（詳しくは content.md の 0） | 条件にしない。レビューの問いのもとにする |

- **数えられないものを、lint に無理に下ろさない。** lint を通すための書き方になる（content.md の 6 の「禁句をほかの空疎な語に置き換えるだけにしない」）。画像と決まりの文を見て AI が判断するところは、なくさない（2026-10-08、ユーザー「機械的に判断ができない、画像と指示から AI が判断するものが入る余地は重要」）。
- **良し悪しの 2 つに決めつけない。** lint の要確認は、直すか、残す理由を言う。レビューで、決まりからは決まらないもの、どちらとも取れるもの、直すと言いたいことが変わるものは「聞く」にして、迷う理由と案を添えてユーザーに返す（deck-review の「直す範囲」。2026-10-08、ユーザー「Good/Bad に強制的に分類せず人に判断を仰ぐ余地を残してください」）。
- **外れの多い条件は、直すか消す。** 要確認が毎回「残した」になる規則（`lint.py --stats`）と、確認を通ったあとにユーザーが直したのに拾えなかった条件は、dreaming の 5 が見る。
