# 資料づくりの実践

資料を作る・直すときに最初に開く。ルートの `AGENTS.md` の「いい資料の考え方」（ユーザーの鉄則と、どの資料でも同じ 6 つ）を前提に、作業の流れと、場面ごとに読むファイルを置く。[deck-practices-001] ワークスペースの決まり（`AGENTS.md` と、そこから指す `rules/<スキル>/<ファイル>`）がプラグインのスキルより優先する。食い違うときはワークスペースのほうに従う。まだユーザーが決めていない点は、各ファイルで「要判断」と書いてある。

## 全体の流れ

「〇〇の資料を作って」とだけ言われたら（フォルダの指定がなくても）、下の「作業の始め方」の 1 から順に進める。スライドもドキュメントも同じ。できている資料を直すだけの依頼は、1・2 で経緯を読んでから 8 に入る。人が答えるのは 5 の 4 つの問いと、10 の聞くことの一覧だけ。5 で構成を合意したら、ユーザーを待たずに 10 まで走り切る（下の「進め方」の deck-practices-006）。

| 工程 | すること | なぜ挟むか（何を防ぐか） | 誰が | 次へ進む条件 |
|---|---|---|---|---|
| 1〜4 準備 | フォルダを決め、過去の資料・社内の資料・顧客の材料を読む | 同じことを調べ直さない。社内の言い方とメッセージにそろえる。出典のない数字を使わない | 親（重い読み物は子） | 使う材料と出典を `references.md` に書いた |
| 5 構成の合意 | 4 つの問いを確かめ、テーマを選び、構成案を書く | 聞き手と問いを取り違えると、あとの工程を全部やり直すことになる。ここだけは人が確かめる | 人と親 | 4 つの答えと構成案（10 枚以下なら 4 つの答えと進め方） |
| 5 方針のレビュー | 会話を渡さない子が、依頼と構成案を突き合わせる | 作った側が気づかない、依頼とのずれと抜けを、組む前に見つける（組んだあとだと何枚も作り直す） | 子（② は人） | 指摘を構成案に入れた |
| 6 代表の 3 枚 | 型の違う 3 枚を組み、子にレビューさせ、型と書き方の直しを「書き方の決め」にする | 型（部品・並べ方・大きさ）と書き方の欠陥は、全ページに写る。残りを書く前に 3 枚で見つける | 親が組み、子が見る | 「書き方の決め」を書き、3 枚の JSON に入れた（3 枚は組み直さない） |
| 7 残りのページ | 3 枚を手本に残りを書く。多ければ子に分ける | 書く時間を縮める。子に分けたときの揺れは、6 の決めと 8 の検索で抑える | 親か子 | 全ページに `slides.py lint` の要修正 0 |
| 8 全体を組む | 「書き方の決め」を全ページに当て、組み、警告・JSON の検索・一覧で見る | 当て漏れ、子どうしの揺れ、ページをまたぐ大きさと位置のずれ | 親 | `check --all` の要修正 0、揺れを直した |
| 9 `/deck-review` | 会話を渡さない子が全体を見る。直して、ラウンド（頼む・指摘を確かめる・直す・組み直して確かめる）を回す | 1 枚ずつ見ていては拾えない、ページをまたぐ欠陥と、作った本人が見落とす欠陥 | 子と親 | 直す指摘が 0 か、上限のラウンド |
| 10 返す | URL、指摘の表、聞くことの一覧を 1 回で返す | 途中で聞かずに走ったものを、まとめて人が決める | 親 | 報告した |
| 11 片付け | 決まりの台帳と記録を埋め、写しを消す | 修正の指示を決まりに戻し損ねない。作業の写しを残さない | 親 | 台帳の戻し先が「未」のものが 0 |

- **10 枚以下のデッキ:** 6 を飛ばし、7 で全体を書いて、8 から続ける。方針のレビューは枚数によらず通す。
- **ドキュメント:** 6 と、7 の子に分けて書くことはない（doc.md 1 つを親が書く）。組み方と確かめ方は `../doc-build/SKILL.md`、8 の確かめは `docs.py check`。
- **確かめの道具の層**（直すたびの `slides.py lint`、区切りの `build`・`check`、区切りに 1 回の全体）は、`../deck-build/SKILL.md` の deck-build-005。工程のどこで組むかは、下の各工程に書く。

## 作業の始め方

### 1. フォルダを決める

指定がなければ依頼から決め、最初の返事で伝える（聞くのは、顧客か社内向けかを決められないときだけ）。顧客向けは `Customers/<顧客>/<内容>_<日付>/`、社内向けは `Internal/<内容>_<日付>/`、資料を作らない調べものは `Research/`（AGENTS.md の「調べもの」）。日付は会議や提出の日、分からなければ今月。ワークスペースの直下にファイルを作らない（AGENTS.md の「フォルダの置き方」）。フォルダがすでにあれば、中身（`構成案*.md`、`社内メモ_*.md`、`references.md`、`build/`）を先に読む。

- [deck-practices-002] **フォルダの名前:** 資料 1 本につき 1 フォルダ。名前は英小文字の `<内容>_<日付>`（例: `Customers/<顧客>/sample_briefing_202610/`）。1 ファイルだけの資料でもフォルダを作る。同じ資料の改訂は同じフォルダで行う。定例のたびに作り直すもの（スケジュールなど）は、回ごとに新しいフォルダにする（例: `schedule_20261007/`、`schedule_20260930/`）。社内向け（勉強会・ミートアップ・イネーブルメント）で顧客に属さないものは `Internal/` に置く。
- **フォルダの中身:** スライドとドキュメントはローカルに置かず、Drive の Google Slides・Docs に組む（URL は構成案）。`build/` を消すかは、下の「残すもの」で決める。
  ```
  構成案.md               … あれば
  社内メモ_<内容>.md      … 顧客に出さない話（話す順、要確認、個人名、社内事情）
  build/                  … 中身の正本（スライドは deck.json と 1 ページ 1 ファイルの p<番号>.json〔前の資料は pages.py〕、ドキュメントは doc.md）。その資料だけの画像は build/assets/
  references.md           … 作るときに参考にした資料の URL の台帳（書き方は materials.md の「台帳」）
  ```

### 2. 同じ顧客の過去の資料を読む

顧客フォルダの中のほかの資料、`社内メモ_*.md` に相手と経緯が、顧客の `memory.md` に資料をまたいで効く好みが書いてある（`構成案*.md` などを開くと hook が続けて出す。`rules.md` の「顧客の memory」）。顧客の `profile.md`（事業、組織、技術の構成、エンジニアの好み）も開く。ないか古ければ（`customer-profile` の「古くなる」）、構成案の前にスキル `customer-profile` で作る・取り直す。

### 3. 社内の資料を探す

まず `references_index.md` を検索する。それから同じテーマの社内のデッキ・ドキュメント・チャットの議論を探し、流用するものと、そろえるメッセージを決める（[materials.md](materials.md)、流用のしかたは [reuse.md](reuse.md)）。

### 4. 顧客の情報を集める

会議の記録と社内のチャット（`factory.toml` の `[sources]`）から、相手の関心、経緯、前回までの話を拾う（[materials.md](materials.md)）。前に引いた会議は `references_index.md` にある。数字と固有名詞は出典を控えておく。3 と 4 で読んだものは `references.md` に書く（materials.md の「台帳」）。

### 5. 構成を合意する

[deck-practices-003] **構成を合意する。** どの資料でも、作り始める前に、資料の種類・聞き手・聞き手の問い・読んだあと聞き手ができること（AGENTS.md の「いい資料の考え方」）をユーザーに確かめる。依頼から書けても確かめる。方針（構成案）を決めたあとのレビューは、`factory.toml` の `[review] plan_reviewer` に従う。`"ai"` は ①AI がレビューしてそのまま作る、`"human"` は ②人がレビューする（書いていなければ ①）。ユーザーがその資料で別のほうを言ったら、そちらにする。どちらにしたかを構成案の前提に書く。基本は ① で、人が確かめるのは最初の 4 つの問いだけ（代表の 3 枚、組むたびの check、`/deck-review` も AI）。② は移行の途中なので残している。この仕組みを説明する資料でも、そう書く。10 枚を超えるデッキや長いドキュメント、相手や目的がはっきりしないときは、`構成案.md` を書いてから作る（ほかは 4 つの答えと進め方をレビューに渡す）。スライドはページごと、ドキュメントは章ごとに要点を書き、流用する社内資料は末尾の「流用元」に URL とページ番号で書く。改訂したら `構成案_v2.md` のように番号を上げる。書く前に [content.md](content.md) を開く。

- **テーマを選ぶ。** テーマはワークスペースのテーマのファイル（`themes/slides/<名前>.json`。組み込みは visual・company）と `factory.toml` の `[docs.themes.<名前>]` で、選ぶ手がかりは `description`（Agent Skills のスキルの選び方にならった）。`slides.py themes`（ドキュメントは `docs.py themes`）が名前・既定か・テンプレートがあるか・`description` を出す。`description` と資料の種類・聞き手・会社の色の指定を突き合わせて選び、構成案の前提に「テーマ: <名前>（<選んだ理由>）」と書く。既定のテーマは、`description` で決まらないときのもの。決まらないもの、ユーザーの指定と食い違うもの、テンプレートのないテーマを選びたいときは、構成の問いと一緒に聞く。スライドは `build/deck.json` の `theme` に書く（`new` がそのテーマで作り、`lint`・`dry` もそのテーマで見る。`../deck-build/slides.md` の 3）。ドキュメントは doc.md の頭の `theme:`（既定のままなら `theme: standard`）。テーマが 2 つ以上あるのに選ばずに `new` すると、一覧を出して止まる。
- **構成案の各ページに 3 つ書く。** 見出し（短い名詞句と、言えること 1 文）、このページの型（並列・対比・推移・構造など。visual.md の 6）、根拠と出典。[deck-practices-012] 言い切りの見出しにするページ（判断を頼むページと数字の結論のページの 2〜3 枚）は、型の欄に「言い切り」と書く（content.md の 4）。数字と固有名詞は、構成案の末尾の「出典の表」（値・出典・確認済みか）にまとめる。この表は、9 のレビューの子が、スライドの数字と突き合わせる（`../deck-review/prompt_slides.md` の観点 2。数字の誤りは画像を見るモデルに判定させず、原稿と突き合わせて見る。研究 1-10）。
- **見出しと言えることだけを順に読んで、話が通るかを確かめる。** 構成案を書いたときは親が読み、方針のレビューの子にも見させる。組んだあとは、`gslides.py check` の lint が出す見出しとリードの一覧を、9 のレビューの子が読む（観点 1。中身 1-1、研究 1-1・1-2）。
- **方針のレビュー:** どの資料でも、`plan_reviewer` のほうで通す。
  - **② 人:** 構成案（構成案を書かない資料は 4 つの答えと進め方）を見せて確認を取る。
  - [deck-practices-004] **① AI:** 会話を渡さない新しいサブエージェントに、ユーザーの元の依頼（整形・整理してよいが、意味は変えない）と資料の方向性（`構成案*.md`、なければ 4 つの答えと進め方）、`社内メモ_*.md` と `references.md` のパス（出典を確かめたいときに開かせる）を渡す。会話と元の材料（議事録・文字起こしなど）は渡さない。作った側の考えに引っ張られ、別の目で見る意味が薄れる。会話で決めたこと・却下した案は、渡す前に構成案か社内メモに書き切る。頼み方は下の「進め方」の「子に頼む」。依頼文は「元の依頼と方向性を読み、方向性が依頼に答えているかを見て、ずれと抜けだけを挙げる。見ること: 聞き手・問い・読んだあとできることが依頼と合っているか、依頼にあるのに方向性にないもの・依頼にないのに足したもの、見出しだけを順に読んで話が通るか、AGENTS.md の「いい資料の考え方」の 6 つ（主役は聞き手、問いを先に、煽らない、新しい見方、公平、見解）から外れていないか」。待つ間に、代表の 3 枚（通さないデッキは全体）のページの JSON を書き始める（deck-practices-013）。指摘は自分で確かめ、直してよいものは構成案を直してそのまま 6 に進む。聞き手・問い・主張を変えるものは変えずに進め、10 の聞くことの一覧に入れる。受けた指摘と直したことは構成案の末尾に残す。
- 方針のレビューのあと、文脈を要約する道具を呼べるなら呼ぶ（deck-practices-005）。

### 6. 代表の 3 枚（10 枚を超えるスライド）

[deck-practices-007] **代表の 3 枚:** 10 枚を超えるデッキは、方針のレビューのあとに、型の違う本文のページを 3 枚（図解、表かコード、文字や要素のいちばん多いページなど）だけ組み（ページの JSON を書き、`deck.json` の `pages` に 3 枚だけを並べて `slides.py new`）、全体を組む前に自分で確かめる。表紙と扉は入れない。決まった型なので、見ても何も判断できない。承認は求めず、待たない。URL は、作った時点で伝える（`../deck-build/SKILL.md` の deck-build-003。見るかはユーザーに任せる）。確かめ方:
   1. `gslides.py check <URL>` で lint の要修正を 0 にし、3 枚の画像を自分で開く。
   2. [deck-practices-008] レビューの子（下の「進め方」の「子に頼む」）に 3 枚を頼む。依頼文は `../deck-review/prompt_slides.md` のページ担当の形（観点 2 と 5）にし、「見ること」の頭に「この 3 枚の型（図・表・文字の量と大きさ・余白）のまま残りのページを組むと全体に広がる欠陥を、先に挙げる」と足す。作り直し・移植なら、元の版の同じページの画像も渡して比べさせる（deck-review の手順 2）。待つ間に、残りのページを JSON に書く（7）。
   3. 指摘は deck-review の「直す範囲」で分け、直すものは直し、聞くものは 10 に回す。直すものは、どこまで広がるかで 3 つに分ける。3 枚は組み直さず、1・2 も通し直さずに、7 に進む。
      - 型で直すもの（同じ型のページで同じになる部品の選び方・並べ方・文字の大きさ・色、表の行の高さ、道具の制約）は、構成案の「書き方の決め」の節に 1 行ずつ書き、残りのページを書く前（子に頼む前）に 3 枚の JSON に入れる（全ページに広がるので、必ず全体を組む前に直す。`grep` で同じ部品を探す）。描き方を変える直しで効くか分からないものは、そのページに `slides.py lint` をかけて確かめ、lint で分からないときだけ 3 枚を組んで画像で見る。
      - 書き方で直すもの（改行の位置、カードの 1 行の字数、見出しの範囲と数、「だけ」「すべて」などの限定の語、言い換えた語と略語の初出）も、「書き方の決め」に 1 行ずつ書き、残りのページを書く前に 3 枚に入れる。
      - そのページだけのものは、7 で残りのページを書く間（子に頼んだら待つ間）に、そのページを直す。型に効く直しは待つ間にしない（子は 3 枚を手本として読み、写す）。
      - 3 枚の直しは、8 で全体を組むときに一緒に組み、全体の `gslides.py check --all` と `/deck-review` で見る。
   4. [deck-practices-009] 選んだ 3 枚とその理由、指摘と直したこと、「書き方の決め」の行の数と当てたページの数を、記録（ワークスペースの `Research/deck_research/log/20261009_rep3_selection.md`。資料ごとの記録なのでワークスペースに書き、決まりに効くことが分かったものだけを [rules.md](rules.md) の「決まりの層」に従って戻す。2026-10-13 に 8 の当て方とカードの高さ・最終行の警告を入れたので、効いたかを見るため、そのあとの 10 本まで）に、その冒頭の形で 1 節足す。10 の報告にも 3 行までで書く。選び方のガイドと 8 の当て方を、この記録で検討するため。
- 記録を書いたら、文脈を要約する道具を呼べるなら呼ぶ（deck-practices-005）。

根拠: 前は URL を渡して 3 枚の承認を待っていたが、見ずに承認されていた（過去の 12 回の承認で、3 枚の中身に触れた返事は 0 回。`Research/deck_rep3_approval_sessions_20261009.md`）。作り直しで元の版と比べるのは、元の版より角丸・アイコンが減ったのを、人の承認もレビューも見逃したことがあるため。3 枚を組み直さないのは、記録の 48 本で、2 回目の確認で全ページに広がる欠陥が新しく出たのは 2 本・3 件（どれも改行の直しの副作用）で、2 回目は 1 本 10〜19 分かかっていたため（`20261009_rep3_selection.md`、2026-10-17 に数えた）。3 枚から後の文脈は中央値で 23 万〜34 万トークンあり、組む工程だけで約 50 万増える（2026-10-10。`Research/pi_compaction_deck_workflow_20261010/README.md`）。AI 実践 1-3。

### 7. 残りのページを書く

10 枚以下のデッキは、ここで全体を書く。代表の 3 枚を通したデッキは、3 枚のページの JSON を手本に、残りのページを `build/p<番号>.json` に書く（`../deck-build/slides.md` の slides-034）。`deck.json` の `pages` には 3 枚だけを並べたままにし、残りはファイルに書くだけにする（並べるのは 8 で全体を組むとき）。書いたページには `slides.py lint` をかけて、要修正を 0 にする。

- [deck-practices-016] **残りのページを子に分けて書く（スライドだけ）。** 残りのページを子に分けて同時に書かせ、親が並べて組んでよい。分けるかと分け方は親が決める。分けないのは、30 枚以下のデッキと、残りが子 2 本に分けるほどないとき（子の立ち上がりの分、縮まない）。単位は章（扉）ごとか構成案の数ページごとのまとまりにし、同じ型・同じ図のページは同じ子にまとめる。いちばんの危うさは子どうしの書き方の揺れで、下の 1 と 8 の確かめで抑える。ドキュメントは doc.md 1 つを親が書くので分けない。
  1. 頼む前に、6 の 3 で直した「書き方の決め」を構成案に書き切り、3 枚の JSON に入れ、ページをまたいで同じにする数字・言い方（呼び方、略語の初出のページ）を足す。2 人以上の担当のページに出るもの（同じ道具・仕組み・段）は、1 行の説明まで決めて書く。子は代表の 3 枚のページの JSON を手本にし、書き換えない。分けるデッキでは、3 枚のレビューを待つ間に親が書くのは「書き方の決め」の下書きと依頼文で、残りのページは子が書く。
  2. 担当ごとに 1 本ずつ、`../deck-build/prompt_pages.md` で頼む。子は担当のページを JSON で 1 ページ 1 ファイル（`build/p<番号>.json`）に書き、並べた `build/pages_<担当>.json` に組まずに `slides.py lint` をかけて返す。主張・数字・順序を変えるものと、決まりから決まらないものは、構成案のとおりに書いて親へ返させる。
  3. 返ったら、子のページを `deck.json` の `pages` に構成案の順に並べ（`../deck-build/slides.md` の slides-031）、8 に進む。子が返したことは、聞くものを 10 に回す。代表の 3 枚の記録には、分け方（子の本数と担当のページ）を書く。

根拠: 親が 1 人で順に書く「全体を書いて組む」工程は 1 本の中央値 17 分（14 本）で、子に分けると 30 枚を超えるデッキで 10 分前後縮む見込み（推測。ワークスペースの `Internal/deck_speed_202610/` の構成案の「候補と見込み」⑤）。13 枚の試しで、書いた人をまたぐ揺れ 4 件はすべて、2 人以上の担当のページに出るものだった。

### 8. 全体を組んで確かめる

[deck-practices-011] **全体を組む前に、6 で直したことを残りのページに当てる。** 残りのページを JSON に書いたら、「書き方の決め」を 1 行ずつ、全ページの見出し・カード・表のセル・ノートと突き合わせて直す（見出しは本文の表とカードを数え直す。言い換えた語と略語は `build/*.json` を検索する）。3 枚で直した部品の書き方（カードの `h` を省いて中身から決める、など）も、残りのページの同じ部品に当てる。当てずに組むと、3 枚で見つけた欠陥が残りのページにそのまま出る。

当て終えたら、`deck.json` の `pages` に全ページを並べ、同じ URL に 1 回だけ組む（`slides.py build`）。続けて、全体の層の確かめ（`../deck-build/SKILL.md` の deck-build-005）をする。

- 組むときの警告（`slides.py` が標準エラーに出す。最終行が 2 字以下、`h` に収まらない、など）を 1 件ずつ見る。
- `gslides.py check <URL> --all` の要修正を 0 にし、要確認を 1 件ずつ見る。
- 子に分けて書いたデッキは、子どうしの揺れ（同じ型の部品の大きさと位置、カードの字数、言い方、ノートの調子）を、警告・`build/*.json` の検索・一覧の画像で見て直す。
- 全ページの一覧の画像（`sheet.py`）で、同じ型の部品の大きさと位置、密度、色を見る。
- 1 枚ずつ原寸では開かない。原寸の画像は、9 の 1 ラウンド目のレビューの子が見る。親が原寸で開くのは、上で引っかかったページだけ（deck-build-005 の「全体を初めて組んで、そのまま `/deck-review` に入るとき」）。

根拠: 記録の 21 本で、全体を組んでから見つかった全ページに広がる欠陥のうち、3 枚で見られる範囲のおよそ 6 割は、3 枚の直しを残りのページに当てていなかったものだった（2026-10-13 に 4 の段とカードの高さ・最終行の警告を入れた）。

### 9. 返す前に `/deck-review` で全体をレビューする

## 進め方（どの工程にも効く）

- [deck-practices-006] **5 で構成を合意したら、ユーザーを待たずに、10 で返すまで走り切る。** 途中で「聞く」になったもの（主張・数字・順序を変える案、ページを足す・消す・分ける案、決まりからは決まらないもの）は、そのページを変えずに先へ進み、10 の聞くことの一覧にまとめる（枠に収まらないときの分割だけは先に入れる。下の deck-practices-010）。書き始める前に、下の「いつ何を読むか」の表の、スライドかドキュメントの行のファイルを開く。
- [deck-practices-010] **確定した主張・数字・順序は、黙って変えない。** 枠に収まらないときは、文字を小さくする前に、言い換えと図解で収める。分ければ収まるなら、分けて組み、10 で聞く（はみ出したまま渡さない）。削らないと収まらないときは、そのページを変えずに進め、削る案を 10 で聞く（AI 実践 1-3）。
- **直すのはページの JSON（ドキュメントは doc.md）と構成案。** スライドは `build/deck.json` と 1 ページ 1 ファイルの `build/p<番号>.json` に書き（`../deck-build/slides.md` の slides-034）、`deck-build` の `slides.py` で Drive の置き場所に組む。部品は JSON の部品（`slides.py schema`）を使い、前の資料から写さない。ページの型（カード、比較、数字の強調、結論バンド）は同じ部品の並べ方にし、ページごとには中身だけを変える（AI 実践 1-9、研究 1-6）。Google Slides の画面で直したときは、同じ直しをページの JSON にも入れる（組み直すと、画面での直しは消える）。前に pages.py で作った資料は pages.py を直す（`../deck-build/slides.md` の 2）。ドキュメントは `build/doc.md` に markdown で中身だけを書き、`doc-build` の `docs.py` で組む（`../doc-build/SKILL.md` の 1）。
- **直すたびに手元で確かめ、区切りで組んで画像を見る。** 直すたびに `slides.py lint` で要修正を 0 にし、区切り（6 の 3 枚、8 で全体を組むとき、9 のラウンドの直しを入れ終えたとき）にだけ `slides.py build` と `gslides.py check` を回す。層ごとに何を見るか、画像を誰が見るかは `../deck-build/SKILL.md` の deck-build-005。ドキュメントは `docs.py check`（`../doc-build/SKILL.md` の 5）。lint の要修正は 0 にし、要確認は 1 件ずつ見て、直すか、残す理由を言えるようにする。
- **ユーザーから修正の指示を受けたら、** AGENTS.md の「修正の指示」のとおりに書き留めて直し、その場で決まりに戻す（戻す先と確かめ方は [rules.md](rules.md)）。
- **子に頼む。** 方針のレビュー、代表の 3 枚のレビュー、ページを書く子、`/deck-review` の子は、どれも会話を渡さない新しい子に、メインと同じモデルを明示して頼む（起こし方は環境ごとに `../deck-review/SKILL.md` の「頼み方」。AGENTS.md の「基本方針」）。画像は親が取り、子に `gslides.py check` を回させない（deck-build-005）。
  - [deck-practices-013] **子に頼んだら、待つ間に、子の結果によらない作業を進める。** 子は裏で走らせ（Claude Code はバックグラウンドの子、T3 Code の委任は `async`）、終わったことは通知か、その環境の待つ道具で受け取る。子の道具が終わるまで返らない環境（T3 を使わない pi の subagent の拡張など）では、待つ間の作業を先に済ませてから頼み、何本かの子は 1 つのメッセージで同時に呼ぶ。子に書かせたファイルを `sleep` で見張らない。待つ間にページの JSON（ドキュメントは doc.md）を書くときも、先に「いつ何を読むか」のスライドかドキュメントの行のファイルを開く。待つ間にすることは次のとおり。
    - 調べものの子: 構成案の骨組み（調べの結果で変わらない節）
    - 方針レビューの子（5）: 代表の 3 枚のページの JSON（代表の 3 枚を通さないデッキは、全体）
    - 代表の 3 枚のレビューの子（6）: 残りのページの JSON（子に分けるデッキは「書き方の決め」の下書きと依頼文。7 の deck-practices-016）

    子の結果に左右される作業（指摘の直し）は先にしない。待つ間に書いたものが指摘で書き直しになったら、次の直しにまとめる。子が見ている資料は、待つ間に組み直さず、`gslides.py check`・`docs.py check` も回さない。子が開くフォルダ（`/tmp/slides_<ID>/` など）の中のファイルも書き換えない（子が見ている画像が変わる）。直しの子（`../deck-review/SKILL.md` の deck-review-011）を待つ間は、011 のとおり、子の担当のページのファイルは書かずに、親の持ち分をほかのファイルに入れる。自分で見つけた直しはページの JSON（ドキュメントは doc.md）に入れておき、指摘の直しと一緒に組む。することがなくなってから待つ。T3 Code の委任は `t3_thread_wait` で待つ（threadId と runId は `delegate_task` が返す `childThreadId`・`childRunId`、`timeoutMs` は 270000）。子が終わればすぐ返り、終わらなければ 270 秒で `timedOut` が返るので呼び直す（呼び直しがプロンプトのキャッシュを 5 分より前に読み直す）。子が何本かなら、1 本ずつ順に待つ（1 つのメッセージで同時に呼ぶと、遅いほうが返るまで、先に終わった子の結果も来ない。2026-10-18 の sandbox で 4 分遅れた）。返ったら `task_status` で結果を読む（読めば、あとから同じ完了の通知が届かない）。Claude Code のバックグラウンドの子は、ターンを終えて通知を待つ。Codex と、ターンを終えると会話が終わる環境（`claude -p` など）では、子を待つ道具で待つ。pi の拡張は 30 秒以上の `sleep` を止める（Claude Code は Bash の `sleep` を自分で止める）。
- [deck-practices-005] **文脈を要約する道具を呼べるなら、工程の区切りで呼ぶ。** 道具（pi の `compact_context` など）がなければ呼ばずに進める。ユーザーに要約を頼んで止まらない（勧めても使われなかった）。区切りは 3 つ。方針のレビューのあと（6 に入る前）、代表の 3 枚の記録を書いたあと（全体を組む前）、`/deck-review` の各ラウンドで直したページを確かめたあと（`../deck-review/SKILL.md` の deck-review-013）。呼ぶ前に、決まったこと・却下した案と理由・出典・要確認・聞くことの一覧・次にすることを `構成案*.md`・`社内メモ_*.md` に書き切る（修正の指示は決まりの台帳、レビューの指摘は deck-review の `$D/review.md`）。道具がなくても書く（自動の要約でも落ちないように）。要約には道具の結果の先頭しか残らない（pi は 2,000 文字）。道具が続きの指示を受け取るなら（`compact_context` の `next`）、手順のどこから続けるかと、読み直すファイル（下の deck-practices-015）を書く。
  - [deck-practices-015] **要約のあと読み直すのは、次の手順に要るファイルだけにする。** 作業中のフォルダの `構成案*.md`・`社内メモ_*.md`、その資料の指摘（`ledger.py list --deck <資料のフォルダ>`）、顧客向けなら顧客の `memory.md`・`profile.md`、続ける手順の節。`references.md` は出典を確かめるときに開く。スキルのファイル（`slides.md`・`visual.md` など。1 本 2 万文字前後）とページの JSON は丸ごと読み直さず、次に使う節と直すページを `grep -n` で探して開く。

## やらないこと

- HTML・Marp・Slidev を経由してスライドにしない。編集できるスライドの品質が落ちる。下書きや見た目の検討に使うのはよい（AI 実践 2 節）。
- NotebookLM や画像生成で作ったスライドを納品物に入れない。全面が画像になり、Google Slides で直せない。素材として使ったときは、`gslides.py check` の `deck.md` にテキストが出るかを確かめる（AI 実践 1-8）。
- 見た目の良し悪しを、画像を見るモデルに点数で付けさせない。人の評価との相関が低い（研究 1-3）。欠陥を挙げさせる。
- AI がよく出すデザイン案（公式の pptx スキルの「Design Ideas」など）のうち、和文に合わないもの（visual.md の 8）は使わない。
