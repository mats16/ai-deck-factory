# 資料づくりの実践

資料を作る・直すときに最初に開く。ルートの `AGENTS.md` の「いい資料の考え方」（ユーザーの鉄則と、どの資料でも同じ 6 つ）を前提に、作業の始め方と、場面ごとに読むファイルを置く。[deck-practices-001] ワークスペースの決まり（`AGENTS.md` と、そこから指す `rules/<スキル>/<ファイル>`）がプラグインのスキルより優先する。食い違うときはワークスペースのほうに従う。まだユーザーが決めていない点は、各ファイルで「要判断」と書いてある。

## 作業の始め方

「〇〇の資料を作って」とだけ言われたら（フォルダの指定がなくても）、次の順に進める。スライドもドキュメントも同じ。できている資料を直すだけの依頼は、1・2 で経緯を読んでから 6 に入る。

1. **フォルダを決める。** 指定がなければ依頼から決め、最初の返事で伝える（聞くのは、顧客か社内向けかを決められないときだけ）。顧客向けは `Customers/<顧客>/<内容>_<日付>/`、社内向けは `Internal/<内容>_<日付>/`、資料を作らない調べものは `Research/`（AGENTS.md の「調べもの」）。日付は会議や提出の日、分からなければ今月。ワークスペースの直下にファイルを作らない（AGENTS.md の「フォルダの置き方」）。フォルダがすでにあれば、中身（`構成案*.md`、`社内メモ*.md`、`references.md`、`build/`）を先に読む。
   - [deck-practices-002] **フォルダの名前:** 資料 1 本につき 1 フォルダ。名前は英小文字の `<内容>_<日付>`（例: `Customers/<顧客>/sample_briefing_202610/`）。1 ファイルだけの資料でもフォルダを作る。同じ資料の改訂は同じフォルダで行う。定例のたびに作り直すもの（スケジュールなど）は、回ごとに新しいフォルダにする（例: `schedule_20261007/`、`schedule_20260930/`）。社内向け（勉強会・ミートアップ・イネーブルメント）で顧客に属さないものは `Internal/` に置く。
   - **フォルダの中身:** スライドとドキュメントはローカルに置かず、Drive の Google Slides・Docs に組む（URL は構成案）。`build/` を消すかは、下の「残すもの」で決める（Google Slides の資料は `build/pages.py` がないと組み直せない）。
     ```
     構成案.md               … あれば
     社内メモ_<内容>.md      … 顧客に出さない話（話す順、要確認、個人名、社内事情）
     build/                  … 生成スクリプトと中身の正本（スライドは slides.py を読み込む pages.py、ドキュメントは docs.py が読む doc.md）。その資料だけの画像は build/assets/
     references.md           … 作るときに参考にした資料の URL の台帳（書き方は materials.md の「台帳」）
     ```
2. **同じ顧客の過去の資料を読む。** 顧客フォルダの中のほかの資料、`社内メモ_*.md` に相手と経緯が、顧客の `memory.md` に資料をまたいで効く好みが書いてある（`構成案*.md` などを開くと hook が続けて出す。`rules.md` の「顧客の memory」）。
3. **社内の資料を探す。** まず `references_index.md` を検索する。それから同じテーマの社内のデッキ・ドキュメント・チャットの議論を探し、流用するものと、そろえるメッセージを決める（[materials.md](materials.md)、流用のしかたは [reuse.md](reuse.md)）。
4. **顧客の情報を集める。** 会議の記録と社内のチャット（`factory.toml` の `[sources]`）から、相手の関心、経緯、前回までの話を拾う（[materials.md](materials.md)）。前に引いた会議は `references_index.md` にある。数字と固有名詞は出典を控えておく。3 と 4 で読んだものは `references.md` に書く（materials.md の「台帳」）。
5. [deck-practices-003] **構成を合意する。** どの資料でも、作り始める前に、資料の種類・聞き手・聞き手の問い・読んだあと聞き手ができること（AGENTS.md の「いい資料の考え方」）をユーザーに確かめる。依頼から書けても確かめる。方針（構成案）を決めたあとのレビューは、`factory.toml` の `[review] plan_reviewer` に従う。`"ai"` は ①AI がレビューしてそのまま作る、`"human"` は ②人がレビューする（書いていなければ ①）。ユーザーがその資料で別のほうを言ったら、そちらにする。どちらにしたかを構成案の前提に書く。基本は ① で、人が確かめるのは最初の 4 つの問いだけ（代表の 3 枚、組むたびの check、`/deck-review` も AI）。② は移行の途中なので残している。この仕組みを説明する資料でも、そう書く。10 枚を超えるデッキや長いドキュメント、相手や目的がはっきりしないときは、`構成案.md` を書いて、選んだほうのレビューを通してから作る。スライドはページごと、ドキュメントは章ごとに要点を書き、流用する社内資料は末尾の「流用元」に URL とページ番号で書く。改訂したら `構成案_v2.md` のように番号を上げる。書く前に [content.md](content.md) を開く。
   - **テーマを選ぶ。** テーマは `factory.toml` の `[slides.themes.<名前>]`・`[docs.themes.<名前>]` で、選ぶ手がかりは `description`（Agent Skills のスキルの選び方にならった）。`slides.py themes`（ドキュメントは `docs.py themes`）が名前・既定か・テンプレートがあるか・`description` を出す。`description` と資料の種類・聞き手・会社の色の指定を突き合わせて選び、構成案の前提に「テーマ: <名前>（<選んだ理由>）」と書く。既定のテーマは、`description` で決まらないときのもの。決まらないもの、ユーザーの指定と食い違うもの、テンプレートのないテーマを選びたいときは、構成の問いと一緒に聞く。組むときは `slides.py new … --theme <名前>`、ドキュメントは doc.md の頭の `theme:`（既定のままなら `theme: standard`）。テーマが 2 つ以上あるのに選ばずに `new` すると、一覧を出して止まる。
   - **構成案の各ページに 3 つ書く。** 見出し（短い名詞句と、言えること 1 文）、このページの型（並列・対比・推移・構造など。visual.md の 6）、根拠と出典。[deck-practices-012] 言い切りの見出しにするページ（判断を頼むページと数字の結論のページの 2〜3 枚）は、型の欄に「言い切り」と書く（content.md の 4）。数字と固有名詞は、構成案の末尾の「出典の表」（値・出典・確認済みか）にまとめる。仕上げでは、スライドの数字がこの表にあるかを突き合わせる（研究 1-10）。
   - **見出しと言えることだけを順に読んで、話が通るかを確かめる。** 構成案の段階と、`gslides.py check` の lint が出す見出しとリードの一覧の両方で行う（中身 1-1、研究 1-1・1-2）。
   - **方針のレビュー:**
     - **② 人:** 構成案（構成案を書かない資料は 4 つの答えと進め方）を見せて確認を取る。
     - [deck-practices-004] **① AI:** 会話を渡さない新しいサブエージェントに、ユーザーの元の依頼（整形・整理してよいが、意味は変えない）と資料の方向性（`構成案*.md`、なければ 4 つの答えと進め方）、`社内メモ_*.md` と `references.md` のパス（出典を確かめたいときに開かせる）を渡す。会話と元の材料（議事録・文字起こしなど）は渡さない。作った側の考えに引っ張られ、別の目で見る意味が薄れる。会話で決めたこと・却下した案は、渡す前に構成案か社内メモに書き切る。モデルは AGENTS.md の「基本方針」のとおり、メインと同じものを指定する。依頼文は「元の依頼と方向性を読み、方向性が依頼に答えているかを見て、ずれと抜けだけを挙げる。見ること: 聞き手・問い・読んだあとできることが依頼と合っているか、依頼にあるのに方向性にないもの・依頼にないのに足したもの、見出しだけを順に読んで話が通るか、AGENTS.md の「いい資料の考え方」の 6 つ（主役は聞き手、問いを先に、煽らない、新しい見方、公平、見解）から外れていないか」。指摘は自分で確かめ、直してよいものは構成案を直してそのまま 6 に進む。聞き手・問い・主張を変えるものは変えずに進め、最後の報告の聞くことの一覧に入れる。受けた指摘と直したことは構成案の末尾に残す。
   - [deck-practices-005] **文脈を要約する道具を呼べるなら、工程の区切りで呼ぶ。** 道具（pi の `compact_context` など）がなければ呼ばずに進める。ユーザーに要約を頼んで止まらない（勧めても使われなかった）。区切りは 3 つ。方針のレビューのあと（6 に入る前）、代表の 3 枚の記録を書いたあと（全体を組む前）、`/deck-review` の各周で直したページを確かめたあと（`../deck-review/SKILL.md` の deck-review-013）。呼ぶ前に、決まったこと・却下した案と理由・出典・要確認・聞くことの一覧・次にすることを `構成案*.md`・`社内メモ_*.md` に書き切る（修正の指示は決まりの台帳、レビューの指摘は deck-review の `$D/review.md`）。道具がなくても書く（自動の要約でも落ちないように）。要約には道具の結果の先頭しか残らない（pi は 2,000 文字）。道具が続きの指示を受け取るなら（`compact_context` の `next`）、手順のどこから続けるかと、読み直すファイル（下の deck-practices-015）を書く。代表の 3 枚から後の文脈は中央値で 23 万〜34 万トークンあり、1 回の呼び出しは 10〜20 万で 9.6 秒、20〜30 万で 11.7 秒、30〜40 万で 17.0 秒かかる。区切りで呼んだのは方針のレビューのあとと全体を組む前が多く、`/deck-review` の周ではほとんど呼ばれず、40 万の自動の要約が走っていた（2026-10-14。pi の記録 23 本。ワークスペースの `Internal/deck_speed_202610/社内メモ_計測の結果.md`、同じフォルダのスライドの p.7・p.12。前の調べは `Research/pi_compaction_deck_workflow_20261010/README.md`）。
     - [deck-practices-015] **要約のあと読み直すのは、次の手順に要るファイルだけにする。** 作業中のフォルダの `構成案*.md`・`社内メモ_*.md`、その資料の指摘（`ledger.py list --deck <資料のフォルダ>`）、顧客向けなら顧客の `memory.md`、続ける手順の節。`references.md` は出典を確かめるときに開く。スキルのファイル（`slides.md`・`visual.md` など。1 本 2 万文字前後）と pages.py は丸ごと読み直さず、次に使う節と直すページを `grep -n` で探して開く。要約の直後に 8〜9 万だった文脈が、まとめて読み直したことで、30 回の呼び出しのあと中央値 21 万に戻っていた（同じ記録）。
6. [deck-practices-006] **作って、確かめる。** 書き始める前に、AGENTS.md の「場面ごとに開くファイル」の表の、スライドかドキュメントの行のファイルを開く。6 は、ユーザーを待たずに、返す（`/deck-review` のあとの報告）まで走り切る。途中で「聞く」になったもの（主張・数字・順序を変える案、ページを足す・消す・分ける案、決まりからは決まらないもの）は、そのページを変えずに先へ進み、最後の報告の聞くことの一覧にまとめる（枠に収まらないときの分割だけは先に入れる。下の「確定した主張・数字・順序」）（過去の 12 回の承認で、3 枚の中身に触れた返事は 0 回だった。`Research/deck_rep3_approval_sessions_20261009.md`）。
   - [deck-practices-007] **代表の 3 枚:** 10 枚を超えるデッキは、方針のレビューのあとに、型の違う本文のページを 3 枚（図解、表かコード、文字や要素のいちばん多いページなど）だけ組み（`slides.py new`）、全体を組む前に自分で確かめる（AI 実践 1-3）。表紙と扉は入れない。決まった型なので、見ても何も判断できない。ユーザーには見せず、承認を待たない。前は URL を渡して承認を待っていたが、見ずに承認されていた。確かめ方:
     1. `gslides.py check <URL>` で lint の要修正を 0 にし、3 枚の画像を自分で開く。
     2. [deck-practices-008] レビューの子（`../deck-review/SKILL.md` の「頼み方」）に 3 枚を頼む。依頼文は `../deck-review/prompt_slides.md` のページ担当の形（観点 2 と 5）にし、「見ること」の頭に「この 3 枚の型（図・表・文字の量と大きさ・余白）のまま残りのページを組むと全体に広がる欠陥を、先に挙げる」と足す。作り直し・移植なら、元の版の同じページの画像も渡して比べさせる（deck-review の手順 2。元の版より角丸・アイコンが減ったのを、人の承認もレビューも見逃したことがある）。
     3. 指摘は deck-review の「直す範囲」で分け、直すものは直し、聞くものは最後の報告に回す。直すものは、どこまで広がるかで 3 つに分ける。型の関数か共通の値（文字の大きさ・余白・色・箱の高さ）で直すものは、関数か値を直す（全ページに広がるので、必ず全体を組む前に直す）。書き方で直すもの（改行の位置、カードの 1 行の字数、見出しの範囲と数、「だけ」「すべて」などの限定の語、言い換えた語と略語の初出）は、直したうえで構成案の「書き方の決め」の節に 1 行ずつ書く（関数を直しても、ほかのページの文には当たらない）。そのページだけのものは、そのページを直す。直したら 3 枚を組み直し、1・2 をもう 1 回だけ通す。2 回目で残ったものは、全体を組んだあとの `/deck-review` で見る。
     4. [deck-practices-011] **全体を組む前に、3 で直したことを残りのページに当てる。** 残りのページを pages.py に書いたら、「書き方の決め」を 1 行ずつ、全ページの見出し・カード・表のセル・ノートと突き合わせて直す（見出しは本文の表とカードを数え直す。言い換えた語と略語は pages.py を検索する）。3 枚で直した部品の呼び方（`d.card` の高さを省いて中身から決める、など）も、残りのページの同じ部品に当てる。全体を組んだら、組むときの警告（`slides.py` が標準エラーに出す。最終行が 2 字以下など）を 1 件ずつ見る。当てずに組むと、3 枚で見つけた欠陥が残りのページにそのまま出る（記録の 21 本で、全体を組んでから見つかった全ページに広がる欠陥のうち、3 枚で見られる範囲のおよそ 6 割がこれだった）。
     5. [deck-practices-009] 選んだ 3 枚とその理由、指摘と直したこと、「書き方の決め」の行の数と当てたページの数を、記録（ワークスペースの `Research/deck_research/log/20261009_rep3_selection.md`。資料ごとの記録なのでワークスペースに書き、決まりに効くことが分かったものだけを [rules.md](rules.md) の「決まりの層」に従って戻す。2026-10-13 に 4 の段とカードの高さ・最終行の警告を入れたので、効いたかを見るため、そのあとの 10 本まで）に、その冒頭の形で 1 節足してから、同じ URL に全体を組む（`slides.py build`）。最後の報告にも 3 行までで書く。選び方のガイドと 4 の段を、この記録で検討するため。
   - **代表の 3 枚の記録を書いたら、全体を組む前に文脈を要約する**（道具を呼べるときだけ。deck-practices-005）。組む工程だけで文脈が約 50 万増え、6 の始まりで 1 回要約するだけでは足りない（2026-10-10。`Research/pi_compaction_deck_workflow_20261010/README.md`）。
   - **直すのは pages.py（ドキュメントは doc.md）と構成案。** スライドは `deck-build` の `slides.py` で Drive の置き場所に組む。Google Slides の画面で直したときは、同じ直しを pages.py にも入れる。組み直すと、画面での直しは消える。ページの型（カード、比較、数字の強調、結論バンド）は関数にし、ページごとには中身だけを渡す（AI 実践 1-9、研究 1-6）。共通の部品は deck-build の `scripts/slides.py` から読み込み、前の資料から写さない（`../deck-build/slides.md` の 2）。ドキュメントは `build/doc.md` に markdown で中身だけを書き、`doc-build` の `docs.py` で組む（`../doc-build/SKILL.md` の 1）。
   - **組むたびに確かめる。** スライドは `gslides.py check`（lint・テキスト・Google が描いたページの画像）、ドキュメントは `docs.py check`（lint・テキスト・Google が書き出した PDF のページの画像・画像でのレイアウトの確かめ、doc.md と組んだ文書の照合、テンプレートとの照合）。照合の要修正も 0 にする。lint の要修正は 0 にする。要確認は 1 件ずつ見て、直すか、残す理由を言えるようにする。変えたページの画像を自分で開いて直す。
   - [deck-practices-010] **確定した主張・数字・順序は、黙って変えない。** 枠に収まらないときは、文字を小さくする前に、言い換えと図解で収める。分ければ収まるなら、分けて組み、最後の報告で聞く（はみ出したまま渡さない）。削らないと収まらないときは、そのページを変えずに進め、削る案を最後の報告で聞く（AI 実践 1-3）。
   - **ユーザーから修正の指示を受けたら、** AGENTS.md の「修正の指示」のとおりに書き留めて直し、その場で決まりに戻す（戻す先と確かめ方は [rules.md](rules.md)）。
   - **返す前に、`/deck-review` で全体をレビューする。** 別のサブエージェントの目と全ページの一覧で、ページをまたぐ欠陥も見る。`factory.toml` の `[review] deck_review_max_rounds` の周まで（書いていなければ 3 周）、直して不具合が増えたら戻す（研究 1-3・1-4）。直したら、スライドとドキュメントは同じ URL に組み直し（`../deck-build/SKILL.md` の「納品物」）。代表の 3 枚を通したデッキは、レビューで見つかった全ページに広がる欠陥を、代表の 3 枚の記録の同じ節の「あと」に書いてから返す（4 で当てたのに残ったものは、そう書く）。
7. **片付ける。** この資料の指摘に、戻し先が「未」のまま残ったものがないか（`ledger.py list --deck <資料のフォルダ> --open`）と、代表の 3 枚の記録の「あと」が埋まっているかを確かめる（[rules.md](rules.md)）。使った資料を `references_index.md` に足す。確認用の PDF や画像はフォルダに残さない（下の「残すもの」）。

## 残すもの

- 残すのは成果物（Drive の Google Slides・Google Docs、html・csv、2026-10-07 より前の pptx、2026-10-09 より前の docx、HTML から作って渡した PDF）と、文書（`構成案*.md`、`社内メモ_*.md`、`references.md`、調査メモ）。
- 生成スクリプト、検証用の画像や PDF、`__pycache__`、`.venv`、旧版の構成案は、資料を使い終わったら消す。
- `build/` は、これから直す見込みのある資料にだけ残す。いまある `build/` は `find Customers Internal -maxdepth 3 -type d -name build` で見る。あることだけで消すかを決めず、各資料の作業状況と直す見込みを確かめる。Google Slides の資料は `build/pages.py`、Google Docs の資料は `build/doc.md` がないと組み直せないので、直す見込みがなくなるまで消さない。`build/` を消した資料と、画面で直し始めたドキュメントは、画面で直し、以後は組み直さない。docx と 2026-10-07 より前の pptx は、公式スキルの編集の手順（unzip → XML を書き換え → zip）で直す。

## いつ何を読むか

場面ごとに開くファイルは、AGENTS.md の「場面ごとに開くファイル」の表（材料は [materials.md](materials.md)、流用は [reuse.md](reuse.md)、構成案と言葉は [content.md](content.md)、見た目は [visual.md](visual.md)（ドキュメントは [visual_doc.md](visual_doc.md)）、決まりの直し方は [rules.md](rules.md)、組み方・確認・納品は `../deck-build/`（ドキュメントは `../doc-build/`）、返す前のレビューは `../deck-review/SKILL.md`）。プラグインのファイル（例: `deck-practices/visual.md`）を開くと、ワークスペースの同じパスの `rules/<スキル>/<ファイル>`（例: `rules/deck-practices/visual.md`）がプラグインの hook で続けて出る（出ない環境では自分で開く）。そこにはワークスペースだけの足しと上書きがあり、そちらを優先する（[rules.md](rules.md) の「決まりの層」）。

## やらないこと

- HTML・Marp・Slidev を経由してスライドにしない。編集できるスライドの品質が落ちる。下書きや見た目の検討に使うのはよい（AI 実践 2 節）。
- NotebookLM や画像生成で作ったスライドを納品物に入れない。全面が画像になり、Google Slides で直せない。素材として使ったときは、`gslides.py check` の `deck.md` にテキストが出るかを確かめる（AI 実践 1-8）。
- 見た目の良し悪しを、画像を見るモデルに点数で付けさせない。人の評価との相関が低い（研究 1-3）。欠陥を挙げさせる。
- AI がよく出すデザイン案（公式の pptx スキルの「Design Ideas」など）のうち、和文に合わないもの（visual.md の 8）は使わない。
