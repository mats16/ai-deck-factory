# Asking and waiting for child agents

Open before you start any child agent (plan review, source check, three-page review, page writers, `/deck-review`, fix owners, research). It holds how to start one in each environment and what to do while it runs.

## Start a child

- [deck-agents-008] **Use an independent context and the same model as the main agent.** Do not pass the conversation history from building; give a new subagent only the per-format prompt and the paths of the material. Have it read the intent from the outline's 「資料の種類・聞き手・聞き手の問い・読んだあと聞き手ができること」. If you are building with Opus, use Opus; with Sonnet, Sonnet; with Codex, the main agent's actual model ID.
- **Claude Code:** ask a new `general-purpose` child. For the model, pass the same alias as the main agent, as in 「基本方針」 of AGENTS.md. If a review is shallow, check the images it opened and its grounds, and ask a new child again with the same model. Do not change the model silently.
- **Codex:** create a new child with `fork_turns: "none"`, and set `model` to the main agent's actual model ID and `reasoning_effort` to the main agent's current setting explicitly. This skill instructs you to specify model and effort explicitly. Do not fork the full history. Do not omit them, because the `[agents]` default model can differ from the main agent.
- [deck-agents-009] **When using the T3 Code delegation tool:** in the live capability list, confirm that the same provider instance and model as the main agent are available, and create a new delegated task targeting them. Make each round a new task, and pass the prompt, the previous findings, how they were handled, and open points explicitly. Set `mode` to `async`, finish the waiting-time work, then wait with `t3_thread_wait` (how to wait: deck-agents-013 below). `mode: "wait"` can return "fetch failed" while the child is still running. If that happens, do not ask again; check with `task_status` whether the child is running, and wait again with `t3_thread_wait`.
- In an environment where you cannot launch a child with the same model and without the conversation history, do not silently switch to another model or a full-history fork; report the constraint. When delivering, report how you launched the child, which model you specified, and whether you could confirm the actual model.

## Ask and wait

- **Ask a child agent.** The plan review, the three-page review, page-writing child agents, and `/deck-review` child agents are all asked of a new child agent without the conversation, with the same model as the main agent stated explicitly (how to start one in each environment: "Start a child" above; 「基本方針」 in AGENTS.md). The parent takes the images; do not have child agents run `gslides.py check` (slides-flow-005).
  - [deck-agents-013] **After asking a child agent, do work that does not depend on its result while waiting.** Run child agents in the background (Claude Code: background child agents; T3 Code: delegation with `async`), and receive completion by notification or with that environment's wait tool. In environments where the child-agent tool does not return until the child is done (e.g. pi's subagent extension without T3), finish the waiting-time work first, then ask, and call several child agents at once in one message. Do not watch files a child agent writes with `sleep`. When writing page JSON (for documents, doc.md) while waiting, first open the files in the deck or document row of "What to read when".
    Do not do work that depends on the child agent's result (fixing findings) first. If something you wrote while waiting must be rewritten because of the findings, fold it into the next fix. Do not rebuild the material a child agent is looking at while waiting, and do not run `gslides.py check` or `docs.py check`. Do not rewrite files in the folders a child agent opens (`/tmp/slides_<ID>/` etc.) either (the images the child agent sees would change). While waiting for fix child agents (deck-review-011 in `../deck-review/prompt_fix.md`), as 011 says, do not write the files of the child agent's pages; put the parent's share into other files. Put fixes you find yourself into the page JSON (for documents, doc.md) and build them together with the fixes for the findings. Wait only when there is nothing left to do. For T3 Code delegation, wait with `t3_thread_wait` (threadId and runId are the `childThreadId` and `childRunId` returned by `delegate_task`; `timeoutMs` is 270000). It returns as soon as the child agent finishes; if it does not finish, it returns `timedOut` after 270 seconds, so call it again (calling again refreshes the prompt cache before its 5 minutes run out). With several child agents, wait for one at a time in order (if you call the waits at once in one message, the results of child agents that finished early do not arrive until the slowest one returns; in the sandbox on 2026-10-18 this caused a 4-minute delay). When it returns, read the result with `task_status` (once read, the same completion notification does not arrive later). For Claude Code background child agents, end the turn and wait for the notification. In Codex and in environments where ending the turn ends the conversation (`claude -p`, etc.), wait with the tool for waiting on child agents. pi's extension stops a `sleep` of 30 seconds or more (Claude Code stops a Bash `sleep` itself).
    What to do while waiting:
    - Research child agent: the skeleton of the outline (the sections the research results do not change)
    - Plan-review child agent (5): the page JSON of the three representative pages (for decks that skip them, the whole)
    - Three-page review child agent (6): the JSON of the remaining pages (for split decks, the draft of 「書き方の決め」 and the request texts; slides-flow-016 in 7)
    - Child agents writing the remaining pages (7): fixes to the three representative pages that affect only that page (step 3 of 6)
    - Source-check child agents (5, 9; deck-flow-019): nothing waits for them; continue the step you are on
    - `/deck-review` child agents (9): the records up to the previous round (the findings table, 「あと」 in the three-representative-pages log), `references.md`, the lint `要確認`, and fixes you found yourself

## Evidence

- Waiting: in 23 pi logs, out of a median of 146 minutes per material, the parent sat waiting for child agents for a median of 22.5 minutes. In one 23-page material, the first 135 minutes had 6 waits totaling 30 minutes, with the parent either watching the child agents' files with `sleep` or stopped waiting for a notification (`Internal/deck_speed_202610/社内メモ_計測の結果.md`, p.8 and p.10 of the material in the same folder). In one 25-page material on 2026-10-16 (98 minutes), the parent waited 6 times with `sleep 270` and `task_status`, and it took about 11 minutes in total between the child agents finishing and the parent noticing. In a 14-page sandbox run on 2026-10-18 (50 minutes) using `t3_thread_wait`, all 4 waits returned within 1 second of the child agent finishing.
