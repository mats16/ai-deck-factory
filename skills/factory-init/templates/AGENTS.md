# このワークスペースの運用ルール

AI Deck Factory（プラグイン）で、スライドとドキュメントを作るワークスペース。使う人の名前・役割・担当の顧客は、`factory.toml` の `user.profile` が指すファイルにある。要るときに読み、このフォルダの文書には写さない。顧客向けの資料（`Customers/`）、社内向けの資料（`Internal/`）、調べものの結果（`Research/`）を作り、置いておく。

このファイルには、どの会話でも要ることだけを書く。資料を作る・直すときにだけ要ることは、プラグインのスキルと、ここから指す `rules/` にある（下の「資料を作る・直すとき」）。

## 決まりの優先

- **このワークスペースの決まりが、プラグインのスキルより優先する。** ワークスペースの決まりは、このファイルと `rules/<スキル>/<ファイル>`（プラグインの同じパスのファイルへの足しと上書き）。食い違うときは、こちらに従う。
- **このワークスペースは、やり取りで育てる 1 つのプロダクト。** 修正の指示は、決まり（このファイルと `rules/`）と点検（`rules/deck-build/checks.py`）に戻す。プラグインの入った場所は書き換えない（入れ直すと消える）。
- **大元を直すべきものは Issue にする。** ほかの人にも効くものは、dreaming が「プラグインに上げる」提案にし、スキル `factory-kaizen` で過去の資料で確かめてから Issue を出す（スキル `deck-practices` の `rules.md` の「決まりの層」）。

## 基本方針

- **日本語で作る。** 英語でと言われたときだけ英語にする（本文、スピーカーノート、ファイル名まで）。
- **車輪の再発明をしない。** 作る前に社内の既存資料を探して、使えるものは積極的に流用する。ページや図だけでなく、メッセージング（製品の位置づけ、言い回し、用語の訳）も社内の資料にそろえる。
- **顧客の情報は、会議の記録と社内のチャットから取る。** 顧客との会議のほか、営業との事前の打ち合わせも、相手と経緯を知るのに役に立つ（道具の使い方は `deck-practices` の `materials.md`）。
- **スライドは Google Slides を Slides API で、ドキュメントは Google Docs を Docs API で直接組む。** スライドは `deck-build` の `slides.py`、ドキュメントは `doc-build` の `docs.py` で組む。pptx・docx は作らない。Word が要るときは Google Docs から書き出す。
- **納品は Google Drive の URL で渡し、確認を頼む。** PDF は作らない（`deck-build` の SKILL.md の「納品物」）。
- **サブエージェントを呼ぶときは、必ずモデルを指定し、原則メインと同じモデルにする。** 省くと、会社の設定や既定値で別のモデルになる。Claude Code ではメインと同じ別名（Opus なら `opus`）を渡す。
- **環境を確かめるときは `factory-doctor`、ワークスペースを作るときは `factory-init`。** 401・403 や、スクリプトが設定を見つけられないときも `factory-doctor` から始める。

## いい資料の考え方

鉄則は「営業色を出さずに、お客様の目線で情報を整理するところから入る。課題や問題意識について目線をそろえることは、提案の中身より重要」。顧客向けの提案だけでなく、社内向けの資料にも当てはめる。どの資料でも次の 6 つを守る。詳しい書き方は `deck-practices` の `content.md` の「0. どの資料でも同じこと」。

1. **主役は聞き手。** 聞き手の状況と問いから始め、自社や機能の紹介から始めない。
2. **問いを先にそろえる。** 問いは聞き手が実際に持っているものを拾い、出典を控える。こちらの見立てには「仮説」と書く。
3. **課題は影響まで書く。煽らない。** 数字は出典のあるものだけを使う。不安をあおる言い方はしない。
4. **聞き手の見方をなぞるだけにしない。** 聞き手がまだ持っていない見方を足す。ただし、特定の製品でしか答えられない形にしない。
5. **公平に書く。** 他社の製品や OSS、今の仕組みでできることは、できると書く。自社の製品の向かないところも書く。
6. **見解ははっきり言う。** 推奨か使い分けを、理由と一緒に書く。

## 資料を作る・直すとき

「〇〇の資料を作って」「このページを直して」と言われたら、作業に入る前にスキル `deck-practices` の SKILL.md を開き、「全体の流れ」と「作業の始め方」の順に進める（スライドもドキュメントも同じ）。場面ごとに開くファイルは、同じ SKILL.md の「いつ何を読むか」の表。開く前から、次の 2 つは守る。

- 作り始める前に、資料の種類・聞き手・聞き手の問い・読んだあと聞き手ができることをユーザーに確かめる（依頼から書けても確かめる）。
- ユーザーに返す前に、スキル `deck-review` で全体をレビューする。

### 修正の指示

作っている途中にユーザーがチャットで出した修正の指示は、その資料を直すだけで終わらせない。次の資料でも同じことを言われないよう、その場でワークスペースの決まり（このファイルか `rules/`）に戻す。戻す先・確かめ方・聞いてから戻すものは `deck-practices/rules.md`。取りこぼしは、定期の整理（スキル `dreaming`）が会話の記録から拾う。

- **受けたらすぐ決まりの台帳に書く。** `python3 <スキル deck-practices のフォルダ>/scripts/ledger.py add --deck <資料のフォルダ> --quote "<ユーザーの言葉（できるだけ原文）>" --fix "<直した箇所>" --to <戻し先> --check <lint・レビュー・なし>`。ユーザーがはっきり決めたこと（案から選んだ、言い切った）には `--decided` を付ける。台帳はこのワークスペースの `.factory/ledger.jsonl`（顧客のことが入るので、外に写さない）。会話はコンパクションで要約になり、指示が落ちることがある。
- **直したら、その場で戻す。** 片付けまで待たない。決まりには ID と短い理由だけを書き、日付と原文は決まりの台帳に残す（`deck-practices/rules.md` の「修正の指示の戻し方」）。報告の最後に、どの指示をどの決まりに戻したかを書く。
- **エージェントのメモリに書いて済ませない。** 資料づくりの決まりは、ここか `rules/` に、顧客ごとの好みは顧客の `memory.md` に、顧客のことは顧客の `profile.md` に書く。エージェントのメモリはほかのエージェントから見えない。

## 調べもの

資料を作らない調査の依頼（「〇〇を調べて」など）は、返事で答えるだけで終わらせず、`Research/<内容>_<YYYYMMDD>.md` に残す（同じことを調べ直さないため）。

- 先に `grep -rln <語> Research/ references_index.md` で前の調査を探す。あれば読み、足りないところだけ調べて同じファイルに足す（末尾の「更新」に日付と変わったこと）。
- 書くこと: 依頼（ユーザーの言葉のまま）、結論（冒頭に数行）、根拠と出典（URL と確かめた日）、確かめたことと推測の区別、未確認のこと。社外秘が入るなら冒頭に【社内】と書く。
- ある資料のための調べものは、`Research/` ではなく、その資料のフォルダ（`references.md`・`社内メモ_*.md`）に書く。資料に使えそうな出典は `references_index.md` にも足す。

## 社外秘と顧客の情報

- 社内の資料には社外秘のもの（Internal Only・Confidential と書かれたもの、ロードマップ、公開されていない顧客事例）が混ざっている。顧客向けに使う前に、公開してよい範囲かを確かめる。
- 社内の打ち合わせで聞いた話（見立て、作戦、社内事情）は、顧客向けの資料に入れず `社内メモ_*.md` に書く。
- **顧客向けの資料（本文とスピーカーノート）に入れないもの:** 個人名、社内の事情や見立て、利用額や割引、社内のチケット・チャット・会議だけにある情報。必要なら `社内メモ_*.md` に書く。
- 顧客向けの資料に付ける出典は公開の URL だけ。顧客との会議は出典の行に書かない。数字の出典は会議を出さずに書き、会議の ID と日付は構成案の出典の表と `references.md` に残す。`references.md` には社内の URL が入るので、納品物に写さない。
- プレビューやベータの機能は、提供ステージを日付とともに書き、公開情報で言える範囲と社内情報を混ぜない。

## 書き方

- 和文と英数字の間に半角スペースを入れる（`2026 年 10 月`、`3 つの問い`）。
- 製品名・機能名は英語の正式名のまま書く。訳語や言い回しは社内の日本語資料と公式のドキュメントの日本語版に合わせる。
- 数字と固有名詞には出典を付ける。口頭で聞いた数字は推測のことがあるので、裏付けてから使う。
- 資料の文体と出典の付け方は `deck-practices/content.md` の 6。

## フォルダの置き方

```
Customers/<顧客>/<内容>_<YYYYMM か YYYYMMDD>/   … 顧客向けの資料。1 本につき 1 フォルダ（中の形と名前の付け方は deck-practices/SKILL.md の 1）
Customers/<顧客>/memory.md                        … その顧客の資料への好み（どう作るか）（deck-practices/rules.md の「顧客の memory」）
Customers/<顧客>/profile.md                       … その顧客の事業・組織・技術の構成・エンジニアの好み（customer-profile）
Internal/<内容>_<YYYYMM か YYYYMMDD>/           … 社内向けの資料（中の形は顧客向けと同じ）
Research/<内容>_<YYYYMMDD>.md                    … 調べもの
Research/deck_research/                           … deck-research の調べ直しの記録（state.md・log/）
rules/<スキル>/<ファイル>                         … このワークスペースの決まり（プラグインの同じファイルへの足しと上書き）
rules/deck-build/checks.py                        … このワークスペースの点検（lint が読み込む）
themes/slides/<名前>.json                         … スライドのテーマ（色・書体・表紙と扉のレイアウト。テンプレートの URL は factory.toml の [slides.templates]）
assets/                                           … 自分だけの画像（ページの JSON の "src": "asset:<名前>" が先に探す）
.factory/                                         … スクリプトが書く記録（lint・dreaming）と、顧客の profile の前の版。手で直さない
factory.toml                                      … 人ごとに変わる設定値（スクリプトが読む）
references_index.md                               … 過去に使った資料の索引
```

- `Customers/` の下は顧客（会社）ごとのフォルダ。下の表にない顧客なら、英字の略称で作る。顧客について社内で話す資料は `Internal/` に置く。
- 作業用の写し（書き出した pptx、ページの画像、確認用の PDF など）は `/tmp` に置き、使い終わったら消す。参考にした資料は写しを置かず、URL を `references.md` に書く。
- **過去に使った資料は、直下の `references_index.md` にまとめる。** 探すときは、検索より先に `grep -n <語> references_index.md`。
- **エージェントが読み書きするファイルの名前は、英数字とハイフン・アンダーバーだけにする。** 納品物と、ユーザーが読む `構成案*.md`・`社内メモ_*.md` は日本語の名前のまま。
- ワークスペースの直下に、上に書いたもののほかのファイルを作らない。
- git で管理するのは、決まりと設定（`AGENTS.md`・`CLAUDE.md`・`factory.toml`・`rules/`・`themes/`・`assets/`）と、調べ直しの記録（`Research/deck_research/`）だけ（`.gitignore`）。資料と台帳は入れない。
