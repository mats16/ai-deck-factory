# Writing pages (JSON)

Open before you write or fix the page JSON (`build/deck.json` and `build/p<number>.json`). Together with [visual.md](visual.md), this is what page writers read.

[slides-pages-001] Do not make pptx for slides; build Google Slides directly with the Slides API. Do not use LibreOffice. Use pptxgenjs only as a relay for inserting local images ([images.md](images.md)). To go back to the pptx method, see the workspace's `Archive/pptx_pipeline_20261007/README.md`. ## Writing pages

New decks write pages in JSON (slides-pages-034). pages.py ("Writing pages.py" below) remains for decks made earlier with pages.py and for pages the JSON components cannot express.

- [slides-pages-034] **Write pages in JSON (`slides/v1`).** The LLM writes only the arrangement and the meaning; the script decides coordinates, frames, corner radii, padding, and text colors. `slides.py` resolves the written form into a form with absolute positions in in and every value filled in (the resolved form), and builds it with the same-named methods of `Deck`. Build requests, lint, and `build` diffs (rebuilding only changed pages) are the same as when writing pages.py. Because it can be read without running code, components and pages can be written one at a time and stopped before building (2026-10-16. The three representative pages and child agents' pages are also written in JSON).

  ```json
  {"apiVersion": "slides/v1", "kind": "page",
   "title": "取り込みは 3 つの段に分ける", "lead": "生のデータを残したまま、使う形へ段ごとに整える", "kicker": "構成",
   "body": [
     {"type": "row", "arrows": true, "items": [
       {"type": "card", "head": "Bronze", "text": "届いたままの形で残す。取り直しの起点になる"},
       {"type": "card", "head": "Silver", "text": "- 型をそろえる\n- 重複を外す\n- 結合できる形にする"},
       {"type": "card", "head": "Gold", "items": [["集計", "画面と報告で使う **集計** を置く"], ["権限", "見せる範囲を決める"]]}]},
     {"type": "text", "text": "段を分けると、***誤りの戻り先***が 1 か所に決まる。手元では `uv run` で回す", "fill": "PANEL"}],

   "source": "[Medallion Architecture](https://docs.databricks.com/aws/en/lakehouse/medallion)"}
  ```

  - **Samples:** A deck that covers every way of writing (all types and keys) is in [samples/json/](samples/json/) (`deck.json` with 14 pages, and `component.json` with one component). When unsure how to write something, open the sample page that uses the same component type, for the syntax only (slides-visual-049 in `visual.md`). selftest checks that the samples use every type and key of the format and that they build without warnings (when you add a key to the format, add it to the samples too).
  - **File header:** Every file starts with `"apiVersion": "slides/v1"` and `"kind"` (modeled on k8s; format versions are in slides-pages-035). `kind` is `deck` (`name` and `pages`), `page` (one page), or `component` (one component; it is placed on an untyped page for checking).
  - **Deck file:** `build/deck.json` (`kind: deck`) holds the material name (`name`. Append `｜Internal Only` for internal materials and `｜Confidential` for confidential ones. The material name is not shown in the footer; only the classification remains at the end of the copyright line) and the page order (`pages`). Write pages one per file as `build/p<outline number>.json` (`kind: page`) (so that fixing child agents can edit files page by page. slides-pages-031). `pages` lists only paths of page files and of other deck files (child agents' `pages_<owner>.json`) (one page per file). If the deck has `theme` (a name from `slides.py themes`), `new` uses it when `--theme` is omitted, `lint` and `dry` check with that theme's file, and `build` stops if it differs from the deck's theme (do not write it in child agents' `pages_<owner>.json`). `new`, `build`, `lint`, and `dry` read `deck.json` in `build/` (they stop if both it and pages.py exist). To call pages from pages.py, use `d.spec("p05.json")` inside `make` (a list of files or a dict can also be passed; dicts passed from Python can omit the header).
  - **Pages:** `type` is `page` (when omitted. `title`, `lead`, `kicker`, `body`, `band`, `source`, `speakerNotes`), `cover` (`title`, `kicker`, `sub`, `variant`, `speakerNotes`), `divider` (`num`, `title`, `sub`, `variant`, `speakerNotes`), or `slide` (an untyped page. `bg`, `foot`, `body`, `source`, `speakerNotes`). `band` is the conclusion band: `"文"` or `{"text": …, "sub": …}`. `source` is the source line (the leading 「出典: 」 is added).
  - **Author notes:** Every page type and the deck file accept `authorNotes`, a list of strings that is built nowhere: not on the slide and not in the speaker notes. Write in it what the makers need to keep but the audience does not see, such as facts moved off the slide, caveats, and the point of the page (`["…", "…"]`). Changing it does not rebuild the page, because it adds no build requests. It does not reach Google Slides, so `deck.md` of `gslides.py check` does not show it; read it in the page files. pages.py decks have no `authorNotes`; write such text in the outline instead.
  - **Arrangement:** `body` places items top to bottom with 0.3 in between (using the body's left edge and width, from a top edge set by whether there is a lead). `stack` places items vertically with 0.24 in between; `row` places them horizontally and matches the height to the tallest item (cards, boxes, labels, code, and filled text stretch). In a `row`, `num`, `icon`, components with `w`, and labels with `"w": "fit"` take their own width, and the rest share the remaining width equally. `"widths": [3, 2]` splits by ratio. `"arrows": true` draws a horizontal arrow at the vertical center between each pair of neighbors (gap 0.6 in). `grid` wraps at `cols` columns and matches heights per row. For columns of the same shape (e.g. three columns each stacking a card and a code box), do not put `stack`s in a `row`; put the items in a `grid` in tier order (`stack` does not stretch, so tier heights do not match. visual.md slides-visual-024). `gap` changes the gaps.
  - **Free-form diagrams:** Only inside a `frame` (which needs `h`), write `x`, `y`, `w` on components (in, from the frame's top-left). Omitting `h` derives it from the content. Use `frame` only for diagrams that `row`, `stack`, and `grid` cannot express (branches, vertically offset boxes, points on an axis). A horizontal flow (A → B → C) is a `row` with `"arrows": true` holding marked cards or `label`s (it uses the full body width, and heights and arrow positions align). Boxes in a `frame` are also placed as `label`s (filled box and text as one shape) or marked cards (`"valign": "middle"` if placing an icon); do not overlay `text` on a filled `box` (it stops when a filled box contains only text; an enclosure holding a heading and cards is allowed). A `frame` laid out as one horizontal row joined by arrows gets a build warning recommending `row`.
  - **Arrows:** Give components an `id` and connect them with `{"type": "arrow", "from": "a", "to": "b"}`. If they are apart horizontally, the arrow is drawn horizontally between the facing sides, at the center of their vertical overlap (slides-visual-025. If they do not overlap, diagonally between the side centers). If they are apart vertically, it is drawn vertically. If both ends are boxes (`card`, `code`, `box`, centered `label` and `stat`, centered `text` with fill or outline; `shape` only rectangle or rounded rectangle), the arrow is connected to the centers of the box sides (it follows when the boxes are moved on screen. slides-component-024). `"route": "bent"` makes an elbow line (horizontal–vertical–horizontal if apart horizontally, vertical–horizontal–vertical if apart vertically. For diagrams that branch from or merge into one box. Only when both ends are connectable boxes. A single flow that neither branches nor merges places the boxes in the same row or column and draws straight lines. visual.md slides-visual-043). For branches, make every branch `bent` (a branch whose center is at the same height is drawn straight without bending. Making only one straight makes it diagonal, and it shows up in the build warnings). To decide the exit and entry sides, write `from` and `to` as `"<id>.<side>"` (side is `top`, `bottom`, `left`, or `right`. `{"from": "k3.right", "to": "he.bottom"}` leaves the right side horizontally and enters the other box's bottom side vertically). Write it on both ends and do not write `route` (only when both ends are connectable boxes). Perpendicular sides bend once (e.g. a line returning from a box in a lower tier to a box in an upper tier); facing sides bend twice (also when joining diagonally separated boxes vertical–horizontal–vertical). The exit side must face the entry point, and the entry side must face the exit point (sides that do not face it, and both ends facing the same direction, stop). Ends at `[x, y]`, and ends pointing at images, icons, or layout containers, are not connected. Arrows take no space and are drawn last on the page. Write the line's name (「① ログインして要求」 etc.) in `"label"`. It is placed as 11pt `SUB` text: top center for horizontal lines, right of the middle for vertical lines, and on the middle segment for bent lines (the exit segment for lines that bend once) (slides-visual-025). `"label_side"` changes the position (`top` or `bottom` for horizontal lines, `right` or `left` for vertical lines; it stops if it does not match the direction of the segment holding the label). Placing a label as positioned `text` makes it float away from the line or overlap it. To draw two lines (there and back) between the same two boxes, give each an `"offset"` (in; for horizontal lines down is positive, for vertical lines right is positive) to shift it up/down (left/right) from the box center (e.g. `-0.2` and `0.2`. If the label of the upper line is `top` and that of the lower line is `bottom`, no label sits between the two lines). Offset lines do not attach to the side-center connection points, so they are drawn from side to side without connecting to the boxes (they do not follow when the boxes are moved on screen). It cannot be written on bent lines, ends with a side, or `[x, y]` ends, and it stops if the offset pushes an end outside the box.
  - [slides-pages-038] **Position checks (build warnings):** On the resolved form, it reports: an arrow line passing over other components (excluding the components at both ends and enclosures containing an end; for unfilled text, only where the text is), arrowhead tips gathering within 0.1 in, components partly overlapping (an enclosure fully containing the other, and components placed on the ring of an ellipse (`shape: ellipse`), are fine), labels of diagonal or bent lines overlapping lines, bordered components inside an enclosure (`box`) closer than 0.08 in to its sides (slides-visual-044), bent lines for a single flow that neither branches nor merges (slides-visual-043; arrows with sides written are not checked), and misaligned tier heights among same-shape `stack`s in a `row` (slides-visual-024; `grid` cannot draw arrows and splits columns equally, so a `row` with `"arrows": true` and a `row` with differing column widths are not checked). `slides.py lint` and `dry` show them before building (2026-10-16. In the first JSON deck of 29 pages, 10 of 13 rebuilds of only 1–2 pages included `frame` pages, and half of the image findings in rounds 2–3 of `/deck-review` were `frame` diagrams. 「3 本の矢じりが同じ点に重なる」, found on images in round 3, shows up in this warning from the moment the page is written). Text heights and the bend positions of bent lines (estimated at the middle) are estimates, so check borderline cases on images. Bring this warning to 0 before building `frame` diagrams (do not build and move positions 0.1 in at a time while looking at images).
  - **Components:** Numbers count from 1. Every component accepts `id`, `w`, `h` (except `icon`, `num`, `arrow`; `row`, `stack`, `grid`, and `list` do not accept `h`. Height comes from the content; only `frame` requires `h`).
    - `text`: `text`, `size`, `color`, `bold` (whole text bold), `fill`, `line`, `dash`, `weight`, `align` [left, center, right], `valign` [top, middle, bottom], `mono`, `spacing` (line spacing %; if omitted, 125 for 2+ lines), `para_gap` (space between paragraphs, pt), `pad` (space between the edge of a filled box and the text, in; if omitted, one character's width), `shape` (shape of the figure: `rectangle`, `round_rectangle`, `ellipse`, `chevron`, `home_plate`, `folded_corner`, `can`. Only shapes used in past materials; add others when they are used. Normally do not write it. If omitted, a filled box is a rounded rectangle with radius 0.1 in and an outline-only box is a rectangle [`visual.md` §4]. Writing `rectangle` on a filled box shows up in the build warnings), `radius` (corner radius, in)
    - `label` (tag): `text`, `size`, `color`, `bold` (bold by default), `fill`, `align`, `mono`, `pad`, `radius`. `"w": "fit"` fits the width to the text (one character's width on each side)
    - `card`: `head`, `text` or `items: [["見出し", "説明"], …]` (an item without a description stops; lists that are not heading–description pairs go in `text` as bullets), `fill` (default `CARD`), `line` (default `RULE` on a `CARD` background, none on other backgrounds. `visual.md` §4, "fill or outline, not both"). `step` (in) places items at fixed intervals (only to align the top edges of items across left and right cards; markup cannot be written in `items`)
      - **Marked cards:** Writing one of `icon` (Iconify name), `num` (number), or `image` (logo etc.; written the same way as `src`) puts the mark on the left and the heading (bold 12pt) and body to its right. `"align": "center"` puts the mark at the top center and centers the text too. The content (mark and text) is placed at the vertical center of the frame. Cards stretched by `row` or `grid` to match their neighbors (and cards made taller with `h`) are top-aligned, so their heading heights match the neighbors'. A mark placed beside the text is always aligned to the first line of the heading (the first line of the body when there is no heading), regardless of how much text there is. Wherever the card is placed (`row`, `grid`, or `frame`), its mark lines up with the neighboring cards' marks. When the content (mark and text) of a card made taller with `h` is at most half the card's height, a build warning recommends `"valign": "middle"` (it looks at height, not line count; it is not shown for cards stretched to match their neighbors, cards with `valign`, or cards with `"align": "center"`; to keep the card top-aligned so its heading lines up with the neighbors', write `"valign": "top"`). `"valign": "middle"` keeps the content vertically centered even when stretched and centers the mark on the text (boxes in architecture diagrams etc.). `"valign": "top"` is always top-aligned. On a `NAVY` background, text and marks are white, and the number circle is red regardless of background (cards with dark backgrounds and no mark are also white text; `step` cannot be used on dark backgrounds). `"shape": "round_rectangle"` makes the number a rounded tag (only cards with `num`; it is not the shape of the card's box). This one component replaces `node`, `icard`, and `ncard`, which past materials made per material (together used on more than 100 pages)
    - `list` (marks and text in a list): `items` is a list of items; each item is text with markup or `{"head": …, "text": …}` (`- ` bullets cannot be written in an item's body). Items without a mark get numbers (red circles) counted in item order from `start` (default 1). Writing `icon` on the list makes it the mark of every item. Writing one of `icon`, `num`, or `image` on an item changes the mark of that item only (mixing numbers and icons still aligns the body's left edge). The mark's center is aligned to the center of the item's first line (the heading line if there is `head`). From the second line, text is indented to the body's left edge, and the mark stays beside the first line. `head` is bold 12pt. `text` written with `head` becomes gray supplementary text (`SUB`); `text` alone is in the body color. `size` (mark size: `small`, `medium` [default], `large`, same as `num`), `shape` (number shape; same as `num`), `digits` (zero-padded digits of integer numbers; `2` gives 01, 02 …), `color` (icon color; default is the body color), `gap` (space between items, in; default 0.16). If you place numbers or icons and text side by side with `row`, `row` aligns the top edges, so the text sits above the mark's center (shows up in the build warnings). Write marks and text as a `list` (sample: `samples/json/list.json`)
    - `stat` (emphasized number): `value` (the large number; `size` default 32pt bold), `unit` (unit; half the size of the number), `label` (what the number is; bold 12pt), `sub` (supplement; `SUB`), `color` (number color; default `RED_TEXT`, `RED_ON_NAVY` on `NAVY` backgrounds), `fill`, `line`, `align`. This is `stat` and `bignum` from past materials. The number and the unit go in the same paragraph (so it does not hit the lint rule 「数字だけの大きな段落」)
    - `code`: `text` lines, `hot` the numbers of lines to make red, `size`
    - `table`: `rows` (list of rows; the top `header` rows are heading rows), `widths` (ratios), `align` (alignment per column: `["left", "center", "center"]`), `valign` (vertical alignment in cells: `top`, `middle` [default], `bottom`), `mono_cols` (column numbers), `header` (number of heading rows; default 1; `true` is 1, `false` is 0), `first_col`, `zebra`, `borders` (rules: `rows` is horizontal rules only [default. `visual.md` §5], `grid` is horizontal, vertical, and outer border, `none` is none), `row_h` (minimum row height in in; may be a list per row), `fills` (`[[row, column, color], …]`; emphasis filling a whole row or column. Rows and columns are counted by their position in `rows`: the heading row is row 1 and the leftmost column is column 1. `"all"` means the whole column or row. `[[3, "all", "RED_SOFT"]]` is all of row 3 counting from the heading row [row 2 of the content])
      - **Cells:** A string (markup allowed; see "Text markup" below) or `{"text": …}`. `{…}` accepts `colspan` and `rowspan` (number of cells merged to the right and down), `fill` (that cell's fill), `color` (text color), `align` and `valign` (that cell's alignment; they win over the column's `align` and the table's `valign`). Merging works as in HTML tables: do not write cells at positions covered by a merged cell (lower rows are written from the left, skipping columns covered by an upper `rowspan`; a row whose columns are all covered is `[]`). The number of columns is the sum of `colspan` in row 1, and it stops if any row does not match. A cell where every paragraph starts with `- ` is a bullet list. Write the fill of a merged cell in that cell's `fill` (it stops if `fills` paints only covered positions; a `fills` that paints a whole row or column becomes, on a merged cell, the fill of its top-left position). If the fill (`fill`, `fills`) is a dark color (`NAVY`, `RED` etc.), the text is white. A light fill on a heading row makes its text the body color. For a two-tier heading in a comparison table, use `"header": 2`, write `{"text": "製品の比べ", "colspan": 2}` in the upper row and `{"text": "観点", "rowspan": 2}` in the left column (sample: `samples/json/table_merge.json`). Use `"borders": "grid"` only when the boundaries of merged cells are hard to see
    - `image` (`src`, `alt`), `icon` (`name`, `size` in, `color`), `num` (`n`; `size` is `small`, `medium`, or `large`; `fill`; `shape` is `ellipse` [default; a perfect circle] or `round_rectangle` [a rounded tag; height is the circle's diameter, width fits the number]. Write zero-padded numbers as `"n": "01"`), `box` (`fill`, `line`, `dash`, `weight`, `shape`, `radius`), `arrow` (`from`, `to`, `color`, `head`, `dash`, `weight`, `route`, `label`, `label_side`, `offset`)
    - `gantt` (schedule; slides-pages-010): `cols` (column names: `["10 月", "11 月", …]`), `rows` (`[{"head": item, "bars": [{"from": 1, "to": 2, "text": "設計", "status": "tbd"}], "marks": [{"at": 3.5, "text": "本番"}], "note": supplement}, …]`), `today` (red vertical line for today). There is one way of counting: column n runs from position n to n + 1. A bar's `from` and `to` are column numbers (from 1, both ends included; `"from": 1, "to": 2` is all of columns 1–2); the time points `today` and `at` are positions (3 is the left edge of column 3, 3.5 is its middle, the number of `cols` + 1 is the right edge). Bars are in column units; a bar starting mid-month cannot be written. The table is a grid (vertical rules between months), and bars are overlaid as 9pt filled tags (slides-visual-037). Bar text is up to 2 lines (about 5 characters per line; break with `\n`). Overlapping bars move to a lower tier in the same row. Do not write bar colors; write the meaning with `status` (modeled on mermaid's `done` and `crit`; the component decides the colors, so meanings match across materials): `plan` (a fixed plan; default; navy), `tbd` (undecided; dotted outline), `done` (finished; light gray), `hot` (cannot be delayed; red text on a light red background; use for 1–2 bars). State which color means what in the lead or in a legend sentence. `marks` are milestones (mermaid's `milestone`): a red diamond at position `at`, with an 11pt one-line phrase to its right (to its left if it would pass the table's right edge). Do not draw one-day events (start, go-live, deadline) as a one-column bar. If a mark or phrase overlaps a bar, it moves to a lower tier. Writing `note` on any row adds a supplement column on the right, and month columns become 1.0 in (if not written, month columns share the body width). Items and supplements cannot contain markup (nor can milestone phrases). Placed last, directly under the body (`body`), it distributes the leftover height to the rows (up to 0.4 in per row; it does not stretch inside `row` or `stack`). `h` cannot be written. This is `gantt` from past materials
    - `bars` (single-series bar chart; `visual.md` §5): `items` (`[["2024", 180], …]`; values 0 or more), `unit` (unit after the number), `horizontal` (horizontal bars: long names, rankings. Default is vertical bars, for time sequences), `hot` (number of the bar to emphasize: red bar and red number; only one bar). No legend or tick marks; the number is written at the end of each bar and one baseline is drawn. Vertical bar height defaults to 2.6 in (change with `h`); horizontal bars are 0.42 in each. Bars are `NAVY`, and the color cannot be changed (add 2+ series when needed). A `line` and a straight `threshold` can be overlaid on the bars (both can be written together. The threshold always uses the bars' scale; a reference line on the line's scale [a target rate etc.] cannot be drawn)
      - `line` (vertical bars only): `{"values": [6.5, 8, 10.5, 13], "unit": "%", "label": "利益率"}`. `values` is one number per bar, in the same order and count as `items` (modeled on mermaid xychart's `line [..]`; names come from `items`). Use it for numbers with a different unit from the bars, such as rates and cumulative totals. In a 0.8 in band above the bars, it draws a gray (`SUB`) line and points on a separate scale from the bars, and writes the number above each point. `label` (what the number is) is one line at the top-left of the band. The band is low, so the scale does not start at 0: the smallest number is at the bottom of the band and the largest at the top (numbers are written at the points). Height defaults to 3.4 in (3.7 in with `label`), and the bar band is the same as without `line`
      - `threshold`: `{"value": 90, "label": "目標"}`. One number compared on the same scale as the bars, such as a target, limit, or average. It draws a red dotted line and places a tag (「目標 90 分」; unit from `unit`) outside to the right of the line for vertical bars and above the line for horizontal bars. If the number exceeds the bars, the line spans the full height. When the line passes through the number at a bar's end, that number is put inside the bar in white (outside the line, it would look like a number beyond the line. If the bar is too low or thin to hold it, it is a build warning. lint does not count shapes whose alt-text title is `ai-deck-factory bar` [bars; the description is the name and number] in the space below boxes). There is no component for comparison numbers that differ per bar (plans per year etc.)

Pages are referenced by file name, so reordering does not break it), `<br>` (line break inside a paragraph; JSON cannot write `\v`), `\n` (paragraph). Bold, red, and size can contain other formatting and links (`**{32:48}** モデル`). Starting every paragraph with `- ` makes a bullet list (blank lines between bullets are dropped; for space between them use `para_gap`. Mixing bullet paragraphs and plain paragraphs in one `text` stops; bullets apply to every paragraph in the frame, so split them into separate `text`s). `` `code` `` drops the `` ` `` and sets the text in the body font (command names in running text are not monospaced; slides-visual-014. Monospace is for `code`, `text` and `label` with `mono`, and table `mono_cols`). Write literal symbols as `\\*` or `\\{` (two `\` because it is a JSON string). Markup also works in table cells (not in Gantt items and supplements).
  - **Colors:** Role names only (`NAVY`, `PANEL`, `RED_TEXT` etc.; the list is the colors in `slides.py schema`). 6-digit hex cannot be written (the theme file decides the values, so every color pair can be measured with the theme's colors. A color that is truly needed can be written in `raw`, and lint reports it as `要確認`). Text color follows the fill (white on `NAVY`; unfilled text follows the `bg` of a `slide` if it is dark), so write it only when you want to change it.
  - **Images:** `src` is a URL, a path relative to the JSON file (`"img/a.png"`), or `"asset:gcp/bigquery.png"` (`asset()`). Local images are uploaded at build time (carry in [images.md](images.md)). SVG URLs are converted to PNG. Local PNG, JPEG, GIF, and SVG get their height from the aspect ratio; URL images need `h`.
  - **Commands:** `slides.py lint p05.json <URL>` and `dry` (same as for other files; page links are checked when the parent builds. By default `lint` checks only pages changed since the last run, so use `--all` to see all findings), `slides.py resolve p05.json [<URL>]` (prints the resolved form; use it to check what was placed where), `slides.py schema` (JSON Schema of the format; pass it to structured outputs or an editor), `slides.py stats` and `upgrade` (slides-pages-035).
  - **What stops:** not readable as JSON; missing or unreadable header `apiVersion` or `kind`; unknown `type`, key, color, or shape; missing required key; wrong type; duplicate or missing `id`; `x` or `y` outside a frame; table rows that do not match the column count (miscounted `colspan` or `rowspan`); `fills` on a row or column not in the table; missing image; no `h` on an image of unknown aspect ratio; an argument in `raw` that the method does not have; numbers out of range (size, weight, line spacing, and `h` greater than 0; gaps and positions 0 or more; `cols` and `variant` 1 or more); components and arrow ends outside a `frame`; bullet paragraphs mixed with plain paragraphs; text alone overlaid inside a filled box. Each stops with its location, like `p05.json.body[0].items[2]（card）: …`. A missing link-target page and the same page listed twice also stop. The body likely overlapping the conclusion band or the source line shows up in the build warnings. Text or marks of a `card`, `stat`, `label`, or filled or outlined `text` with `h` that likely do not fit that height also show up in the build warnings (the visual top/bottom padding and the 0.4 in default of `label` may be tightened, e.g. a one-line vertically centered card at 0.6 in).
  - **lint locations:** When a `slides.py lint` finding quotes text, the component's location (`（p05.json.body[1]）`) is appended (not on `gslides.py check` findings).
  - **lint units:** `slides.py lint` chooses rules by the unit of the file passed. `deck.json` and pages.py are the whole deck (all rules). Page files (`kind: page`) and child agents' `pages_<owner>.json` and `.py` are pages: rules decided by looking at the whole deck (whether page 1 is the cover, section dividers, the number of conclusion bands, the number of assertive headings, the confidentiality notice) are not reported. A one-component file (`kind: component`) is a component: page rules (headings, sources, empty space at the bottom and middle of the page, character counts) are also not reported, only rules inside the component (text size, font, contrast, box padding, wrapping, wording etc.).
  - **Pages the JSON components cannot express:** Free-form diagrams can be built by placing `box`, `text`, `label`, `arrow`, and `image` by position inside a `frame`. A deck that needs components that even writing outside the format (`raw` in slides-pages-035) cannot express does not have `deck.json`; it has pages.py, where `make` calls the JSON pages in order with `d.spec` and only those pages are written as functions (write `NAME` in pages.py; "Writing pages.py" below). If a second material needs it, add it to the JSON components (same as slides-legacy-004; `factory-kaizen`).
- [slides-pages-035] **Format versions, and writing outside the format.** The format grows by watching how it is used (2026-10-16).
  - **Version:** `apiVersion` at the head of the file (now `slides/v1`). Raise it only when the meaning of a key changes (renaming or removing it, changing default behavior). Do not raise it when adding keys, types, or markup (old files still read as they are; old plugins stop on new keys as 「知らないキー」 and recommend an update). After raising it, rewrite files of the previous version with `slides.py upgrade`; builds also read previous-version files by rewriting them. The version is a promise about the meaning of keys, not about appearance (changing default values of the arrangement does not raise it; pages whose appearance changed are rebuilt through the page hash). The resolved form (`resolve`) has no version (it is made on the spot and not saved).
  - **Writing outside the format:** For anything the format's keys cannot express, write `"raw": {…}` on the component (not allowed on layout containers [`row`, `stack`, `grid`, `frame`]. These are arguments of the same `Deck` method: the table above and the docstrings in `slides.py`. `{"zebra": false}` etc.). Check the argument names before building. They are reported as lint `要確認` (「JSON の形の外の書き方」), and if a format key can express it, that key is suggested. There is no way to write raw Slides API requests (they cannot be read statically, and their order has meaning). Anything `raw` cannot express goes in pages.py ("Pages the JSON components cannot express" in slides-pages-034).
  - **Growing it:** Each time `build` builds a deck of JSON pages, it records the `raw` keys used and their counts in the workspace's `.factory/spec_raw.jsonl` (it records even when there is no `raw`, so removed keys drop out of the count. Material text is not recorded. Materials with tmp in the name are not counted). `slides.py stats` prints the number of materials that used each key. Keys used in two or more materials become proposals to add to the format (from dreaming §5 to `factory-kaizen`). When the owner adds one to the format, add "raw argument → format key" to `SPEC_PROMOTED` in `slides.py`, and rewrite `raw` in earlier materials with `slides.py upgrade <file>…` (values are converted to the format's notation: `"CENTER"` to `"center"`, `"DARK1"` to `"NAVY"`. Values that cannot be converted stay in `raw`. Rewritten files have their JSON reformatted).
- [slides-pages-031] **Writing pages in separate files (when child agents write them. step 7 in [workflow.md](workflow.md), slides-flow-016).** A child agent writes its pages in JSON (slides-pages-034), one page per file as `build/p<outline number>.json`, and places `build/pages_<owner>.json` listing them in outline order (`{"apiVersion": "slides/v1", "kind": "deck", "name": "<owner>", "pages": ["p06.json", …]}`). It does not rewrite other files (`deck.json`, the three representative pages, other owners' pages). The child does not build; it checks with `slides.py lint pages_<owner>.json <URL>` (`[p<number>]` is the position within the owner's pages. `dry` skips lint and only shows whether it stops and the build warnings). The URL is the deck where the three representative pages were built; like `build`, it reads the cover and section-divider patterns (`variant`) and the theme from there (read only. If not passed, only pattern 1 exists, and 2 or higher stops). Images, page links, and lint across pages (section dividers, the number of conclusion bands etc.) are checked by `gslides.py check` after the parent builds. The parent lists the child agents' page files in `deck.json` `pages` in outline order and builds once (if an owner's pages are consecutive, one `pages_<owner>.json` may be listed). One page per file is so that `/deck-review`'s fixing child agents can edit files page by page (`../deck-review/prompt_fix.md`).

  ```json
  {"apiVersion": "slides/v1", "kind": "deck", "name": "〇〇様_ご説明資料", "pages": [
    "p01.json",
    "pages_a.json",
    "p05.json", "p06.json", "p07.json"]}
  ```

  (p1 is the cover, p2–p4 are child A's, and p5–p7 mix the parent and child B, so they are listed one by one.) For pages.py materials, what a child wrote in a pages.py-style file (`build/pages_<owner>.py`: page functions and `make(d)`, with `from pages import …`) can still be checked with `lint` and `dry` as before. Import it inside pages.py's `make` (importing at the top makes the child's file import pages.py back, and it stops).

## Laying out shapes and text

Do not align positions by computing coordinates; align with the features of shapes and text frames (`align`, `valign`). This holds up better when text grows, and is easier to fix on screen.

- **Make a shape and the text inside it one object.** Numbers, tags, and words inside arrows are `d.text(…, fill=RED, color=ON_RED, align="CENTER", valign="MIDDLE")`. `finish` groups the rounded background and the text into one editable group. A perfect circle is `kind="ELLIPSE"`. Unfilled text is a transparent rectangle as before.
  - [slides-pages-008] **Build circular numbers with `d.num` and choose the size from small, medium, and large** (circle size and text size have a balance, so do not decide diameter and text size per material. Samples are on the template's component pages). `d.num` uses `d.text(…, kind="ELLIPSE")`. Google places text in a circle a further 0.1 in inside the inscribed rectangle, so in 0.3–0.36 in circles the text area is narrower than a 14pt digit and the digit shifts to the upper right (0.3 in: 3.5 pt right, 2 pt up; 0.36 in: 1.5 pt right. 「10」 wraps to 2 lines). Changing the font does not fix it (with 7 fonts it shifted right by 1.2–2.7 pt). `d.text` makes the circle fill only, overlays a transparent frame the same size as the circle, and groups them (shift within 0.6 pt). In a rectangular frame, even if the text area (the frame minus inner padding) is narrower than the digits, the overflow is spread evenly up/down and left/right and the text is centered. However, 2+ characters wrap if the width is too small (「10」 wraps at a 0.20 in text area and fits on 1 line at 0.22 in). A frame exactly at the estimated digit width wrapped when the font changed character widths slightly (「10」 in a medium circle; #51). So regardless of character count, the width is widened to the larger of the circle and the digit width, plus 0.05 in on each side (no branch that widens only for 2+ characters). The frame is wider than the circle, so do not connect arrows to numbers. Line spacing is 100%. At first the frame was larger than the circle by only the padding (0.1 in), but the frame was too large when selected (the current 1-character frame is 0.1 in wider than the circle). Do not place a circle with `d.box` or `_shape` and put text in it. Rounded-rectangle numbers (`shape="round_rectangle"`) for the same reason overlay, on a rounded background (`d.box`), a transparent frame widened the same way as for circles (`wide` of `d.text`).
- **When a large frame holds several blocks of text, separate frames are fine.** Cards with heading and body are `d.card` (it overlays a slightly smaller text frame on the box. The inner padding of a text frame is 0.1 in and cannot be changed, so the space between frame and text is made here). Use `body` to put the body in one frame, or `items` to list (heading, description) items at even intervals. For complex frames holding numbers, labels, and so on, place the frame with `d.box` and put text frames `PAD` (0.08 in) inside it. [slides-pages-028] Decide the height of `d.card` from its content by passing `None` as `h` (`card_h` estimates the line count, moving alphanumeric words to the next line without splitting them across lines). Do not stretch it to match the neighboring column or the page bottom (in the records of the three representative pages, boxes larger than their content appeared in almost every deck). To align column heights, pass the maximum `card_h(w, head, body=…)` of the cards in the row. For cards mixing text of different sizes (large numbers) and for `d.box`, the caller decides the height. The inner text frame is not clipped when it overflows the box and is drawn as is, so when you add items or lines, also fix the box height (`step` in `items` uses the same interval for every item, so it overflows easily when an item with many lines comes last). Check the space between the last line and the bottom edge with 「要確認（画像で測った）」 of `gslides.py check` (`visual.md` §4. 2026-10-09).
- [slides-pages-009] **Build the grid of gridded diagrams (Gantt, comparison tables, matrices) as a table (`d.table`).** Do not assemble rectangles and lines. Only things hard to express in a table (bars across months, the today line, labels) are placed as shapes on top of the table. With a table, whoever opens it can easily add rows and edit wording (lint reports `要確認` when there are 3 or more vertical lines with the same top edge and length). Table rows grow to fit the text (`row_h` is the minimum height). For tables with shapes on top, keep cell text to one line and check positions on images.
  - [slides-pages-010] A customer's regular-meeting schedule (one Gantt page) is written with JSON `gantt` ("Components" above) (the component enforces the numbers below). Body text is 11pt, one month column is 1.0 in, and bar text is 9pt (slides-visual-037. A bar is one shape of fill and text. For bars with tags too, overlaying a separate text frame on a filled rectangle makes lint report `要修正` for text under 11pt); words are up to 5 characters per line and 2 lines, with line breaks set by `\n`. Leftover height below the table (the table's bottom edge goes down to above the footer) is distributed equally to the rows (only as much as keeps rows from looking stretched: about 0.4 in for 11pt body text), and bars are placed at the vertical center of their rows. If only the top is packed and the bottom is empty, the page's visual weight shifts upward. For the next meeting, recreate it in a new folder (workspace `AGENTS.md` 「フォルダの置き方」) with page JSON, and get a new URL with `slides.py new`.
  - `vlines` of `d.table` (`(first column, number of columns)`) draws vertical rules in those columns below the heading row (`gantt` uses it for month boundaries). Rule shading (light between months, dark at item boundaries) is not supported. When needed, add a component (set `tableRange` of `updateTableBorderProperties` to the cell range).
- **Charts:** a single-series bar chart is written with JSON `bars` ("Components" above; drawn with shapes, so lint applies). Lines overlaid on bars (numbers with a different unit) and straight lines (targets, limits) can be written with `line` and `threshold` of `bars`. Bars with 2+ series, lines without bars, and charts whose numbers should be editable in Sheets (`createSheetsChart`) have no component, so add one to slides.py the first time it is needed (when past materials were counted on 2026-10-16, pages with boxes sized by values were 29 of 1,780, all single-series bars). Rules for legends, tick marks, and colors are in `visual.md` §5.
- **Align `y`, `h`, and `valign` for text placed side by side.** Cards placed side by side, numbers and headings, labels and body text, and so on get the same frame top edge and height, and the same `valign`. Things placed one line each (numbers and headings etc.) are centered with `MIDDLE`. Cards with different amounts of text use `TOP` so the heading heights match.
- **Put text stacked vertically in one text frame, separated by line breaks.** For things stacked top and bottom, such as heading and body or label and supplement, list `("見出し\n", {"bold": True})` and the body in `parts`. Do not make separate frames with shifted `y`.
- **Make the source line runs with a link per name.** Like `("Mandiant M-Trends 2026", {"link": url})`, attach links to the names of blogs, talks, and docs, and keep connecting 「、」 and parentheses as plain strings. Link to the Appendix source page with `{"link": <page number>}`. Use the same URLs in the source line and in the Appendix list (in pages.py, put them in one place at the top). In JSON, write `[name](URL)` and `[name](#p12)`. lint reports source lines without links as `要確認` (2026-10-06).
- [slides-pages-011] **To align a text's left edge with the edge of another element, use `d.text(…, edge=True)`** (moves the frame outward by `INSET` (0.1 in); `page`, `source`, and `cover` already do this). Do not put a function in pages.py that moves frames outward (the old `t()`) (so that each material does not carry the same function).
- [slides-pages-012] **For text left- or right-aligned in a filled box, passing the fill to `d.text` or `d.label` makes the space between the box edge and the text one character wide** (`visual.md` §4). The inner padding of a text frame is 0.1 in and cannot be changed, and even at 11pt it is less than one character, so the text frame is shrunk inward and grouped with the shape. When overlaying text on a `d.box`, keep the text edge at least one character away from the box edge. lint reports as `要確認` text whose space from the filled box's edge is narrower than one character (the smallest text size in that frame).
- [slides-pages-013] **When putting a large number and its description in one frame, do not adjust line spacing to match the number.** `d.text` sets 100% line spacing only for paragraphs at 2× the base (`size`) or larger (with 125% left as is, Google's line advance is wider than pptx, and the number and description looked apart).
