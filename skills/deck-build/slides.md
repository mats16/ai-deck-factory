## 1. Commands

```sh
K=<deck-build folder>/scripts   # the folder holding deck-build's SKILL.md. From other skills, that skill's folder + ../deck-build/scripts
cd <folder>/build
python3 $K/slides.py new <Drive folder URL> <YYYYMMDD_name> [--theme <theme>]   # first build. Write the printed URL into the outline and tell the user right away (SKILL.md deck-build-003)
python3 $K/slides.py lint [pages_<owner>.py | <page>.json] [<URL>] [--pages 3,5 | --all] [--talk]   # after every edit. Turns the build requests into JSON locally without building, and lints them (unit. SKILL.md deck-build-005. Does not read Google. §3 below)
python3 $K/slides.py lint <workspace>/themes/slides/<name>.json   # checks only the theme file (format, fonts, contrast of role pairs. slides-036 in §3 below)
python3 $K/slides.py plan <URL> [<page>.json …]   # prints what build will write (writes nothing. slides-037 below)
python3 $K/slides.py build <URL> [<page>.json …] [--force]   # at checkpoints. Rebuilds, in the same URL, only pages whose content changed (pass files to rebuild only those pages. Stops if the deck was edited on screen. Below)
python3 $K/slides.py dry [pages_<owner>.py | <page>.json] [<URL>]  # runs make without building; prints build warnings, page count, and pages without notes (default is deck.json or pages.py. slides-031 in §2 below)
python3 $K/slides.py resolve <page>.json [<URL>]   # prints the resolved form of a JSON page (positions in in, and every value) (slides-034)
python3 $K/slides.py schema [--brief]   # JSON Schema of the JSON page format (--brief is a quick reference of types and keys; read this when writing pages)
python3 $K/slides.py stats    # prints, per key, the number of materials that used writing outside the JSON page format (raw) (slides-035)
python3 $K/slides.py upgrade <file>…   # rewrites raw entries that the format's keys can express (slides-035)
python3 $K/slides.py themes   # theme names, descriptions, whether a template exists, which is the default (§3 below)
python3 $K/slides.py theme <URL> [<name>] [--force]   # writes the theme held by a template or deck to themes/slides/<name>.json (§3 below)
python3 $K/gslides.py check <URL> [--talk]          # after building. lint, text, images of changed pages (/tmp/slides_<first 8 chars of ID>/), box bottom margins measured on images, changed.json (e2e)
python3 $K/gslides.py check <URL> --all             # re-fetches images of all pages (once per checkpoint: before /deck-review, or when looking across pages)
python3 $K/gslides.py check <URL> --pages 3,5       # re-fetches images of those pages only (if the page count changed, all pages automatically)
uv run -q $K/sheet.py /tmp/<name>.png /tmp/slides_<ID>/p-0{2,3,4}.png   # tiles several pages into one image
python3 $K/slides.py merge fix_a.py fix_b.py          # for pages.py materials: merges page functions that child agents wrote in separate files into pages.py (does not build. Below)
```

- The location (Drive folder) and name are in `SKILL.md` "Placing files on Drive". Do not create pptx locally.
- Temporary decks for building or trying components separately get `tmp` in their name (`gslides.py check` does not count them in the lint log. Move them to the trash after checking).
- [slides-002] **Rebuilding erases edits made in the Google Slides UI, and comments lose their anchors.** Fix the page JSON (pages.py for older materials) and the outline. `build` stops if the deck was edited on screen after the last build (it saves the last ID of the Drive revision list at build time in appProperties and compares; comments, replies, and resolving do not advance it) or if there are unresolved comments. When it stops, put the edits and the responses to comments into the page JSON (pages.py), then rebuild with `--force` (`../deck-practices/SKILL.md` "Working practices": fix the page JSON (doc.md for documents) and the outline). Materials built before 2026-10-19 saved the revision in a different form, so the next build stops once. Check Drive `revisions` to confirm there were no edits after the last build time, then use `--force`.
- [slides-029] **For pages.py materials, `merge` replaces functions in pages.py with the same-named functions a child agent wrote in `build/fix_<owner>.py`** (functions not in pages.py are added before `make`). Child agents do not write pages.py; they write a separate file, and the parent merges and builds once (`../deck-review/SKILL.md` deck-review-011). Only functions are merged; imports come from pages.py (the parent adds names the child used that are not imported). It stops on `make`, constants, or the same function in both files (the parent writes shared code and the page order). The previous pages.py is kept as `pages.py.bak` (if that exists, it is not overwritten: `pages.py.bak1` …). It warns if `make` does not call an added function. Before building, check that the function names in the printed JSON match the owners passed.
- [slides-033] **`build` rebuilds only pages whose content changed.** It appends a hash of the page's request content to the end of the page ID, and if the deck has a page with the same hash, it keeps that page and only reorders (the same for added, removed, reordered, or duplicate pages). The hash does not cover the notes: when only the notes changed, it keeps the page and rewrites its notes (so a script written after building rebuilds no page; deck-practices-021). Pages built before 2026-10-23 have the notes in the hash: they are kept while their notes stay the same, and a page whose notes changed is rebuilt once. The hash covers the contents of local images, whether the page is the cover (page 1 has its page number removed), and the hashes of linked pages. A page with a link to another page is rebuilt together when the link target is rebuilt (in pages.py decks, also when two or more pages have the same content; JSON pages are told apart by their file names). A deck built by an older `build` rebuilds all pages once, the first time. `--force` rebuilds all pages. Rebuilt pages are written to `/tmp/slides_<first 8 chars of ID>/changed.json`, and `check` fetches only their images. The master's theme is also aligned (slides-036 in §3), so both full and partial rebuilds are decided by the hash of the final requests.
- [slides-037] **Look with `plan` before building. You can build selected pages.** Before building, see which pages will be rebuilt or deleted and whether there are on-screen edits or comments, to prevent unexpected rebuilds and erasing on-screen edits. `plan <URL> [<file>…]` prints as JSON what `build` will write (master theme differences `theme`; pages to rebuild or create `rebuild`; pages whose content changed but are kept as before because they were not selected `frozen`; the number of kept pages; the number of pages to delete; the number of reorders; on-screen edits and comments `screen` [if any, `build` stops]) and writes nothing to Google. `build <URL> <file>…` rebuilds only the JSON pages passed (all pages for a deck file) and keeps the previously built slides for the other pages (so that only finished pages are published while other pages are half-written). Previous slides are found by a mark of the page file name put in the page ID. Unselected pages are still created if they link to a page being rebuilt or were never built. The theme belongs to the whole deck, so it is aligned when different even if not passed; passing only the theme file writes only the master. As a theme file, only the deck's own theme file can be passed. `--force` rebuilds only the passed pages (and also skips the on-screen-edit check). For pages kept as before, the links in their previous content in the deck are checked, and they are rebuilt if they point to pages being rebuilt or deleted. The `raw` count (slides-035) is recorded only on full builds. pages.py decks cannot select pages. Pages built by `build` before this change have no mark, so they are rebuilt if their content changed even when not selected (one full build adds the marks).
- When fixing only 1 page of a 53-page deck, `build` went from 23 → 8 s and `check` from 23 → 8 s (median. With the old version, a `check` run that hit 429 waits took 67 s. Rebuilding/fetching all pages still takes 21 s / 20 s. 2026-10-15). `slides.py lint` takes 2–7 s. `build` and `check` print per-step seconds on one line to stderr.
- **Build warnings** are printed to stderr by `lint`, `dry`, and `build`, with the count on the last line (child agents writing pages also check them with `lint` on their own files). They are pre-build estimates, so check the images before deciding to fix or keep. All warnings are listed below (the rule is in the parentheses of each row).
  | Warning | How to fix |
  |---|---|
  | A manually broken line likely does not fit the frame | Rephrase, or move the line break |
  | The last line of auto-wrapped text likely has 2 characters or fewer | Rephrase, or fix the lines with `\v` (visual-013) |
  | The title was shrunk, or the lead likely runs to 2 lines | Shorten the title and the lead (`content.md` §4) |
  | A table cell likely wraps | Rephrase, or change the column widths (`widths`) |
  | The content of a component with `h` likely does not fit that height | Remove `h` (height comes from the content), or shorten the text |
  | The body likely overlaps the conclusion band or the source line | Reduce the content, or split the page (deck-practices-010) |
  | A filled box was made square (`shape: rectangle`) | Remove `shape` unless there is a reason (`visual.md` §4) |
  | A diagram laid out in one horizontal row and joined by arrows | Write it with `"arrows": true` on a `row` (slides-038 below) |
  | An arrow becomes diagonal, a line passes over a component, a label of a diagonal or bent line overlaps a line, arrowheads gather at one point | Change the arrow ends, sides, `route`, or `label_side`, or align the box heights (slides-038) |
  | Components partly overlap | Separate them, or put one fully inside the other (slides-038) |
  | Text of a Gantt bar is 3 lines or more; a bar chart's name or number wraps | Shorten it, split it with `\n`, or use horizontal bars |
- slides.py runs on plain `python3` (standard library). Only when inserting local images and icons by react-icons name (`Tb…`) does it use global node (pptxgenjs, react-icons, sharp) (§6. Not needed for URL images and Iconify icons).
- [slides-003] Plain `python3` has no Pillow, python-pptx, or markitdown, and there is no ImageMagick. Run anything that needs libraries with uv, and put tools in `scripts/` (like `sheet.py`). Crop images with `sips -c <height> <width> --cropOffset <top> <left> <input> --out <output>` (px).
- Script roles: `slides.py` (components and assembly; page area and color definitions are here too), `template.py` (rebuilding templates), `gslides.py` (checks and reuse), `lint.py` (counting rules), `box_pad.py` (measures on images the space between a box's bottom edge and its text, and the space above and below top-aligned text in light panels; it needs Pillow, so it runs with uv and is called by `gslides.py check`), `gapi.py` (Google API calls: auth, 429 retries, error bodies, uploads). When changing how the API is called, change only `gapi.py`. Per-person values (template URLs and locations, default theme, quota project) are not written in code; they go in `factory.toml` directly under the workspace (the folder above the material folders, e.g. `~/Documents`) (read by `gapi.factory()`. §3).

## 2. Writing pages

New decks write pages in JSON (slides-034). pages.py ("Writing pages.py" below) remains for decks made earlier with pages.py and for pages the JSON components cannot express.

- [slides-034] **Write pages in JSON (`slides/v1`).** The LLM writes only the arrangement and the meaning; the script decides coordinates, frames, corner radii, padding, and text colors. `slides.py` resolves the written form into a form with absolute positions in in and every value filled in (the resolved form), and builds it with the same-named methods of `Deck`. Build requests, lint, and `build` diffs (rebuilding only changed pages) are the same as when writing pages.py. Because it can be read without running code, components and pages can be written one at a time and stopped before building (2026-10-16. The three representative pages and child agents' pages are also written in JSON).

  ```json
  {"apiVersion": "slides/v1", "kind": "page",
   "title": "取り込みは 3 つの段に分ける", "lead": "生のデータを残したまま、使う形へ段ごとに整える", "kicker": "構成",
   "body": [
     {"type": "row", "arrows": true, "items": [
       {"type": "card", "head": "Bronze", "text": "届いたままの形で残す。取り直しの起点になる"},
       {"type": "card", "head": "Silver", "text": "- 型をそろえる\n- 重複を外す\n- 結合できる形にする"},
       {"type": "card", "head": "Gold", "items": [["集計", "画面と報告で使う **集計** を置く"], ["権限", "見せる範囲を決める"]]}]},
     {"type": "text", "text": "段を分けると、***誤りの戻り先***が 1 か所に決まる。手元では `uv run` で回す", "fill": "PANEL"}],
   "band": {"text": "生のデータを残すことが、取り直しを安くする", "sub": "段ごとに責任を分ける"},
   "source": "[Medallion Architecture](https://docs.databricks.com/aws/en/lakehouse/medallion)",
   "speakerNotes": "左から順に、データが整っていく流れを話す。"}
  ```

  - **Samples:** A deck that covers every way of writing (all types and keys) is in [samples/json/](samples/json/) (`deck.json` with 14 pages, and `component.json` with one component). When unsure how to write something, open the sample page of the same type. selftest checks that the samples use every type and key of the format and that they build without warnings (when you add a key to the format, add it to the samples too).
  - **File header:** Every file starts with `"apiVersion": "slides/v1"` and `"kind"` (modeled on k8s; format versions are in slides-035). `kind` is `deck` (`name` and `pages`), `page` (one page), or `component` (one component; it is placed on an untyped page for checking).
  - **Deck file:** `build/deck.json` (`kind: deck`) holds the material name (`name`. Append `｜Internal Only` for internal materials and `｜Confidential` for confidential ones. The material name is not shown in the footer; only the classification remains at the end of the copyright line) and the page order (`pages`). Write pages one per file as `build/p<outline number>.json` (`kind: page`) (so that fixing child agents can edit files page by page. slides-031). `pages` lists only paths of page files and of other deck files (child agents' `pages_<owner>.json`) (one page per file). If the deck has `theme` (a name from `slides.py themes`), `new` uses it when `--theme` is omitted, `lint` and `dry` check with that theme's file, and `build` stops if it differs from the deck's theme (do not write it in child agents' `pages_<owner>.json`). `new`, `build`, `lint`, and `dry` read `deck.json` in `build/` (they stop if both it and pages.py exist). To call pages from pages.py, use `d.spec("p05.json")` inside `make` (a list of files or a dict can also be passed; dicts passed from Python can omit the header).
  - **Pages:** `type` is `page` (when omitted. `title`, `lead`, `kicker`, `body`, `band`, `source`, `speakerNotes`), `cover` (`title`, `kicker`, `sub`, `variant`, `speakerNotes`), `divider` (`num`, `title`, `sub`, `variant`, `speakerNotes`), or `slide` (an untyped page. `bg`, `foot`, `body`, `source`, `speakerNotes`). `band` is the conclusion band: `"文"` or `{"text": …, "sub": …}`. `source` is the source line (the leading 「出典: 」 is added).
  - **Arrangement:** `body` places items top to bottom with 0.3 in between (using the body's left edge and width, from a top edge set by whether there is a lead). `stack` places items vertically with 0.24 in between; `row` places them horizontally and matches the height to the tallest item (cards, boxes, labels, code, and filled text stretch). In a `row`, `num`, `icon`, components with `w`, and labels with `"w": "fit"` take their own width, and the rest share the remaining width equally. `"widths": [3, 2]` splits by ratio. `"arrows": true` draws a horizontal arrow at the vertical center between each pair of neighbors (gap 0.6 in). `grid` wraps at `cols` columns and matches heights per row. For columns of the same shape (e.g. three columns each stacking a card and a code box), do not put `stack`s in a `row`; put the items in a `grid` in tier order (`stack` does not stretch, so tier heights do not match. visual.md visual-024). `gap` changes the gaps.
  - **Free-form diagrams:** Only inside a `frame` (which needs `h`), write `x`, `y`, `w` on components (in, from the frame's top-left). Omitting `h` derives it from the content. Use `frame` only for diagrams that `row`, `stack`, and `grid` cannot express (branches, vertically offset boxes, points on an axis). A horizontal flow (A → B → C) is a `row` with `"arrows": true` holding marked cards or `label`s (it uses the full body width, and heights and arrow positions align). Boxes in a `frame` are also placed as `label`s (filled box and text as one shape) or marked cards (`"valign": "middle"` if placing an icon); do not overlay `text` on a filled `box` (it stops when a filled box contains only text; an enclosure holding a heading and cards is allowed). A `frame` laid out as one horizontal row joined by arrows gets a build warning recommending `row`.
  - **Arrows:** Give components an `id` and connect them with `{"type": "arrow", "from": "a", "to": "b"}`. If they are apart horizontally, the arrow is drawn horizontally between the facing sides, at the center of their vertical overlap (visual-025. If they do not overlap, diagonally between the side centers). If they are apart vertically, it is drawn vertically. If both ends are boxes (`card`, `code`, `box`, centered `label` and `stat`, centered `text` with fill or outline; `shape` only rectangle or rounded rectangle), the arrow is connected to the centers of the box sides (it follows when the boxes are moved on screen. slides_py-024). `"route": "bent"` makes an elbow line (horizontal–vertical–horizontal if apart horizontally, vertical–horizontal–vertical if apart vertically. For diagrams that branch from or merge into one box. Only when both ends are connectable boxes. A single flow that neither branches nor merges places the boxes in the same row or column and draws straight lines. visual.md visual-043). For branches, make every branch `bent` (a branch whose center is at the same height is drawn straight without bending. Making only one straight makes it diagonal, and it shows up in the build warnings). To decide the exit and entry sides, write `from` and `to` as `"<id>.<side>"` (side is `top`, `bottom`, `left`, or `right`. `{"from": "k3.right", "to": "he.bottom"}` leaves the right side horizontally and enters the other box's bottom side vertically). Write it on both ends and do not write `route` (only when both ends are connectable boxes). Perpendicular sides bend once (e.g. a line returning from a box in a lower tier to a box in an upper tier); facing sides bend twice (also when joining diagonally separated boxes vertical–horizontal–vertical). The exit side must face the entry point, and the entry side must face the exit point (sides that do not face it, and both ends facing the same direction, stop). Ends at `[x, y]`, and ends pointing at images, icons, or layout containers, are not connected. Arrows take no space and are drawn last on the page. Write the line's name (「① ログインして要求」 etc.) in `"label"`. It is placed as 11pt `SUB` text: top center for horizontal lines, right of the middle for vertical lines, and on the middle segment for bent lines (the exit segment for lines that bend once) (visual-025). `"label_side"` changes the position (`top` or `bottom` for horizontal lines, `right` or `left` for vertical lines; it stops if it does not match the direction of the segment holding the label). Placing a label as positioned `text` makes it float away from the line or overlap it. To draw two lines (there and back) between the same two boxes, give each an `"offset"` (in; for horizontal lines down is positive, for vertical lines right is positive) to shift it up/down (left/right) from the box center (e.g. `-0.2` and `0.2`. If the label of the upper line is `top` and that of the lower line is `bottom`, no label sits between the two lines). Offset lines do not attach to the side-center connection points, so they are drawn from side to side without connecting to the boxes (they do not follow when the boxes are moved on screen). It cannot be written on bent lines, ends with a side, or `[x, y]` ends, and it stops if the offset pushes an end outside the box.
  - [slides-038] **Position checks (build warnings):** On the resolved form, it reports: an arrow line passing over other components (excluding the components at both ends and enclosures containing an end; for unfilled text, only where the text is), arrowhead tips gathering within 0.1 in, components partly overlapping (an enclosure fully containing the other, and components placed on the ring of an ellipse (`shape: ellipse`), are fine), labels of diagonal or bent lines overlapping lines, bordered components inside an enclosure (`box`) closer than 0.08 in to its sides (visual-044), bent lines for a single flow that neither branches nor merges (visual-043; arrows with sides written are not checked), and misaligned tier heights among same-shape `stack`s in a `row` (visual-024; `grid` cannot draw arrows and splits columns equally, so a `row` with `"arrows": true` and a `row` with differing column widths are not checked). `slides.py lint` and `dry` show them before building (2026-10-16. In the first JSON deck of 29 pages, 10 of 13 rebuilds of only 1–2 pages included `frame` pages, and half of the image findings in rounds 2–3 of `/deck-review` were `frame` diagrams. 「3 本の矢じりが同じ点に重なる」, found on images in round 3, shows up in this warning from the moment the page is written). Text heights and the bend positions of bent lines (estimated at the middle) are estimates, so check borderline cases on images. Bring this warning to 0 before building `frame` diagrams (do not build and move positions 0.1 in at a time while looking at images).
  - **Components:** Numbers count from 1. Every component accepts `id`, `w`, `h` (except `icon`, `num`, `arrow`; `row`, `stack`, `grid`, and `list` do not accept `h`. Height comes from the content; only `frame` requires `h`).
    - `text`: `text`, `size`, `color`, `bold` (whole text bold), `fill`, `line`, `dash`, `weight`, `align` [left, center, right], `valign` [top, middle, bottom], `mono`, `spacing` (line spacing %; if omitted, 125 for 2+ lines), `para_gap` (space between paragraphs, pt), `pad` (space between the edge of a filled box and the text, in; if omitted, one character's width), `shape` (shape of the figure: `rectangle`, `round_rectangle`, `ellipse`, `chevron`, `home_plate`, `folded_corner`, `can`. Only shapes used in past materials; add others when they are used. Normally do not write it. If omitted, a filled box is a rounded rectangle with radius 0.1 in and an outline-only box is a rectangle [`visual.md` §4]. Writing `rectangle` on a filled box shows up in the build warnings), `radius` (corner radius, in)
    - `label` (tag): `text`, `size`, `color`, `bold` (bold by default), `fill`, `align`, `mono`, `pad`, `radius`. `"w": "fit"` fits the width to the text (one character's width on each side)
    - `card`: `head`, `text` or `items: [["見出し", "説明"], …]` (an item without a description stops; lists that are not heading–description pairs go in `text` as bullets), `fill` (default `CARD`), `line` (default `RULE` on a `CARD` background, none on other backgrounds. `visual.md` §4, "fill or outline, not both"). `step` (in) places items at fixed intervals (only to align the top edges of items across left and right cards; markup cannot be written in `items`)
      - **Marked cards:** Writing one of `icon` (Iconify name), `num` (number), or `image` (logo etc.; written the same way as `src`) puts the mark on the left and the heading (bold 12pt) and body to its right. `"align": "center"` puts the mark at the top center and centers the text too. The content (mark and text) is placed at the vertical center of the frame. Cards stretched by `row` or `grid` to match their neighbors (and cards made taller with `h`) are top-aligned, so their heading heights match the neighbors'. A mark placed beside the text is always aligned to the first line of the heading (the first line of the body when there is no heading), regardless of how much text there is. Wherever the card is placed (`row`, `grid`, or `frame`), its mark lines up with the neighboring cards' marks. When the content (mark and text) of a card made taller with `h` is at most half the card's height, a build warning recommends `"valign": "middle"` (it looks at height, not line count; it is not shown for cards stretched to match their neighbors, cards with `valign`, or cards with `"align": "center"`; to keep the card top-aligned so its heading lines up with the neighbors', write `"valign": "top"`). `"valign": "middle"` keeps the content vertically centered even when stretched and centers the mark on the text (boxes in architecture diagrams etc.). `"valign": "top"` is always top-aligned. On a `NAVY` background, text and marks are white, and the number circle is red regardless of background (cards with dark backgrounds and no mark are also white text; `step` cannot be used on dark backgrounds). `"shape": "round_rectangle"` makes the number a rounded tag (only cards with `num`; it is not the shape of the card's box). This one component replaces `node`, `icard`, and `ncard`, which past materials made per material (together used on more than 100 pages)
    - `list` (marks and text in a list): `items` is a list of items; each item is text with markup or `{"head": …, "text": …}` (`- ` bullets cannot be written in an item's body). Items without a mark get numbers (red circles) counted in item order from `start` (default 1). Writing `icon` on the list makes it the mark of every item. Writing one of `icon`, `num`, or `image` on an item changes the mark of that item only (mixing numbers and icons still aligns the body's left edge). The mark's center is aligned to the center of the item's first line (the heading line if there is `head`). From the second line, text is indented to the body's left edge, and the mark stays beside the first line. `head` is bold 12pt. `text` written with `head` becomes gray supplementary text (`SUB`); `text` alone is in the body color. `size` (mark size: `small`, `medium` [default], `large`, same as `num`), `shape` (number shape; same as `num`), `digits` (zero-padded digits of integer numbers; `2` gives 01, 02 …), `color` (icon color; default is the body color), `gap` (space between items, in; default 0.16). If you place numbers or icons and text side by side with `row`, `row` aligns the top edges, so the text sits above the mark's center (shows up in the build warnings). Write marks and text as a `list` (sample: `samples/json/list.json`)
    - `stat` (emphasized number): `value` (the large number; `size` default 32pt bold), `unit` (unit; half the size of the number), `label` (what the number is; bold 12pt), `sub` (supplement; `SUB`), `color` (number color; default `RED_TEXT`, `RED_ON_NAVY` on `NAVY` backgrounds), `fill`, `line`, `align`. This is `stat` and `bignum` from past materials. The number and the unit go in the same paragraph (so it does not hit the lint rule 「数字だけの大きな段落」)
    - `code`: `text` lines, `hot` the numbers of lines to make red, `size`

### Writing pages.py (earlier materials, and pages JSON cannot express)

    d.source(s, ["出典: ", ("ブログの名前", {"link": "https://…"})])
    d.note(s, "話すこと。")

def make(d):
    p_cover(d)
    p_summary(d)

## 4. Laying out shapes and text

Do not align positions by computing coordinates; align with the features of shapes and text frames (`align`, `valign`). This holds up better when text grows, and is easier to fix on screen.

- **Make a shape and the text inside it one object.** Numbers, tags, and words inside arrows are `d.text(…, fill=RED, color=ON_RED, align="CENTER", valign="MIDDLE")`. `finish` groups the rounded background and the text into one editable group. A perfect circle is `kind="ELLIPSE"`. Unfilled text is a transparent rectangle as before.
  - [slides-008] **Build circular numbers with `d.num` and choose the size from small, medium, and large** (circle size and text size have a balance, so do not decide diameter and text size per material. Samples are on the template's component pages). `d.num` uses `d.text(…, kind="ELLIPSE")`. Google places text in a circle a further 0.1 in inside the inscribed rectangle, so in 0.3–0.36 in circles the text area is narrower than a 14pt digit and the digit shifts to the upper right (0.3 in: 3.5 pt right, 2 pt up; 0.36 in: 1.5 pt right. 「10」 wraps to 2 lines). Changing the font does not fix it (with 7 fonts it shifted right by 1.2–2.7 pt). `d.text` makes the circle fill only, overlays a transparent frame the same size as the circle, and groups them (shift within 0.6 pt). In a rectangular frame, even if the text area (the frame minus inner padding) is narrower than the digits, the overflow is spread evenly up/down and left/right and the text is centered. However, 2+ characters wrap if the width is too small (「10」 wraps at a 0.20 in text area and fits on 1 line at 0.22 in). A frame exactly at the estimated digit width wrapped when the font changed character widths slightly (「10」 in a medium circle; #51). So regardless of character count, the width is widened to the larger of the circle and the digit width, plus 0.05 in on each side (no branch that widens only for 2+ characters). The frame is wider than the circle, so do not connect arrows to numbers. Line spacing is 100%. At first the frame was larger than the circle by only the padding (0.1 in), but the frame was too large when selected (the current 1-character frame is 0.1 in wider than the circle). Do not place a circle with `d.box` or `_shape` and put text in it. Rounded-rectangle numbers (`shape="round_rectangle"`) for the same reason overlay, on a rounded background (`d.box`), a transparent frame widened the same way as for circles (`wide` of `d.text`).
- **When a large frame holds several blocks of text, separate frames are fine.** Cards with heading and body are `d.card` (it overlays a slightly smaller text frame on the box. The inner padding of a text frame is 0.1 in and cannot be changed, so the space between frame and text is made here). Use `body` to put the body in one frame, or `items` to list (heading, description) items at even intervals. For complex frames holding numbers, labels, and so on, place the frame with `d.box` and put text frames `PAD` (0.08 in) inside it. [slides-028] Decide the height of `d.card` from its content by passing `None` as `h` (`card_h` estimates the line count, moving alphanumeric words to the next line without splitting them across lines). Do not stretch it to match the neighboring column or the page bottom (in the records of the three representative pages, boxes larger than their content appeared in almost every deck). To align column heights, pass the maximum `card_h(w, head, body=…)` of the cards in the row. For cards mixing text of different sizes (large numbers) and for `d.box`, the caller decides the height. The inner text frame is not clipped when it overflows the box and is drawn as is, so when you add items or lines, also fix the box height (`step` in `items` uses the same interval for every item, so it overflows easily when an item with many lines comes last). Check the space between the last line and the bottom edge with 「要確認（画像で測った）」 of `gslides.py check` (`visual.md` §4. 2026-10-09).
- [slides-009] **Build the grid of gridded diagrams (Gantt, comparison tables, matrices) as a table (`d.table`).** Do not assemble rectangles and lines. Only things hard to express in a table (bars across months, the today line, labels) are placed as shapes on top of the table. With a table, whoever opens it can easily add rows and edit wording (lint reports `要確認` when there are 3 or more vertical lines with the same top edge and length). Table rows grow to fit the text (`row_h` is the minimum height). For tables with shapes on top, keep cell text to one line and check positions on images.
  - [slides-010] A customer's regular-meeting schedule (one Gantt page) is written with JSON `gantt` ("Components" in §2) (the component enforces the numbers below). Body text is 11pt, one month column is 1.0 in, and bar text is 9pt (visual-037. A bar is one shape of fill and text. For bars with tags too, overlaying a separate text frame on a filled rectangle makes lint report `要修正` for text under 11pt); words are up to 5 characters per line and 2 lines, with line breaks set by `\n`. Leftover height below the table (the table's bottom edge goes down to above the footer) is distributed equally to the rows (only as much as keeps rows from looking stretched: about 0.4 in for 11pt body text), and bars are placed at the vertical center of their rows. If only the top is packed and the bottom is empty, the page's visual weight shifts upward. For the next meeting, recreate it in a new folder (workspace `AGENTS.md` 「フォルダの置き方」) with page JSON, and get a new URL with `slides.py new`.
  - `vlines` of `d.table` (`(first column, number of columns)`) draws vertical rules in those columns below the heading row (`gantt` uses it for month boundaries). Rule shading (light between months, dark at item boundaries) is not supported. When needed, add a component (set `tableRange` of `updateTableBorderProperties` to the cell range).
- **Charts:** a single-series bar chart is written with JSON `bars` ("Components" in §2; drawn with shapes, so lint applies). Lines overlaid on bars (numbers with a different unit) and straight lines (targets, limits) can be written with `line` and `threshold` of `bars`. Bars with 2+ series, lines without bars, and charts whose numbers should be editable in Sheets (`createSheetsChart`) have no component, so add one to slides.py the first time it is needed (when past materials were counted on 2026-10-16, pages with boxes sized by values were 29 of 1,780, all single-series bars). Rules for legends, tick marks, and colors are in `visual.md` §5.
- **Align `y`, `h`, and `valign` for text placed side by side.** Cards placed side by side, numbers and headings, labels and body text, and so on get the same frame top edge and height, and the same `valign`. Things placed one line each (numbers and headings etc.) are centered with `MIDDLE`. Cards with different amounts of text use `TOP` so the heading heights match.
- **Put text stacked vertically in one text frame, separated by line breaks.** For things stacked top and bottom, such as heading and body or label and supplement, list `("見出し\n", {"bold": True})` and the body in `parts`. Do not make separate frames with shifted `y`.
- **Make the source line runs with a link per name.** Like `("Mandiant M-Trends 2026", {"link": url})`, attach links to the names of blogs, talks, and docs, and keep connecting 「、」 and parentheses as plain strings. Link to the Appendix source page with `{"link": <page number>}`. Use the same URLs in the source line and in the Appendix list (in pages.py, put them in one place at the top). In JSON, write `[name](URL)` and `[name](#p12)`. lint reports source lines without links as `要確認` (2026-10-06).
- [slides-011] **To align a text's left edge with the edge of another element, use `d.text(…, edge=True)`** (moves the frame outward by `INSET` (0.1 in); `page`, `source`, and `cover` already do this). Do not put a function in pages.py that moves frames outward (the old `t()`) (so that each material does not carry the same function).
- [slides-012] **For text left- or right-aligned in a filled box, passing the fill to `d.text` or `d.label` makes the space between the box edge and the text one character wide** (`visual.md` §4). The inner padding of a text frame is 0.1 in and cannot be changed, and even at 11pt it is less than one character, so the text frame is shrunk inward and grouped with the shape. When overlaying text on a `d.box`, keep the text edge at least one character away from the box edge. lint reports as `要確認` text whose space from the filled box's edge is narrower than one character (the smallest text size in that frame).
- [slides-013] **When putting a large number and its description in one frame, do not adjust line spacing to match the number.** `d.text` sets 100% line spacing only for paragraphs at 2× the base (`size`) or larger (with 125% left as is, Google's line advance is wider than pptx, and the number and description looked apart).

## 5. Slides API pitfalls

Checked on 2026-10-07.

- **`presentations.create` ignores `pageSize` and makes 10 × 5.625 in.** Always create by copying the template (`slides.py new`).
- **When the page count reaches 0, unused masters are deleted along with their layouts.** Delete previous pages only after creating new ones (`build` does this).
- **The Japanese language (`ja-JP`) cannot be set** (there is no field for it in text style). Leave line-breaking rules (kinsoku) to Google Slides' typesetting, and check on images for punctuation at line starts.
- [slides-014] **The inner padding of a text frame is 0.1 in and cannot be changed. The corner radius of Google's standard rounded rectangle also cannot be set directly.** Shared components compose rectangles and circles to make rounded rectangles with a fixed radius. Filled boxes with an outline (white cards etc.) do not draw a line; they make the outline by overlaying, on a rounded rectangle of the line color, a filled rounded rectangle shrunk inward by the line weight (0.75 pt). Joining circle outlines and side lines produced a 1–2 px step at the seams in Google's rendering. Unfilled rounded enclosures (`d.box(…, line=…, kind="ROUND_RECTANGLE")`) cannot fill the inside, so they are drawn with lines for the sides and Google arcs (`ARC`; by default a quarter circle at the top right) flipped and placed at the 4 corners. When the arcs were joined from 8 short lines, they looked angular and had steps at the seams. Even with arcs, Google draws lines and shape outlines differently, so depending on position a 1 px step remains at corners (it did not go away when replacing flips with rotations, or when making the sides shape outlines. 2026-10-08, measured on the template sample p.5). The default radius for `box`, filled `text`, and `card` is 0.1 in. If the short side is under 0.2 in, the radius is limited to half the short side. Explicit `kind="ROUND_RECTANGLE"` also gets this radius. Use `radius=None` only for things like small line drawings that need Google's standard shape. `kind="RECTANGLE"` stays a rectangle. Changing shared components does not change saved materials; it is applied the next time they are rebuilt with `slides.py build`. Other sessions reload the fixed tools at their next generation.
- [slides-015] **Add dotted lines with `dash=True`. Dotted rounded rectangles are still drawn with radius 0.1 in.** Unfilled rounded rectangles are made of 4 side lines and 4 corner arcs, so those 8 get the dash and weight. When there are both a fill and a dotted outline, a dotted outline is overlaid on the filled rounded rectangle (the method of bordering a filled rounded rectangle cannot be dotted). Adding a dash to Google's standard rounded rectangle (`radius=None`) makes the radius about 1/6 of the short side, and the curvature does not match the cards inside. Red emphasis enclosures use 2pt lines whether dotted or solid (they are lines for emphasis, so do not make them thin). `d.box` and `d.text` use 2pt when `weight` of a red line is omitted. Even at 2pt, a 1 px pale dot remains at the seam between line and arc (visible at 4× zoom; hardly noticeable at 1×). Samples are on the template's component pages (page 4 is a solid line on one table column, page 5 is dotted).
- **Bullet dots are drawn about half the text size to the left of the first line's indent** (6 pt at 11pt, 7.2 pt at 14pt; measured on 2026-10-08). With 0 indent, the dot sticks out beyond the text's left edge in the frame. `d.text(…, bullets=True)` indents the first line by half the text size so that the dot's left edge aligns with the body's left edge.
- Text positions are counted in UTF-16 units (emoji etc. count as 2). `u16` in `slides.py`.
- The ID of the speaker notes frame is known only after the page is created. `build` writes notes in a second batchUpdate.
- [slides-016] Text that overflows its frame is not clipped. lint only checks bodies over 8 lines, so check overflow on images. Whether manually broken lines fit the frame is warned at build time using the `em_width` estimate. The estimate is not accurate to one character, so check lines over 98% of the frame width on images.
- Adding a link makes the text the theme's link color (red) unless a color is written. `d.text` writes the surrounding color.
- Inner padding of table cells cannot be changed via the API.
- **The API accepts font names even for fonts that do not exist, and silently renders another font.** `Noto Sans CJK JP` (the docx font), `Hiragino Sans`, and `Yu Gothic` became Mincho and a Latin serif. Japanese fonts in Google Fonts (BIZ UDPGothic, M PLUS 2, IBM Plex Sans JP etc.) render (`Research/google_slides_jp_fonts_20261007.md`). lint stops with `要修正` on fonts other than the template's font (default Noto Sans JP) (the monospace font for code [default Cascadia Mono, the theme's `mono`] passes for alphanumerics only, and stops when Japanese is included).
- [slides-017] **If the Google Fonts version of a monospace font has ligatures, Google Slides renders them, and the API cannot turn them off.** JetBrains Mono's `->` became a single arrow character. Code uses Cascadia Mono, which has no ligatures (`MONO`; it can be changed with the theme's `mono`, but `LIGATURE_MONO` fonts with ligatures stop), applied with `mono=True` and `mono_cols`. `mono_reqs` also makes leading indentation spaces monospace (if the spaces stay in Noto Sans JP, a 4-character indent shrinks to about 1.5 characters). Character width is estimated with `MONO_EM` (0.586 em; the Cascadia Mono value, not changed by the theme's `mono`) (`Research/monospace_font_google_slides_20261009.md`).
- [slides-018] **Checks use thumbnails (`pages.getThumbnail`) only, not PDF export.** 12 pages take about 5 s (6 in parallel), as fast as exporting to PDF and converting to images. It is the same rendering as the Google Slides UI, can be re-fetched per page, has no 10 MB limit of Drive export, and needs no poppler. Thumbnails count against the expensive read quota (per-minute limit), so `gslides.py` waits and retries when 429 is returned. Thumbnail URLs expire in 30 minutes.
- Drive `files.export` stops at 10 MB (403 「This file is too large to be exported.」). When pptx is needed, use `gslides.py export` (exports from `exportLinks`; it also exported the 14.6 MB 65-page internal template).
- **Exported pptx has language `en` even for Japanese text** (`../deck-research/sources.md`). If asked to hand pptx to a customer, after exporting, align fonts and language with the workspace's `Archive/pptx_pipeline_20261007/skills/office-jp/scripts/fixjp.py --all` (without the language, PowerPoint puts punctuation at line starts). Ask the user before handing it over.

## 6. Images, logos, and icons

- [slides-019] **For images and icons, just pass a URL or a local path to `d.image` or `d.icon`.** How they are inserted (the temporary pptx below) is handled inside `slides.py build`, so do not worry about it when writing pages. Use it as is even for requests that say 「pptx を介さず」 (the deck itself does not go through pptx). Do not omit meaningful icons. Simple line drawings may be built as editable shapes with `d.box` and `d.arrow(..., head=False)`, but do not substitute custom shapes for official product logos or complex images.
- [slides-020] **For where to get them, prefer what can be inserted by URL as is.** Sources and URL forms are in `assets/README.md` (the ledger of assets inside this skill; when you add one, also write it in the ledger. Images only you use go in the workspace's `assets/`; `asset()` looks there first). Search in this order.
  1. Pass public PNG, JPG, or GIF URLs directly to `d.image` (AWS and Azure architecture icons from mingrammer/diagrams, photos from Unsplash, etc.).
  2. Icons and product logos are `d.icon(s, "tabler:database", x, y, 0.4)` (Iconify).
  3. [slides-021] Things distributed only as files (current Google Cloud icons, your own company's product icons) go in `assets/` directly under the workspace and are passed as `asset("gcp/bigquery.png")`. Do not copy them into the material folder (so they can be reused across materials).
  4. Images for that material only (screenshots, diagrams from a reused deck) go in `build/assets/`.
- [slides-022] **The Slides API can read only PNG, JPG, and GIF by URL.** Passing an SVG URL to `d.image` stops. Use PNG URLs first, and when SVG fits better (the PNG is too small to place large, no PNG is distributed, you want to change the color), switch to `png(<SVG URL>, w=1024)` (a URL where wsrv.nl renders it to PNG). Local SVGs (`.svg` in `assets/`) are converted to PNG at build time, so they can be passed as is.
- `d.image(s, <path or URL>, x, y, w, h)`. The image fits in the frame keeping its aspect ratio and is centered in the frame. To align it left or top, give the frame the same ratio as the image.
- [slides-023] **Local images (`assets/`, `build/assets/`) are inserted via Drive at build time (`carry` in `slides.py`).** The Slides API can read only images at public URLs (URLs of private Drive files are refused as not 「publicly accessible」). `build` makes a pptx with pptxgenjs holding one image per page, uploads it to the root of My Drive as Google Slides, inserts from that image's URL, and deletes the uploaded file (no folder is specified, so the script works as is when given to others). It does not change sharing settings to make anything public. Drive has no equivalent of S3 presigned URLs (sharing expirations can be set only for specific people and groups, and do not apply to APIs fetching anonymously). Google Cloud Storage signed URLs also work, but are not used (the speedup is only about 4 s for builds with images, which does not justify keeping a bucket and a signing SA, not working when given to others, and putting images in the sandbox. `Research/gcs_signed_url_images_20261008.md`). Drive's `thumbnailLink` is refused by the Slides API. The URL passed remains in the deck as the image's `sourceUrl`.
- To paste a page of another Google Slides as is, pass `thumb_url(<URL>, <page number>)` to `d.image` (`../deck-practices/reuse.md` Stage 1).
- **Customer logos** are taken from case-study pages your company has published, or from that company's official press kit (it is easy to confirm the permitted scope of use). Do not download them; pass the URL through `png()` and insert with `d.image(s, png("<SVG URL>"), …, alt="<company name>")`. The Splunk logo is the PNG URL of `Splunk_logo.svg` on Wikimedia Commons (width is the fixed value in the ledger; images on splunk.com could not be fetched directly).
- [slides-024] **Icons and product logos** are placed by Iconify name, like `d.icon(s, "tabler:database", x, y, 0.4)` (find names at https://icon-sets.iconify.design/; if a name does not exist, it stops before building). `tabler:` is line art in one color, the body color `303F47` (default). One-color logos are `simple-icons:`, with the brand color passed as `color` (e.g. `d.icon(s, "simple-icons:postgresql", x, y, 0.4, "4169E1")`). Colored logos are `logos:` (for the mark only, `logos:<name>-icon`; `color` has no effect). The alt text gets the name. Pass `color` as 6-digit hex. `color` also accepts role names (`NAVY`, `SUB` etc.). Image colors cannot point to theme colors, so `d.icon` converts them to 6-digit hex from the deck's color scheme (the color scheme is taken from the theme file. For decks without a theme file, `build`, and `lint`, `dry`, and `resolve` given a URL, read it from the deck's master. Otherwise the visual color scheme). react-icons names from older pages.py (`TbDatabase`, `SiPostgresql`) also build as is (converted to PNG locally at build time).
- [slides-025] **When your company's product icon is not in the workspace's `assets/`, before substituting line art (`tabler:`), search the internal icon collection (where to search is in the workspace's `rules/deck-build/slides.md`), and if found, add it to `assets/` and its ledger.** For images with a white rounded background and a shadow, remove the background and shadow to make them transparent. Use line art only for what is not found, and write it in the outline (checked in review aspect 5 of `../deck-review/prompt_slides.md`, "is a product replaced by a generic line icon").
- **Your company's product icons** go in the workspace's `assets/<company>/` and are placed with `d.image(s, asset("<company>/<product>.png"), …, alt="<product>")`. Other companies' products are `logos:` (Snowflake, Oracle, Salesforce, Tableau, Power BI, Redshift, etc.). Google Cloud products such as BigQuery are missing from `logos:` or have old artwork, so use `asset("gcp/<product>.png")`.

## 7. pptx decks from before 2026-10-07

- They were made with pptxgenjs or python-pptx, and the pptx was uploaded to Drive. build.js files that load `deck.js` (8 of them) do not work unless changed to load `deck.js` from the workspace's `Archive/pptx_pipeline_20261007/skills/office-jp/scripts/`. build.js files that carry copied components work as is. When fixing one, ask the user whether to fix it as pptx or rebuild it in Google Slides (the steps for fixing as pptx are in that Archive's `README.md`).
- Decks from before 2026-10-06 were made before the 11pt text minimum and the current colors (visual.md). When rebuilding, ask the user whether to bring the whole deck in line with the current rules.
- [slides-026] **When rebuilding in Google Slides**: rewrite build.js pages as page JSON (slides-034), without changing the content (headings, body, notes). Use JSON components, and do not copy deck.js components (only what JSON components cannot express becomes pages.py functions). Coordinates can mostly be reused, but these 6 things broke.
  - Unfilled text that had `margin: 0` in pptxgenjs shifts by Google's frame inner padding (§5). Use `d.text(…, edge=True)` (§4). Use `d.label` for filled tags and `d.num` for numbers
  - `row_h` of `d.table` also applies to heading rows. For rows that should grow with content, make `row_h` small and let rows grow to fit the text
  - Left-aligned filled tags that took left padding with pptxgenjs `margin` (12pt etc.) fell short of one character in Google, because inner padding is fixed at 0.1 in. Passing the fill to `d.label` or `d.text` leaves one character's space (§4)
  - Putting a large number and its description in one frame at 125% line spacing made them look apart, because Google's line advance is wider than pptx. `d.text` sets 100% line spacing only for the number's paragraph (§4)
  - Grids built from lines (Gantt) are converted to tables, and boxes for people or products that were text only get icons and logos (§4, `visual.md` §6). The added items narrow the text width, producing last lines of 1–2 characters, so check on images and tighten the wording
  - The URL changes (it cannot be built into the pptx URL). Keep the previous pptx on Drive, and ask the user whether to delete it. List both in references_index.md, and write which is the current version
  - [slides-027] Do not copy build.js components (text, box, chip, table etc.) as a component set with the same calls. If building with pages.py, put in only the small functions that material needs (text edge alignment is `edge=True`, tags `d.label`, numbers `d.num`, white cards `d.card`; do not copy these into pages.py). Confirm the approach with the user, and if over 10 pages, check the three representative pages (`../deck-practices/SKILL.md` "How to start", step 6) yourself before building the whole deck.
