description: Full review of a material (Google Slides or Google Docs) before returning it to the user. Uses lint, a contact sheet of all pages, and a separate subagent's eyes to find cross-page defects and single-page defects, verifies the findings, fixes and rebuilds what may be fixed, and asks about anything that changes a claim, number, or order. Checks and fixes during building are done with deck-build's gslides.py check and doc-build's docs.py check; this one runs before delivery. The review prompts are per-format files (prompt_slides.md, prompt_doc.md). `/deck-review <URL>`. Use when asked 「レビューして」「見直して」「渡す前に確認して」, and always before returning a newly made material to the user. For fixes after delivery, run only the scope decided in deck-practices "Requests after delivery".

# Full review before delivery

[deck-review-001] While building, run lint with deck-build's `gslides.py check` for slides and doc-build's `docs.py check` for documents, and open the images of the changed pages yourself and fix them (`../deck-build/SKILL.md` "Reading the results", `../doc-build/SKILL.md` §5). This skill is the review of the whole material that runs after that, before returning it to the user. Steps, What to fix, Finding format, and How to ask are the same for every format; only the review prompt is split per format (slides: [prompt_slides.md](prompt_slides.md), documents: [prompt_doc.md](prompt_doc.md)). A separate pair of eyes finds the cross-page defects that page-by-page checks miss (story, runs of the same pattern, uneven whitespace and density, the number of decorations) and the defects the maker overlooks (研究 1-3、AI 実践 1-4、中身 1-12; the abbreviations are in the table in `../deck-practices/SKILL.md`). For fixes after delivery, how far to run (one round on the changed pages only, the whole material, or not at all) is decided by deck-practices-017 in `../deck-practices/SKILL.md`.

`/deck-review <Google Slides or Google Docs URL> [--talk]`. If the URL is omitted, use the URL written in the outline of the working folder. The URL decides the format (`/presentation/` is slides, `/document/` is a document). `--talk` is for materials that are spoken, such as LTs (slides only). Steps 1–6 below (check again, ask, verify findings, fix, rebuild and check) count as one round; run up to the round limit.

## Steps

```sh
K=<deck-build folder>/scripts   # The folder that holds deck-build's SKILL.md. From another skill, ../deck-build/scripts relative to that skill's folder
python3 $K/gslides.py check <URL> --all [--talk] # Slides. Images of all pages (the checkpoint for cross-page review)
D=/tmp/slides_<first 8 chars of ID>              # Output of check (deck.json from presentations.get [not build/deck.json], deck.md, p-NN.png)
python3 $K/docs.py check <URL>                    # Document (Google Docs)
D=/tmp/docs_<first 8 chars of ID>                # Output of check (doc.json, text.md, p-N.png)
uv run -q $K/sheet.py $D/sheet.png $(ls $D/p-*.png | sort -V) --cols 4 --width 400 --per 16   # Contact sheet (16 pages each: sheet-1.png …; sheet.png if 16 pages or fewer)
```

1. **Check all pages again.** For slides, run `gslides.py check --all` and the contact sheet; for documents, run `docs.py check` and the contact sheet. If you just built the whole material and ran `check --all` (deck-practices "How to start", step 8) and have not rebuilt since, reuse that output (`$D`) and contact sheet; do not run them again. If lint `要修正` items remain, fix them first.
2. [deck-review-002] **Confirm the audience.** Take the material type, the audience, and what the audience can do after reading (`../deck-practices/SKILL.md` "How to start", step 5) from the outline and write them into the review prompt. Use the outline's words as they are and do not add audiences (adding them produces off-target findings that do not fit the audience).
   [deck-review-003] **When porting to another format, also compare with the original.** Hand over the original's checkable images, layout, icons, and alignment, and check rounded corners, meaningful icons, text placement, and changes in whitespace. If you cannot prepare the original's images, state which part is not covered. Do not treat a lint pass as evidence that the design was kept.
3. [deck-review-004] **Ask.** Ask with the per-format review prompt (slides: [prompt_slides.md](prompt_slides.md), documents: [prompt_doc.md](prompt_doc.md)) ("How to ask"). For documents, also ask for one reader test at the same time ("Reader test" in `prompt_doc.md`; it checks whether a reader can reach the answers from the document alone). Decide from the page count and the wait time whether to show all pages to one child or to split the page review among owners and ask in parallel ("How to ask", "Split and ask in parallel"). While waiting, do work that does not depend on the result (the record and `references.md` up to the previous round, lint `要確認` items, fixes you found yourself). Do not rebuild the material the child is looking at, and do not run check (deck-practices-013 in `../deck-practices/SKILL.md`).
4. **Verify the findings.** Review children also report defects that do not occur. Fixing without verifying changes places that need no change and creates new defects. Before fixing, check one by one whether each finding really occurs. Check visual findings (overflow, misalignment, overlap) on the full-size image (`$D/p-NN.png`; crop details with `sips -c`) or by the coordinates in the JSON in `$D` (`deck.json`, `doc.json`). If it does not occur, mark it 「残した（誤り）」 (that count is used to fix rules and aspects that miss often; `../deck-practices/rules.md`). Put lint `要確認` items into the same table, one per row. For each verified finding, write the matching rule in the 「決まり」 column ("Finding format" below).
5. [deck-review-005] **Fix.** Follow "What to fix" below. Fix the page JSON (pages.py for older decks; `build/doc.md` for documents) and the outline, and rebuild with `slides.py build <URL>` (`docs.py build <URL>` for documents). When you fix the body, apply the same fix to the same spot in that page's speaker notes (counts, ranges, names, assertions), because fixing only the body leaves a mismatch with the notes that shows up in the next round.
   [deck-review-011] **You may split the fixes among children that own pages (slides only).** The time between rounds (the parent verifies, fixes, and rebuilds) is longer than the child's review (in 23 pi records, the median child review was 4.9–6.9 minutes and the time between rounds 11.7 minutes; `Internal/deck_speed_202610/社内メモ_計測の結果.md`). The parent decides whether and how to split.
   - Give a child only the rows verified in step 4 and marked 「直す」 under "What to fix". The unit is the page file (`p<number>.json`; slides-031 in `../deck-build/slides.md`; for pages.py decks, the page function 〔slides-030〕). Rows that hit the same file or function go to the same child. 2–4 pages per child.
   - The parent keeps: 「聞く」 rows, fixes that touch a claim, number, or order, and cross-page fixes (inconsistent notation, numbers across pages, the order in `deck.json`; for pages.py decks, shared functions and constants and the order in `make`). For the part of a cross-page fix that falls on an owner's page, the parent decides the fix and adds it to that child's rows. The parent does not write an owner's files or functions until the child returns (it would conflict with the child's fix).
   - Rounds not to split: rounds with fewer than 4 pages to fix, and rounds where every page's fix takes a few lines (a period, a word swap, an empty cell). Also do not split pages.py decks whose pages are not split into functions (written the old way with all pages in `make`), because the child's functions would not be called from `make`. A child takes 2–4 minutes each, so it does not pay off (one trial on 12 pages on 2026-10-14; the threshold is a guess). Do not split documents (`build/doc.md` is a single file, and fixing any section moves the page breaks).
   - Ask the same way as in "How to ask" (a new child, the same model as the main agent), with the prompt in [prompt_fix.md](prompt_fix.md). The child edits its page files in place (for pages.py decks, it writes the fixed functions to `build/fix_<owner>.py` and does not write pages.py) and does not build. Fixes that conflict with the outline or the corrections, and fixes that touch anything outside its pages, are returned without deciding. While waiting, the parent puts its own share into files outside the owners' (pages.py for pages.py decks).
   - When the children return, re-sort the returned rows in the step 4 table (「直す」, 「聞く」), bring `slides.py lint <URL>` to zero `要修正`, then build only once (`slides.py build`). If a child does not return, or `lint` stops on a JSON error, the parent fixes that child's rows (do not re-ask and wait). For pages.py decks, merge in `build/` with `slides.py merge fix_<owner>.py …`, check that the function names that come out match the owners, add the names the child wrote on the docstring's 「import:」 line to pages.py's imports, then build (if merge stops on a syntax error, the parent fixes it too). Delete each child's `fix_<owner>.py` right after merging (if it stays under the same name into the next round, the previous round's function gets merged in place of a child that finished without writing). Delete `pages.py.bak*` when delivering in step 7.
6. **Check the fixed pages again.** While putting in fixes, use `slides.py lint <URL>` (no build) to bring `要修正` to zero; after all of the round's fixes are in, build only once, run `gslides.py check <URL>` (takes images of the fixed pages only and writes `$D/changed.json`; for documents, `docs.py check <URL>` on all pages, because page breaks move), rebuild the contact sheet, and ask again with the fixed pages and the contact sheet. From round 2, add 「直したこと」 (one line per page) to the prompt and have the child return only new defects and ones not fully fixed. Write the 「聞く」 items so that they are not raised again. Steps 1–6 count as one round; stop at the number of rounds in `[review] deck_review_max_rounds` in `factory.toml` (1–3; 3 if not set). If a fix increases defects, revert that fix, because the more rounds you run, the more likely a fix's side effects create new defects ("Basis" below).
   [deck-review-006] **How to end.** You may stop mid-run only when there are zero findings to fix. If even one finding was fixed, ask for the next round (except when the last round has ended). Fixes made in the last round need not be sent to a child again, but check them yourself with `gslides.py check` (`docs.py check` for documents) and the images of the fixed pages before delivering. Findings not fully fixed in the last round (also when the count does not drop, and when the limit is 1 round) go in the table as 「残した（<number of rounds> ラウンドで打ち切り）」 when you deliver (so you do not end without checking after a fix, or deliver while hiding that the count did not drop).
   [deck-review-013] **Before asking for the next round, write out and summarize the round.** Append the round's table ("Finding format" below), the 「直したこと」 to add to the next round's prompt, and the questions for the user to `$D/review.md` (the same file as the table delivered in step 7). If you can call a context-summarizing tool, call it after that (deck-practices-005 and 015 in `../deck-practices/SKILL.md`). In the continuation instructions, write which round you are about to ask for, the URL, `$D`, and the files to reread (`$D/review.md`, the outline, step 6 and "How to ask" in this file, the review prompt). If you cannot call it, just append and ask for the next round. This step averages 68 calls per run, and 8 of 11 automatic summaries at 400k ran here (2026-10-14; the same record as deck-practices-005).
7. **Deliver.** Return the Drive URL, the findings table (format below), and the list of questions for the user to the user. Write the delivered table (all rounds) to `$D/review.md` (do not rewrite the earlier rounds' rows appended in deck-review-013; add the last round's table. For findings carried over to the next round, write the page and 「何が起きているか」 with the previous round's wording; the ledger uses these two and the rule to identify the same finding), and import it into the rule ledger with `python3 <deck-practices folder>/scripts/ledger.py review --deck <material folder> --table $D/review.md` (dreaming counts results per rule. The same row is not counted twice, and the same row across rounds takes the later round's result). After checking, you may delete `$D`. For pages.py decks, also delete the `build/pages.py.bak*` left by `slides.py merge`.

Basis: the round limit and reverting when things get worse follow research on draw-look-fix loops (ACE: two thirds finish in one pass, limit of 3 passes, roll back when worse) (研究 1-3・1-4).

## What to fix

[deck-review-007] Review findings mix things that a fix settles and things whose fix changes what the material says. Fixing the latter silently changes the claims, numbers, and order agreed with the user without the user knowing (deck-practices-010 in "Working practices" of `../deck-practices/SKILL.md`: "Do not silently change confirmed claims, numbers, or order."). So sort each finding into one of the two before fixing. When unsure, ask.

| Category | Examples | What to do |
|---|---|---|
| 直す | lint `要修正`, 「和欧間のスペース」, 「約物」, overflow, overlap, collision with the footer, misaligned arrows, boxes larger than their content, inconsistent notation, first use of abbreviations, line-break positions that do not change the wording | Fix it and write 「直した」 in the table. Do not shrink text to fit (consider rephrasing, a diagram, then splitting the page, in that order; for a split, build it split and then ask; deck-practices-010 in `../deck-practices/SKILL.md`). Shrinking a box so the bottom of the page becomes empty is fine (adding content is a question) |
| 聞く | Changing a heading, claim, number, or order; adding, deleting, or splitting pages; adding another example or path for fairness; removing a conclusion band or kicker; preferences in phrasing; items the reviewer rated 「聞く」 (not decided by the rules, or readable either way) | Do not fix. Write 「聞く」 and a proposed fix in the table and return it to the user |

## Finding format

One finding per row. The reviewer returns up to 「直し方の案」; you (the maker) write 「結果」 and 「決まり」. Compare the counts per round to see whether fixes increased them.

`p<ページ> | <出所: lint・一覧・画像・テキスト・読み手テスト> | <観点 1〜5> | <直す／見直す／聞く> | <何が起きているか> | <直し方の案> | <結果: 直した・残した（理由）・残した（誤り）・聞く> | <決まり>`

- **決まり:** the ID of the rule the finding falls under (`visual-012`, `ws-visual-003`; customer memory is `ws-memory-001`; separate several with `,`). Attach to each ID, in 「」, a phrase copied verbatim, in the rule's own language, from that rule's text (the text after `[ID]`) (`visual-013「単語や文節の途中で折り返さない」`; do not put `|` or 「」 in the phrase). `ledger.py review` reports and skips only that ID when the phrase is not in that ID's rule text or the ID's rule is not found (this stops mislabeled IDs; IDs without a phrase are imported and their count is reported). For lint findings, use `lint:<rule name>` (the name inside `[ ]` in the lint output). If no rule applies, `-`. Do not make the reviewer look these up (so it looks with eyes that do not know how the material was made; deck-review-008). You look them up in `rules/`, the customer's `memory.md`, and the skill rules when verifying the findings. If unsure, use `-` and do not guess (this becomes the count of whether a rule worked or missed).

## How to ask

- [deck-review-008] **Use an independent context and the same model as the main agent.** Do not pass the conversation history from building; give a new subagent only the per-format prompt and the paths of the material. Have it read the intent from the outline's 「資料の種類・聞き手・聞き手の問い・読んだあと聞き手ができること」. If you are building with Opus, use Opus; with Sonnet, Sonnet; with Codex, the main agent's actual model ID.
- **Claude Code:** ask a new `general-purpose` child. For the model, pass the same alias as the main agent, as in 「基本方針」 of AGENTS.md. If a review is shallow, check the images it opened and its grounds, and ask a new child again with the same model. Do not change the model silently.
- **Codex:** create a new child with `fork_turns: "none"`, and set `model` to the main agent's actual model ID and `reasoning_effort` to the main agent's current setting explicitly. This skill instructs you to specify model and effort explicitly. Do not fork the full history. Do not omit them, because the `[agents]` default model can differ from the main agent.
- [deck-review-009] **When using the T3 Code delegation tool:** in the live capability list, confirm that the same provider instance and model as the main agent are available, and create a new delegated task targeting them. Make each round a new task, and pass the prompt, the previous findings, how they were handled, and open points explicitly. Set `mode` to `async`, finish the waiting-time work of step 3, then wait with `t3_thread_wait` (how to wait: deck-practices-013 in `../deck-practices/SKILL.md`). `mode: "wait"` can return "fetch failed" while the child is still running. If that happens, do not ask again; check with `task_status` whether the child is running, and wait again with `t3_thread_wait`.
- In an environment where you cannot launch a child with the same model and without the conversation history, do not silently switch to another model or a full-history fork; report the constraint. When delivering, report how you launched the child, which model you specified, and whether you could confirm the actual model.
- Pass the paths of the image folder (`$D`), the contact sheet, the text (`deck.md`, `text.md`), the outline, the root `AGENTS.md`, and, for customer-facing materials, that customer's `memory.md` (the audience's preferences) and `profile.md` (the customer's business and setup). Do not pass the page JSON, pages.py, or `build/doc.md` (so it looks with eyes that do not know how the material was made).
- You may run two children side by side split by aspect (story and wording; visuals).
- **Split and ask in parallel.** Defects contained in one page (aspect 2's single-page matters, and aspect 5's checks on single-page images) do not get missed more when split by page. When there are many pages and one child would likely look shallowly at the later pages, or when you want to cut the wait, split into owners per chapter (section divider) or per few pages and ask at the same time (in Claude Code, call several children in one message; with T3 Code delegation, make a separate task per owner). The main agent decides whether and how to split (round 1 on 12 pages took about 100k tokens and 3.4 minutes with one child; `Research/deck_review_skill_design_20261008.md`). When splitting, keep the following.
  - Keep one whole-material child. It covers cross-page matters (aspects 1 and 3, aspect 2's numbers across pages and rehashes, aspect 4's inconsistent notation and first use of abbreviations, and aspect 5's contact sheet). Do not have it report single-page matters, and let it open full-size images only to confirm a cross-page suspicion, up to 3 images (how to change the prompt is at the top of [prompt_slides.md](prompt_slides.md)). When split into two by aspect, the "story and wording" child is this one.
  - Have page owners open only the full-size images of their pages, and give them the full text (without knowing abbreviations and numbers explained on earlier pages, they report off-target findings). For cross-page matters, have them return only the suspicion, marked 「全体へ」. For an owner's page images and that page's lint and box_pad findings, you can pass the entries in `$D/changed.json` (from round 2) as they are. Have them use only images the parent took; do not let a child run check (they would compete for the limit of 60 images per minute per person).
  - Make each owner a group of a few pages (per chapter, or pages of the same pattern), not one child per page (each child costs startup and skill loading, and there are model API rate limits). From round 2, if only 1–3 pages were fixed, the parent checks them without a child.
  - The main agent merges the findings. Merge overlaps into one before verifying in step 4. From round 2, one child is enough if few pages were fixed. Because the split changes between rounds, compare counts per page.
- Do not have them give scores. Have them return only a list of defects.
- **Have pi (T3 Code delegation) children write findings to a file and reply with only the counts and the path** (`<findings file>` is `$D/review_<round>_<owner>.md`). pi's summary keeps only the first 2,000 characters of a tool result. If a summary happens between receiving and fixing, the later findings are lost (2026-10-10; one child had 16k characters; `Research/pi_compaction_deck_workflow_20261010/README.md`). For other children, delete the line "Write all of the above to <findings file> …" from the prompt and receive the findings in the reply.
- Before putting in a finding, check that it does not stray from the one sentence that page wants to say. Put ones that stray into 「聞く」.
