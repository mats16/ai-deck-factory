# 返す前の全体のレビュー

[deck-review-001] 作っている途中は、スライドは deck-build の `gslides.py check`、ドキュメントは doc-build の `docs.py check` で lint を通し、変えたページの画像を自分で開いて直す（`../deck-build/SKILL.md` の「結果の見方」、`../doc-build/SKILL.md` の 5）。ここは、それが済んでからユーザーに返す前に通す、資料全体のレビュー。手順・直す範囲・指摘の形・頼み方は形式によらず同じで、依頼文だけを形式ごとに分けてある（スライドは [prompt_slides.md](prompt_slides.md)、ドキュメントは [prompt_doc.md](prompt_doc.md)）。1 枚ずつ見ていると拾えない、ページをまたぐ欠陥（話の筋、同じ型の連続、余白と密度のばらつき、飾りの数）と、作った本人が見落とす欠陥を、別の目で洗い出す（研究 1-3、AI 実践 1-4、中身 1-12。略称は `../deck-practices/SKILL.md` の表）。

`/deck-review <Google Slides か Google Docs の URL> [--talk]`。URL を省いたら、作業中のフォルダの構成案に書いた URL を使う。形式は URL で決める（`/presentation/` はスライド、`/document/` はドキュメント）。`--talk` は LT など話す資料（スライドだけ）。下の手順の 1〜6（確かめ直す・頼む・指摘を確かめる・直す・組み直して確かめる）を 1 ラウンドと数え、上限のラウンドまで回す。

## 手順

```sh
K=<deck-build のフォルダ>/scripts   # deck-build の SKILL.md のあるフォルダ。ほかのスキルからは、そのスキルのフォルダの ../deck-build/scripts
python3 $K/gslides.py check <URL> --all [--talk] # スライド。全ページの画像（ページをまたいで見る区切り）
D=/tmp/slides_<ID の頭 8 字>                      # check の出力（presentations.get の deck.json〔build/deck.json とは別〕・deck.md・p-NN.png）
python3 $K/docs.py check <URL>                    # ドキュメント（Google Docs）
D=/tmp/docs_<ID の頭 8 字>                        # check の出力（doc.json・text.md・p-N.png）
uv run -q $K/sheet.py $D/sheet.png $(ls $D/p-*.png | sort -V) --cols 4 --width 400 --per 16   # 一覧（16 枚ずつ sheet-1.png …。16 枚以下なら sheet.png）
```

1. **全ページを確かめ直す。** スライドは `gslides.py check --all` と一覧、ドキュメントは `docs.py check` と一覧を回す。直前に全体を組んで `check --all` を回し（deck-practices の「作業の始め方」の 8）、そのあと組み直していなければ、その出力（`$D`）と一覧をそのまま使い、回し直さない。lint の要修正が残っていたら、先に直す。
2. [deck-review-002] **聞き手を確かめる。** 資料の種類・聞き手・読んだあと聞き手ができること（`../deck-practices/SKILL.md` の「作業の始め方」の 5）を、構成案から拾って依頼文に書く。構成案の言葉のまま書き、聞き手を足さない（足すと、聞き手とずれた的外れな指摘が出る）。
   [deck-review-003] **別形式への移植は元資料とも比べる。** 元資料の確認可能な画像・配置・アイコン・揃え方の資料を渡し、角丸・意味のあるアイコン・文字の配置・余白の変化を確認する。元の画像を用意できない場合はその範囲を明示する。lint 合格をデザイン保持の証拠にしない。
3. [deck-review-004] **頼む。** 形式ごとの依頼文（スライドは [prompt_slides.md](prompt_slides.md)、ドキュメントは [prompt_doc.md](prompt_doc.md)）で頼む（「頼み方」）。ドキュメントは、同時に読み手テストを 1 本頼む（`prompt_doc.md` の「読み手テスト」。読み手が文書だけで答えにたどり着けるかを見る）。1 本で全ページを見せるか、ページごとの見方を担当に分けて並列に頼むかは、枚数と待ち時間を見て決める（「頼み方」の「分けて並列に頼む」）。待つ間は、結果によらない作業（前のラウンドまでの記録と `references.md`、lint の要確認、自分で見つけた直し）を進め、子が見ている資料は組み直さず、check も回さない（`../deck-practices/SKILL.md` の deck-practices-013）。
4. **指摘を確かめる。** レビューの子は、起きていない欠陥も挙げる。確かめずに直すと、直さなくてよいところを変えて新しい欠陥を作る。直す前に 1 件ずつ、本当に起きているかを見る。見た目の指摘（はみ出し・ずれ・重なり）は、原寸の画像（`$D/p-NN.png`。細部は `sips -c` で切り取る）か `$D` の JSON（`deck.json`・`doc.json`）の座標で見る。起きていなければ「残した（誤り）」にする（その数は、外れの多い決まりと観点を直すのに使う。`../deck-practices/rules.md`）。lint の要確認も、同じ表に 1 件ずつ入れる。確かめた指摘には、当たる決まりを「決まり」の列に書く（下の「指摘の形」）。
5. [deck-review-005] **直す。** 下の「直す範囲」に従う。直すのはページの JSON（前の資料は pages.py。ドキュメントは `build/doc.md`）と構成案で、`slides.py build <URL>`（ドキュメントは `docs.py build <URL>`）で組み直す。本文を直したら、同じページのスピーカーノートの同じ箇所（数・範囲・名前・言い切り）も同じ直しに合わせる（本文だけ直すと、ノートとの食い違いが次のラウンドで出る）。
   [deck-review-011] **直しをページの担当の子に分けてよい（スライドだけ）。** ラウンドの間（親が確かめて直し、組み直す）は、子のレビューより長い（pi の記録 23 本で、子のレビューの中央値 4.9〜6.9 分、ラウンドの間 11.7 分。`Internal/deck_speed_202610/社内メモ_計測の結果.md`）。分けるか、どう分けるかは親が決める。
   - 子に渡すのは、手順 4 で確かめ、「直す範囲」で「直す」にした行だけ。単位はページのファイル（`p<番号>.json`。`../deck-build/slides.md` の slides-031。pages.py の資料はページの関数〔slides-030〕）で、同じファイル・関数に当たる行は同じ子に渡す。1 本に 2〜4 枚。
   - 親が持つもの: 「聞く」の行、主張・数字・順序に触れる直し、ページをまたぐ直し（表記ゆれ、ページ間の数字、`deck.json` の順、pages.py の資料は共通の関数・定数と `make` の順）。ページをまたぐ直しのうち担当のページに当たる箇所は、親が直し方を決めて、その子の行に足す。担当のファイル・関数は、子が返すまで親も書かない（子の直しとぶつかる）。
   - 分けないラウンド: 直すページが 4 つ未満のラウンドと、どのページの直しも数行で済むラウンド（句点、言葉の差し替え、空のセル）。pages.py のページが関数に分かれていない（前の書き方で `make` に全ページを書いた）資料も分けない（子の関数が `make` から呼ばれない）。子は 1 本 2〜4 分かかり、得にならない（2026-10-14 の 12 枚の試しの 1 本。目安は推測）。ドキュメントは分けない（`build/doc.md` は 1 つのファイルで、どの節を直しても改ページが動く）。
   - 頼み方は「頼み方」の起動のしかた（新しい子、メインと同じモデル）で、依頼文は [prompt_fix.md](prompt_fix.md)。子は担当のページのファイルをそのまま直し（pages.py の資料は、直した関数を `build/fix_<担当>.py` に書き、pages.py を書かない）、組まない。構成案・修正の指示とぶつかる直しと、担当の外に触れる直しは、自分で決めずに返す。子を待つ間に、親は自分の持ち分を、担当の外のファイル（pages.py の資料は pages.py）に入れる。
   - 子が返したら、返した行を手順 4 の表で仕分け直し（直す・聞く）、`slides.py lint <URL>` で要修正を 0 にしてから 1 回だけ組む（`slides.py build`）。子が返らない、`lint` が JSON の誤りで止まるときは、その子の行を親が直す（頼み直して待たない）。pages.py の資料は、`build/` で `slides.py merge fix_<担当>.py …` で合わせ、出た関数の名前が担当と合うかを見て、子が docstring の「import:」に書いた名前を pages.py の import に足してから組む（merge が文法の誤りで止まるときも、親が直す）。子の `fix_<担当>.py` は合わせたらすぐ消す（次のラウンドに同じ名前で残すと、書かずに終わった子の代わりに前のラウンドの関数が合わさる）。`pages.py.bak*` は手順 7 で返すときに消す。
6. **直したページを確かめ直す。** 直しを入れるあいだは `slides.py lint <URL>`（組まない）で要修正を 0 にし、そのラウンドの直しを入れ終えてから 1 回だけ組み、`gslides.py check <URL>`（直したページの画像だけを取り、`$D/changed.json` に書く。ドキュメントは `docs.py check <URL>` で、改ページが動くので全ページ）と一覧を作り直し、直したページと一覧を頼み直す。2 ラウンド目からは、依頼文に「直したこと」（ページごとに 1 行）を足し、新しく起きた欠陥と直りきっていないものだけを返させる。「聞く」にしたものは、挙げ直さないように書く。1〜6 を 1 ラウンドと数え、`factory.toml` の `[review] deck_review_max_rounds` のラウンド（1〜3。書いていなければ 3）までにする。直して欠陥が増えたら、その直しを戻す。ラウンドを重ねるほど、直しの副作用で新しい欠陥が出やすくなるため（下の「根拠」）。
   [deck-review-006] **終わり方。** ラウンドの途中で止めてよいのは、直す指摘が 0 件になったときだけ。直した指摘が 1 件でもあれば、次のラウンドを頼む（最後のラウンドが終わったときを除く）。最後のラウンドで直したものは、子に頼み直さなくてよいが、`gslides.py check`（ドキュメントは `docs.py check`）と直したページの画像を自分で見てから返す。最後のラウンドで直しきれなかった指摘（件数が減らないときも、上限が 1 ラウンドのときも同じ）は、表に「残した（<ラウンドの数> ラウンドで打ち切り）」と書いて返す（直したあと確かめずに終えたり、件数が減らないことを伏せて返したりしないため）。
   [deck-review-013] **次のラウンドを頼む前に、そのラウンドを書き出し、要約する。** そのラウンドの表（下の「指摘の形」）と、次のラウンドの依頼文に足す「直したこと」、聞くことを `$D/review.md` に書き足す（手順 7 で返す表と同じファイル）。文脈を要約する道具を呼べるなら、そのあとで呼ぶ（`../deck-practices/SKILL.md` の deck-practices-005・015）。続きの指示には、何ラウンド目を頼むところからかと、URL・`$D`・読み直すファイル（`$D/review.md`、構成案、このファイルの手順 6 と「頼み方」、依頼文）を書く。呼べなければ、書き足しだけして次のラウンドを頼む。この工程は呼び出しが 1 本あたり平均 68 回あり、40 万の自動の要約 11 回のうち 8 回がここで走っていた（2026-10-14。deck-practices-005 と同じ記録）。
7. **返す。** Drive の URL、指摘の表（下の形）、聞くことの一覧をユーザーに返す。返した表（全部のラウンド）を `$D/review.md` に書き（deck-review-013 で書き足した前のラウンドの行は書き直さず、最後のラウンドの表を足す。次のラウンドに持ち越した指摘は、ページと「何が起きているか」を前のラウンドの文のまま書く。台帳は、この 2 つと決まりで同じ指摘と見分ける）、`python3 <deck-practices のフォルダ>/scripts/ledger.py review --deck <資料のフォルダ> --table $D/review.md` で決まりの台帳に取り込む（決まりごとの結果を dreaming が数える。同じ行は 2 度数えず、ラウンドをまたぐ同じ行はあとのラウンドの結果にする）。確認が済んだら `$D` は消してよい。pages.py の資料で `slides.py merge` が残した `build/pages.py.bak*` も消す。

根拠: ラウンドの上限と、悪化したら戻すのは、描いて見て直すループの研究（ACE。1 回で終わるのは 3 分の 2、上限 3 回、悪化したら巻き戻す）にならった（研究 1-3・1-4）。

## 直す範囲

[deck-review-007] レビューの指摘には、直せば済むものと、直すと資料の言いたいことが変わるものが混ざる。後者を黙って直すと、ユーザーと合意した主張・数字・順序が、ユーザーの知らないうちに変わる（`../deck-practices/SKILL.md` の「進め方」の deck-practices-010「確定した主張・数字・順序は、黙って変えない」）。そこで、直す前にどちらかに分ける。迷ったら聞く。

| 区分 | 例 | どうするか |
|---|---|---|
| 直す | lint の要修正、和欧間のスペース、約物、はみ出し・重なり・フッターとの衝突、矢印のずれ、中身より大きい箱、表記ゆれ、略語の初出、文言を変えない改行の位置 | 直して、表に「直した」と書く。文字を小さくして収めない（言い換え・図解・ページの分割の順に考え、分割は分けて組んでから聞く。`../deck-practices/SKILL.md` の deck-practices-010）。箱を縮めてページの下が空くのはよい（中身を足すのは聞く） |
| 聞く | 見出し・主張・数字・順序を変える、ページを足す・消す・分ける、公平さのために別の例や経路を足す、結論バンドやキッカーを外す、言い回しの好み、レビュー担当が重さを「聞く」にしたもの（決まりからは決まらない、どちらとも取れる） | 直さずに、表に「聞く」と直し方の案を書いて、ユーザーに返す |

## 指摘の形

1 件 1 行。レビュー担当は「直し方の案」まで返し、「結果」と「決まり」は本人が書く。ラウンドごとに件数を比べ、直して増えていないかを見る。

`p<ページ> | <出所: lint・一覧・画像・テキスト・読み手テスト> | <観点 1〜5> | <直す／見直す／聞く> | <何が起きているか> | <直し方の案> | <結果: 直した・残した（理由）・残した（誤り）・聞く> | <決まり>`

- **決まり:** その指摘が当たる決まりの ID（`visual-012`・`ws-visual-003`、顧客の memory は `ws-memory-001`。いくつかなら `,` で区切る）。ID には、その決まりの文（`[ID]` のあとの文）から写した語句を「」で添える（`visual-013「単語や文節の途中で折り返さない」`。語句には `|` と「」を入れない）。`ledger.py review` は、語句がその ID の決まりの文にないか、ID の決まりが見つからないときは、その ID だけ取り込まずに知らせる（ID の付け違いを止める。語句を添えていない ID は、取り込んで件数を知らせる）。lint の指摘は `lint:<規則の名前>`（lint の出力の `[ ]` の中）。当たる決まりがなければ `-`。レビュー担当には探させない（作り方を知らない目で見るため。deck-review-008）。指摘を確かめるときに、本人が `rules/`・顧客の `memory.md`・スキルの決まりから引く。迷うものは `-` にし、当て推量で書かない（決まりが効いたか・外れたかの数になる）。

## 頼み方

- [deck-review-008] **独立したコンテキストで、メインと同じモデルを使う。** 作成時の会話履歴は渡さず、新しいサブエージェントに形式ごとの依頼文と資料のパスだけを渡す。意図は構成案の「資料の種類・聞き手・聞き手の問い・読んだあと聞き手ができること」から読み取らせる。Opus で作成しているなら Opus、Sonnet なら Sonnet、Codex ならメインの実際のモデル ID を使う。
- **Claude Code:** `general-purpose` の新しい子に頼む。モデルは AGENTS.md の「基本方針」のとおり、メインと同じ別名を渡す。浅いレビューは、開いた画像と根拠を確認して同じモデルで新しい子に頼み直す。モデルは黙って変更しない。
- **Codex:** `fork_turns: "none"` で新しい子を作り、`model` にメインの実際のモデル ID、`reasoning_effort` にメインの現在の設定を明示する。このスキルがモデル・effort の明示指定を指示する。全履歴の fork は使わない。`[agents]` の既定モデルに任せるとメインと異なる場合があるため、省略しない。
- [deck-review-009] **T3 Code の委任ツールを使う場合:** ライブの能力一覧で、メインと同じ provider instance・モデルが使えることを確かめ、その対象を指定して新しい委任タスクを作る。各ラウンドとも新しいタスクにし、依頼文・前の指摘・対応・未解決点を明示して渡す。`mode` は `async` にして、手順 3 の待つ間の作業を済ませてから、`t3_thread_wait` で待つ（待ち方は `../deck-practices/SKILL.md` の deck-practices-013）。`mode: "wait"` は、子が動いたまま「fetch failed」を返すことがある。そうなったら頼み直さず、`task_status` で子が動いているかを確かめて、`t3_thread_wait` で待ち直す。
- 同じモデルの指定や会話履歴を渡さない起動ができない環境では、別モデルや全履歴の fork に黙って切り替えず、制約を報告する。返すときは、起動方法と指定したモデル、実モデルを確認できたかを報告する。
- 渡すのは、画像のフォルダ（`$D`）、一覧、テキスト（`deck.md`・`text.md`）、構成案、ルートの `AGENTS.md`、顧客向けならその顧客の `memory.md`（聞き手の好み）と `profile.md`（相手の事業と構成）のパス。ページの JSON・pages.py・`build/doc.md` は渡さない（作り方を知らない目で見てもらう）。
- 観点を分けて 2 本並べてもよい（話の筋と言葉、見た目）。
- **分けて並列に頼む。** 1 枚で閉じる欠陥（観点 2 の 1 枚の中のことと、5 の 1 枚ずつの画像で見るもの）は、ページで分けても見落としが増えない。ページが多く、1 本では後ろのページの見方が浅くなりそうなときや、待ち時間を縮めたいときは、章（扉）ごとか数枚ごとの担当に分け、同時に頼んでよい（Claude Code は 1 つのメッセージで子を何本も呼ぶ。T3 Code の委任は担当ごとに別のタスクにする）。分けるかと分け方は、メインが決める（12 枚の 1 ラウンド目は、1 本で約 10 万トークン・3.4 分だった。`Research/deck_review_skill_design_20261008.md`）。分けるときは次を守る。
  - 全体の 1 本は残す。ページをまたぐもの（観点 1・3、2 のページ間の数字と焼き直し、4 の表記ゆれと略語の初出、5 の一覧）は、全体の 1 本が見る。全体の 1 本には 1 枚の中のことを挙げさせず、原寸の画像は、ページをまたぐ疑いを確かめるときだけ 3 枚まで開かせる（依頼文の替え方は [prompt_slides.md](prompt_slides.md) の頭）。観点で 2 本に分けたときの「話の筋と言葉」が、これに当たる。
  - ページ担当には、担当のページの原寸の画像だけを開かせ、テキストは全文を渡す（前のページで説明した略語や数字を知らないと、的外れな指摘を出す）。ページをまたぐものは、疑いだけを「全体へ」と書いて返させる。担当のページの画像と、そのページの lint・box_pad の指摘は `$D/changed.json`（2 ラウンド目から）の項目をそのまま渡せる。画像は親が取ったものだけを使わせ、子に check を回させない（1 人 1 分 60 枚の上限を取り合う）。
  - 担当は数ページのまとまり（章ごとか、同じ型のページ）にし、1 ページに 1 本にしない（子 1 本ごとに立ち上がりとスキルの読み込みがかかり、モデルの API のレート制限もある）。2 ラウンド目から直したページが 1〜3 枚なら、子を立てずに親が見る。
  - 指摘はメインが合わせる。重なりを 1 件にまとめてから、手順 4 で確かめる。2 ラウンド目からは、直したページが少なければ 1 本でよい。分け方がラウンドで変わるので、件数はページごとに比べる。
- 点数は付けさせない。欠陥の一覧だけを返させる。
- **pi（T3 Code の委任）の子には、指摘をファイルに書かせ、返事は件数とパスだけにさせる**（`<指摘のファイル>` は `$D/review_<ラウンド>_<担当>.md`）。pi の要約には、道具の結果の先頭 2,000 文字しか入らない。受け取ってから直すまでに要約が入ると、後ろの指摘が消える（2026-10-10。1 本で 1.6 万文字あった。`Research/pi_compaction_deck_workflow_20261010/README.md`）。ほかの子には、依頼文の「ここまでを <指摘のファイル> に書き…」の行を消して頼み、返事で受け取る。
- 指摘を入れる前に、そのページで言いたい 1 文からそれないかを確かめる。それるものは「聞く」に入れる。
