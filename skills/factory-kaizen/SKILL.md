# 工場を改善する（大元に PR を出す）

ワークスペースは、修正の指示とやり取りの積み重ねで、決まり（AGENTS.md・`rules/`）と点検（`rules/deck-build/checks.py`）を育てていく 1 つのプロダクトとして扱う。そのうち、ほかの人にも効くもの（その人の好みや顧客の事情でないもの）だけを、ここで大元（プラグイン）に PR として出す。何をどこに置くかは `../deck-practices/rules.md` の「決まりの層」。

前提: `factory.toml` の `[factory] source` に、プラグインのリポジトリの git の checkout があること（持ち主でなければ fork を `gh repo fork --clone` で作る）。`gh` にログインしていること。ワークスペースで回す。

```sh
P="python3 <このスキルのフォルダ>/scripts/kaizen.py"
$P start <名前>                                   # .factory/kaizen/<名前>/repo に worktree（ブランチ kaizen/<名前>）
$P lint <名前> <資料の URL ...>                    # いまの資料に、前の版と変えた版の lint をかけて比べる
$P rebuild <名前> <資料のフォルダ ...> [--pages 2,5]   # 正本から前後の版で仮に組み、変わったページの画像を並べる（仮の資料はゴミ箱へ）
$P open <名前> --title <題> --body <本文.md> [--draft]
$P clean <名前>                                   # マージか却下のあと
```

## 手順

1. **出すものを決める。** 何を変えるか、なぜか（決まりの台帳の `ledger.py why <決まりの ID>` に出る指摘と資料・顧客の数、再発とレビューの結果、`.factory/lint_runs.jsonl` や dreaming の記録の数字）を 1 つにまとめる。原文と資料の名前は PR に書かず（2 の `start` のあとは `verify/detail.md` にだけ書く）、PR には数を書く。ワークスペースの `rules/` に写しがあるなら、それを大元に移す形にする。顧客の `memory.md`（`ws-memory`）の好みは、じかに上げない（2 社以上で同じなら、dreaming が先に `rules/` に寄せる。`../deck-practices/rules.md` の「顧客の memory」）。移した決まりには、プラグインの接頭辞の新しい ID を付ける（worktree の中で同じ接頭辞のいちばん大きい番号の次。`ws-` は付けない）。本文には ID と短い理由だけを書き、日付と原文は書かない（`../deck-practices/rules.md` の「修正の指示の戻し方」）。
2. **`start` して、`.factory/kaizen/<名前>/repo` の中を直し、commit する。** プラグインの入った場所や、元のリポジトリの checkout そのものは直さない。commit の書き方はそのリポジトリの決まりに合わせる。
3. **過去の資料で確かめる。** 変えたものに合わせて選ぶ。
   - 決まり・点検（`lint.py`、`checks.py` から移したもの）: `lint` を、その規則が効くはずの資料と、効いてはいけない資料の両方にかける。候補は `.factory/lint_runs.jsonl` の資料（その規則の指摘が出た資料）と `references_index.md` の「作った」。
   - 組み方・見た目（`slides.py`・`docs.py`・`template.py`、`visual.md`・`visual_doc.md`、テンプレート、画像）: `rebuild` を、変わるはずのページがある資料にかける。前後の画像は必須（`open` が止める）。
   - 見た目が前後で変わらない変更（lint だけの変更で `visual.md` の文も変えたときなど）: `rebuild` は「変わったページ: なし」になり、画像を作らない。変えた決まりが効くページの画像（見本を組んだものなど）を `verify/img/` に手で置き、本文の「過去資料での検証」に、見た目が前後で変わらないことを書く。`rebuild` の目印（`verify/pr.md` の `<!-- img:<ファイル名> -->`）のない画像は、`open` が検証の記録の末尾の「ほかの画像」にまとめて載せる（ほかの場所に載せたいなら、`verify/pr.md` に目印を足す）。
   - 文だけの直し（手順の書き換えなど）: 検証が要らなければ、本文の「過去資料での検証」に `検証しない理由:` を書く。
   - 結果を読み、増えた指摘が誤検知でないか、消えた指摘が本当に直ってよいものかを、`.factory/kaizen/<名前>/verify/detail.md`（資料の名前と指摘の本文が入る）で確かめる。思った結果でなければ 2 に戻る。
4. **本文を書く。** 下の型で `.factory/kaizen/<名前>/body.md` に書く。
5. **ユーザーに確かめてから `open` する。** PR はリポジトリの外の人も読む。次の 2 つを見せて、よいと言われてから出す。
   - 本文
   - 載せる画像（`verify/img/`）。顧客向けの資料（`Customers/`）の画像は、顧客の名前・数字・社外秘が写るので、原則として載せない。社内向けか、公開の内容だけの資料で確かめ直す。
   `open` は、節がそろっているか、検証があるか、見た目の変更に画像があるかを確かめてから、画像を `pr-assets` ブランチに置き、検証の記録（資料は「資料 1」の番号だけ。名前・URL・本文は出さない）を本文に足して PR を作る。
6. **返す。** PR の URL を返す。dreaming のプラグインへの提案（P-ID）から出したなら、`ledger.py sent <P-ID> --pr <URL>` で決まりの台帳に残す（PR で提案と違う ID にしたら `--rule <その ID>` も付ける）（dreaming が同じ提案を出し直さない）。マージされずに閉じられたら `ledger.py reject <P-ID> --reason <理由>`。マージされたら `claude plugin update ai-deck-factory@ai-deck-factory`（pi は入れ方による）で届くことを伝え、`clean` する。届くと、dreaming が `ledger.py candidates` の「写しを消す」で、ワークスペースの `rules/` の写しを消す提案を出す（上げた文が、入っているプラグインにあるかで見る）。出典の指摘は `sent` で新しい ID につながっている。出典にしなかった指摘が写しに残っていれば（`ledger.py why <ws-ID>`）、指摘ごとに `ledger.py route <c-ID> <プラグインの ID>` でつなぎ直す。

## 本文の型

```markdown
## 変えること
<何がどう変わるか。1〜3 行>

## 理由
<なぜ大元で変えるべきか。ほかの人にも効く理由>

## 背景
<きっかけ。ユーザーの発言（原文）、起きたこと、数字（lint の残り方、dreaming の記録）。顧客の名前は書かない>

## 過去資料での検証
<何で確かめたか、結果をどう読んだか（増えた指摘・消えた指摘が正しいか）。下に factory-kaizen が表と画像を足す>

## 影響と戻し方
<既存の資料・ワークスペースの rules/ への影響。戻すときは revert でよいか>
```

## 注意

- PR の本文と画像に、顧客の名前・社内の URL・個人名を入れない（AGENTS.md の「社外秘と顧客の情報」と同じ）。`open` は、題・本文・コミットメッセージ・ブランチの名前・変えたファイルの名前・足した行に、ワークスペースの `Customers/` の顧客の名前、`Customers/<顧客>/` と `Internal/` の資料のフォルダの名前（年の 4 桁の数字が入ったもの。決まりでは `<内容>_<日付>`）、`factory.toml` の `[factory] private` の語があると止める。日付のないフォルダの名前や、日本語の社名・製品名は `[factory] private` に書く。決まりの出典の括弧は「顧客向けの資料の p.3」「ユーザー「（顧客）は〜」」のように書く。
- 検証で組んだ仮の資料は `drive.factory` に作り、終わったらゴミ箱に移す（`--keep` のときだけ残る）。lint の記録（`.factory/lint_runs.jsonl`）には入らない。
