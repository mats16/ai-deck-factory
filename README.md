# AI Deck Factory

日本語のスライド（Google Slides）とドキュメント（Google Docs）を Slides API・Docs API で直接組み、lint・Google が描いたページの画像・別の目のレビューで確かめて渡す仕組み。会話の記録から、決まりに戻し忘れた指示を拾って決まりを育てていく（dreaming）。

同じソースを、Claude Code のプラグインと pi のパッケージの両方から入れられる。

## 中身

| スキル | すること |
|---|---|
| `factory-init` | ワークスペースを作る（AGENTS.md・CLAUDE.md・factory.toml・references_index.md・rules/ の雛形と資料のフォルダ。あるファイルは上書きしない） |
| `factory-doctor` | 前提を確かめる（Python・uv、ワークスペース、スキルの重なり、Google の認証、テンプレートと Drive のフォルダ、gh） |
| `factory-kaizen` | プラグインの改善を、過去の資料で前後を比べてから Issue にする（理由・背景・検証の結果・見た目なら画像・変更案の差分）。PR は持ち主が作る |
| `deck-practices` | 資料を作る・直すときに最初に読む。全体の流れと各工程の意図、作業の始め方、構成案と言葉、見た目の決まり、決まりの層と修正の指示の戻し方 |
| `deck-template` | 会社のテンプレートから、AI Deck Factory のテンプレート（テーマ）を作る。日本語のテンプレートがある・英語しかない・ない、の 3 つ。書体・大きさ・大枠の色を残し、和文の書体とコントラストを合わせる（`template.py audit`、`slides.py lint <テーマのファイル>`） |
| `deck-build` | Google Slides を組む（`slides.py`）・確かめる（`gslides.py check`・`lint.py`）。Drive への置き方。スクリプトはドキュメントと共有。使い回す画像は `assets/`、一通りの書き方を入れた JSON のページの見本は `samples/json/` |
| `doc-build` | Google Docs を `build/doc.md` から組む・確かめる（`docs.py`）。テンプレートはワークスペースの `rules/doc-build/templates/` |
| `deck-review` | 返す前の全体のレビュー。会話を渡さない新しいサブエージェント（メインと同じモデル）に頼む |
| `customer-profile` | 顧客の profile（`Customers/<顧客>/profile.md`。事業、組織、技術の構成、エンジニアの好みと文化、いまの取り組み）を `[sources]` と公開の情報から作る・取り直す・書き足す。ユーザーが言った行は残す |
| `deck-research` | ベストプラクティスの調べ直し。調べた記録（`state.md`・`log/`）はワークスペースの `Research/deck_research/` |
| `dreaming` | 会話の記録から、決まりを定期的に整理する |

```
INSTALL.md                        会話で入れるときに、エージェントが読む手順（README の「会話で入れる」）
.claude-plugin/plugin.json        Claude Code のプラグイン
.claude-plugin/marketplace.json   このリポジトリをそのままマーケットプレイスにする
package.json                      pi のパッケージ（pi.skills: ./skills）
skills/                           上の 11 個（Claude Code と pi で共通）
hooks/hooks.json                  Claude Code の hook（プラグインのファイルを読んだら rules/ を、顧客の資料を読んだら memory.md を続けて出す）
hooks/rules_overlay.py            その中身（Claude Code と pi で共有）
extensions/rules.ts               pi の拡張（同じことを pi の read・bash で）
docs/                             設定のガイド（claude-code-plugin.md: Claude Code に入れる範囲と確かめ方。pi.md: pi に入れる範囲と確かめ方。development.md: 開発しながら動作を見る）
```

## 会話で入れる

Claude Code か pi を開き、次を貼る（どのフォルダで開いた会話でもよい）。

```text
AI Deck Factory を入れて、ワークスペースを作ってください。
手順は https://raw.githubusercontent.com/mats16/ai-deck-factory/main/INSTALL.md にあります。WebFetch ではなく curl で読み、そのとおりに進めてください。
```

エージェントが [INSTALL.md](INSTALL.md) に従い、ワークスペースにするフォルダと全社の共有テーマのフォルダ、定期の整理を回すかを聞き、Python・uv を見て、そのフォルダだけにプラグインを入れる。続けて、入れた `factory-init` と `factory-doctor` の手順で `factory.toml`（Google の認証、テーマ、Drive の置き場所、材料を集める道具）を一緒に埋め、要修正が 0 になるまで進める。最後に、定期の整理（dreaming）を回すなら、エージェントが自分の道具にあるスケジューラー（T3 Code・Claude Code Desktop・Omnigent など）に登録する（なければ、launchd か cron の入れ方を示す）。自分で回すのは、ブラウザが開く Google のログインだけ。終わったら、ワークスペースの直下で会話を開き直す。

## 入れ方

手で入れるときの手順。Python 3.11 以上と `uv` が要る。Google の認証は下の「Google の認証」。

**Claude Code**

```sh
claude plugin marketplace add https://github.com/mats16/ai-deck-factory.git   # 手元の checkout なら ~/Projects/ai-deck-factory
claude plugin install ai-deck-factory@ai-deck-factory
claude plugin update ai-deck-factory@ai-deck-factory               # GitHub から入れたとき、直して commit・push したあと
```

マーケットプレイスが GitHub を指していれば、会話は `~/.claude/plugins/cache/` に写した版を読む。`plugin.json` に版を書いていないので commit の SHA が版になり、push してから `update` で届く。手元のパスで足したなら、会話は checkout をそのまま読むので、保存すれば次の会話から効く（commit も `update` も要らない）。手元で直しながら試すときは `claude --plugin-dir ~/Projects/ai-deck-factory`（worktree と検証用のワークスペースで試す手順は [docs/development.md](docs/development.md)）。スキルは `/ai-deck-factory:factory-init` のように呼ぶ。資料のフォルダだけで効かせる（`--scope project`）入れ方と、効いている範囲の確かめ方は [docs/claude-code-plugin.md](docs/claude-code-plugin.md)。

**pi**

```sh
pi install ~/Projects/ai-deck-factory                                # 手元の checkout をそのまま読む（写さない）
pi install git:github.com/mats16/ai-deck-factory        # git から
```

スキルは `/skill:factory-init` のように呼ぶ。資料のフォルダだけで効かせる（`-l`）入れ方と、project trust、効いている範囲の確かめ方は [docs/pi.md](docs/pi.md)。

入れたら、ワークスペースにするフォルダで `factory-init`、続けて `factory-doctor` を呼ぶ。

## ワークスペース

資料を置くフォルダ（例: `~/Documents`）。スクリプトは、今いるフォルダから上へたどって最初に見つかった `factory.toml` のフォルダをワークスペースとして扱う。`factory-init` が置くもの:

- `factory.toml`: 人ごとに変わる値（認証、テンプレート〔`[slides.templates]`: テーマの名前 = テンプレートの URL〕と社名、Drive の置き場所、材料を集める道具〔`[sources]`: 社内の検索・チャット・会議の記録・wiki など〕、レビューの進め方〔`[review]`: 構成を決めたあとを誰が見るか、`/deck-review` の周の上限〕）。テンプレートは `deck-build/scripts/template.py visual --from-base`（`company` も）で作ると URL が書き込まれる。元にするテンプレートは `factory.toml` に持たず、`--from-base <元の URL>` で渡す。渡さなければ、白紙の pptx（`deck-build/assets/blank.pptx`）を Google Slides に変換して上げ、そこから作る。会社で配るテーマは全社の共有テーマのフォルダ（`[drive] shared_themes`）に置き、使う人は `slides.py themes` で見つけて `slides.py theme <url>` で写す（`deck-build/slides.md` の 3）。
- `themes/slides/<名前>.json`: テーマのファイル（`kind: Theme`。色・書体・著作権表示・表紙と扉のパターンと、使い分けの `description`。エージェントが `slides.py themes` の一覧から資料ごとに選ぶ）。組み込みの visual・company はプラグインの `deck-build/themes/` にあり、同じ名前のファイルを置くとそちらが勝つ。factory-init は置かない（会社のテーマを作るとき〔`deck-template`〕と、共有のテーマを写すときにできる）。
- `AGENTS.md`（と `@AGENTS.md` を読む `CLAUDE.md`）: どの会話でも要る決まり。
- `rules/<スキル>/<ファイル>`: 資料を作る場面だけで要る、このワークスペースの決まり。
- `Customers/<顧客>/memory.md`: その顧客の資料への好み（どう作るか。相手が何者かは `profile.md`）（顧客の memory）。その顧客の資料の `構成案*.md` などを開くと、hook が続けて出す。
- `Customers/<顧客>/profile.md`: その顧客の事業・組織・技術の構成・エンジニアの好み（顧客の profile。行ごとに出典と日付）。`customer-profile` が作り、顧客向けの資料の作り始めに読む。30 日より古ければ取り直す。
- `Customers/`・`Internal/`・`Research/`、`references_index.md`: 資料と台帳。`Research/deck_research/` は `deck-research` の調べ直しの記録（`state.md`・`log/`。代表の 3 枚の選び方の記録も）。
- `.factory/`: スクリプトが書く記録。`ledger.jsonl`（決まりの台帳。修正の指示、決まりの ID ごとの出典と再発、dreaming の提案・適用・却下とプラグインへの提案の Issue、判断待ちと答え、deck-review の指摘の結果。`deck-practices/scripts/ledger.py` が読み書きする）、`lint_runs.jsonl`（`lint.py --stats` が読む）、`spec_raw.jsonl`（JSON のページの形の外の書き方の数。`slides.py stats` が読む）、`dreaming/last_run`・`dreaming/log/`・`dreaming/backup/`、`profile/`（`customer-profile` が取り直す前の顧客の profile）。

自分だけの画像は `assets/` に置く。`slides.asset()` はここを先に探し、なければ `deck-build/assets/` を使う。

## 書体

テーマに書けば変えられる。書かなければ既定の書体で組む。

| 使うところ | 書く場所 | 既定 | 書ける書体 |
|---|---|---|---|
| スライドの本文 | テーマのファイル（`themes/slides/<名前>.json`）の `font`（`template.py` がマスターに書く） | Noto Sans JP | 下の「本文の書体」の 18 個（`slides.py` の `JP_FONTS`）と、欧文の DM Sans（`FONT_EM`）。ほかは `slides.py lint` と `template.py` が止める |
| スライドのコード | テーマのファイルの `mono` | Cascadia Mono | Google Fonts の等幅の書体。リガチャのある書体（`LIGATURE_MONO`）は止める |
| ドキュメントの本文 | `[docs.themes.<名前>] font` | Noto Sans JP | スライドの本文と同じ |
| ドキュメントのコード | `[docs.themes.<名前>] mono` | Cascadia Mono | スライドのコードと同じ |

- **文字の幅の見込みは、測った書体のものを使う。** `slides.py` の `em_width` は、本文の英数字を `FONT_EM` の幅（Noto Sans JP Regular の `ASCII_EM`、DM Sans の `DM_SANS_EM`）で、コードを `MONO_EM`（Cascadia Mono、0.586 em）で見込む。測っていない書体は Noto Sans JP の幅で見込み、折り返しの見込み（組むときの警告、`d.card` の高さ、lint の行数）がずれるので、Google が描いたページの画像で見る。
- **Google Fonts にない名前は、API が受け付けて黙って別の書体で描く。** 書いたら見本のページ（`template.py <名前>`、ドキュメントはそのテーマの文書）を組み、画像で確かめる。
- lint の「書体が … でない」「等幅の … に和文」は、テーマの書体と比べる。

**本文の書体（和文あり）:** 2026-10-07 に、テンプレートを複製した試しのデッキで同じ文を書体ごとに描き、Google Slides で描けることを確かめた。Google Docs で組んでいるのは Noto Sans JP だけで、ほかは Docs では確かめていない。印象ごとの選び方は `deck-template/SKILL.md` の「書体」。

| 分け | 書体 |
|---|---|
| ゴシック | Noto Sans JP（既定）、IBM Plex Sans JP、BIZ UDPGothic、BIZ UDGothic、Zen Kaku Gothic New、M PLUS 1p、M PLUS 2、LINE Seed JP、Murecho、Sawarabi Gothic |
| 丸ゴシック | M PLUS Rounded 1c、Zen Maru Gothic、Kosugi Maru |
| 明朝 | Noto Serif JP、BIZ UDPMincho、Shippori Mincho、Zen Old Mincho |
| 手書き風 | Klee One |
| 描けない（明朝と欧文のセリフ体になる。`template.py` の `NO_RENDER`） | Noto Sans CJK JP、Hiragino Sans、Yu Gothic |

**本文の書体（欧文）:** DM Sans だけ書ける。和文の字がなく、Google Slides は和文を別のゴシックで描く（どの書体になるかは選べない）。2026-10-15 に、Google Fonts の版（可変）の英数字の幅を測り、Google Slides が字の大きさによらず opsz 14 の版で描くことを、12・18・30pt で描いた画像で確かめた。

**コードの等幅の書体:** 2026-10-09 に調べた。等幅には和文の字形がないので、和文は本文の書体のまま、英数字の続きにだけ付ける。

| 分け | 書体 |
|---|---|
| Google Slides で描いたページの画像で確かめた | Cascadia Mono（既定。リガチャなし） |
| リガチャがないことを、Google Fonts の版を HarfBuzz で組んで確かめた（Google が描いたページでは見ていない） | Source Code Pro、Fira Mono、IBM Plex Mono、Roboto Mono |
| リガチャが出る（`->` が矢印 1 字になる。`mono` に書くと止める） | JetBrains Mono（Google Slides で出た）、Fira Code、Cascadia Code |
| Google Fonts にない（Arial で描かれる） | Iosevka、Hack、SF Mono、Menlo、Commit Mono、Monaspace |

## 決まりの層と育て方

ワークスペースは、やり取りの積み重ねで決まりと点検を育てていく 1 つのプロダクト。大元（プラグイン）を直すべきものだけを Issue にし、持ち主が Issue から直す。

| 層 | 置き場所 | 中身 | 誰が変えるか |
|---|---|---|---|
| 顧客の memory（その顧客の資料で、いちばん優先） | `Customers/<顧客>/memory.md` | その顧客の資料への好み（どう作るか。相手が何者かは `profile.md`） | 作る会話がその場で書く。dreaming は提案する。2 社以上で同じ趣旨なら `rules/` に寄せる |
| ワークスペース（優先） | `AGENTS.md`、`rules/<スキル>/<ファイル>`、`rules/deck-build/checks.py` | その人・その組織の決まりと点検、修正の指示で育つもの | 作る会話がその場で戻す。dreaming は提案し、「適用」で当てる。経緯は決まりの台帳（`.factory/ledger.jsonl`）に残す（git は前提にしない） |
| プラグイン | `skills/`（入った場所は読むだけ） | 誰が使っても同じ決まり、点検、スクリプト、テンプレート | `factory-kaizen` で Issue。持ち主が直してマージしたら `update` で届く |

- **決まりの本文と経緯を分ける。** 決まりは 1 項目ごとに ID（プラグインは `[visual-<番号>]`、ワークスペースは `[ws-visual-<番号>]`）と短い理由だけを書く。日付・ユーザーの言葉・どの資料か・ユーザーが決めたかは、ワークスペースの決まりの台帳に ID でつなぐ（`ledger.py why <ID>`）。資料・顧客の数から、ワークスペースに寄せるか、プラグインに上げるかを決める。
- **`rules/` と memory は読み忘れない。** プラグインのファイルを開くと（Claude Code は Read・Bash・Skill、pi は read・bash）、hook が同じパスの `rules/` のファイルを続けて出す。顧客の資料の `構成案*.md`・`社内メモ_*.md`・`references.md` を開くと、その顧客の `memory.md` を続けて出す。
- **次の一手は台帳が出す。** `ledger.py candidates` が、決まりごとの数から、下ろす（点検か作る手順へ）・書き直す・条件を足す・上げる・写しを消す・上書きを見直すを出す。境目（2 本以上の資料、2 社以上の顧客）はスクリプトが持ち、dreaming は趣旨と提案の文を考える。
- **点検もワークスペースで育てる。** `rules/deck-build/checks.py` の `slides(p, r)`・`doc(doc, r)` を、lint（`gslides.py check`・`docs.py check`）が毎回呼ぶ。`HARD` に入れた名前は要修正。書き方は `factory-init/templates/rules/README.md`。
- **大元に上げる。** ほかの人にも効くものは、dreaming が「プラグインに上げる」提案にし、`factory-kaizen` で出す。
  1. 元のリポジトリを `.factory/kaizen/` に clone して変更案を書く（手元に checkout や fork は要らない）。
  2. 過去の資料で確かめる。lint は前の版と変えた版をかけ比べ、見た目は正本から両方の版で仮に組み直してページの画像を並べる。
  3. 理由・背景・検証の結果・画像・変更案の差分を入れた Issue を作る。Issue には資料の名前・URL・本文を出さず、「資料 1」の番号と規則ごとの数の変化、ユーザーが選んだ画像だけを載せる。ブランチは push しない。
  4. 持ち主が Issue を読んで入れるかを決め、ほかのコードと合わせて直して PR にする（simplify・レビューも持ち主がする）。
  5. 直しが届いたら、`rules/` の写しを消す。
- `deck-research` の調べ直しの結果も、`factory-kaizen` で Issue にする（変更案に入れるのはスキルの直しと `sources.md`。調べた記録はワークスペースに残す）。

## Google の認証

API を直接呼ぶ（MCP は使わない）。トークンは `deck-build/scripts/gapi.py` が次の順に取る。gcloud も、ほかの Google のスキルも、動かすときには要らない。

1. 環境変数 `GOOGLE_OAUTH_ACCESS_TOKEN`（ほかの仕組みで取ったトークンを渡すとき）
2. `authorized_user` の認証情報の JSON（`GOOGLE_APPLICATION_CREDENTIALS`、なければ gcloud の ADC のファイル）の refresh_token。作るのは `gcloud auth application-default login --scopes=…`（`factory-doctor` がコマンドを出す）

gcloud の既定の OAuth クライアントで作った認証情報は、`google.quota_project` がないと 403 になる。

## 決めたこと

- 2026-10-11: setup は前の検討の `/deck-init`・`/deck-doctor` の案を、今の作りに合わせて入れる。名前は `factory-init`・`factory-doctor`（ユーザー「名前は `factory-init` `factory-doctor` のほうがいい気がします」）。
